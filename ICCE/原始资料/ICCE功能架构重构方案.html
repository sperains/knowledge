二、目标调用链

UI Permission Gate
  -> UI / Tool Interaction
  -> Application Use Case
  -> Domain Planner / Rule
  -> Mutation Runtime
  -> Store + Event Adapter + Transaction Infrastructure
层级负责禁止
UI Permission / Interaction按用户实际权限和 DiagramType 决定工具、快捷键、拖拽、缩放和删除是否可用。不直接写 Store，不负责事务和领域计划。
Application Use Case接收已经通过 UI 准入的用户意图，组织一次完整用例和事务。不读取权限、Store 或页面状态，不实现几何或关系规则。
Domain Planner / Rule计算数据结构是否合法、变更计划、影响范围和关系决策。不判断用户是否可以创建、移动、缩放或删除，不依赖 Vue、Pinia、EventBus 或协作连接。
Mutation Runtime执行原子图形/连线/关系写入，参与事务并调用事件适配器。不承担区域扩展、删除级联、移动策略或父子关系编排。
Store / Event / Transaction提供状态写入、事实事件和事务记录等基础设施实现。不反向决定业务意图。
权限组织决策：图形创建、删除、移动、缩放、区域操作和连线操作权限只在 UI 交互入口判断。 权限函数直接接收 DiagramType，不通过 tabValue 转换。Application command 不再重复判断权限； Domain 只校验图形类型、包含关系、删除计划、移动计划等数据规则。前端 UI 权限不是后端安全边界，接口仍需执行服务端授权。

说明：薄网关不是必选层。如果它只是参数转发，就直接合并到 Mutation Runtime adapter；只有存在稳定基础设施契约时才保留接口。

1. 重构启动时问题

  • canvas-controller.ts 同时承担图形、连线、关系、区域、快照、事件等职责，领域边界不清晰。
  • useStageEvents.ts 和原 useCollabSync.ts 混合了编排、适配和部分业务规则。
  • 调试页、示例页和生产页混用，导致构建边界不干净。
  • 部分规则散落在工具层、组件层和控制器层，后续扩展成本持续上升。
这些问题不意味着当前实现不可用，而是说明系统已经进入需要系统性收敛的阶段。重构目标应当是稳定迁移，而不是简单重写。

1.1 非目标

  • 不在同一轮迁移中同时引入新的交互模式或新的图形模型。

infrastructure/stores/ 负责真正的状态读写，但“谁来触发最后一层写入”应收口在 application 层，而不是让 UI、工具或领域服务直接碰 store。

规划说明

  • app/ 只放页面入口与装配，不承载业务实现。这里的职责是把路由、页面骨架和全局能力接起来，尽量做到薄。
  • application/ 按用户意图组织，不按技术动作组织。比如“删除选中项”“恢复画布”“设置归属关系”是用例，“更新图形属性”只是实现细节。
  • application/commands/ 默认作为唯一对外执行入口；如果后续确有“多个命令必须作为一个提交单元”或“需要统一横切装饰”的需求，再补 application/facade/，且只能做组合、事务边界和横切收口，不能长成第二个控制器。
  • application/transaction/ 是后续事务记录和历史回放的预留位置，目前仅保留现有画布操作同步能力，不提前建设历史链路。临时预览态、拖拽中间态和高频鼠标反馈留在 ui/。
  • domain/ 是整个方案的核心沉淀区。凡是稳定、可测试、可复用、与框架无关的规则，都优先沉到这里。
  • domain/model/ 负责承载领域对象本身，包括实体、值对象、聚合状态、快照结构和少量与模型强相关的基础方法，不建议退化成纯类型声明仓库。
  • infrastructure/ 负责和外部世界接轨，包括状态存储、协作同步、事件总线、历史记录和适配器，不参与业务规则判断。
  • ui/ 只处理交互编排和视觉展示。Stage 事件路由、工具行为、浮层定位、选择高亮都在这里，但不直接改核心领域数据。
  • debug/ 与生产代码严格分离。调试页、示例页、实验页都放这里，构建时可以明确排除或仅在开发态引入。
  • docs/ 只放架构、迁移、规则说明和演进记录，避免设计讨论散落在业务目录里。

事务协议

以下协议仅作为未来引入历史记录或命令式回放时的设计预案，当前实现不落地这些字段。

type MutationMeta = {
  operationId: string;
  transactionId?: string;
  action: 'add' | 'modify' | 'delete';
  intent: 'create-shape' | 'move-selection' | 'delete-selection' | 'connect-line' | 'set-containment' | 'hydrate-diagram';
  phase: 'preview' | 'commit' | 'replay';
  timestamp: number;
  userId?: string | null;
  reason?: string;
};
  • operationId 串起同一次用户意图的多次变更，transactionId 标识一次实际提交边界。
  • action、intent、phase 用来区分动作、意图和阶段，不要混用。
  • recording、replay 和 commit 的职责分开，预览态不落账，提交态才进入事务层。

事务层的使用方式可以概括为：命令生成元数据，记录器写入可回放变更，回放器恢复同一结果。

权限边界

ICCE 里的“权限节点判断”不要当成单一概念处理，最好拆成三类：权限数据、权限判定、权限展示。这样可以避免把后端授权、业务规则和 UI 状态混在同一层。

类型 主要职责 建议归位 典型内容 不能做什么
权限数据 接收并整理外部授权信息 infrastructure/ 或 app/ 角色、节点权限树、项目授权范围、后端返回的可见性标记 不做复杂业务判断，不直接控制界面细节
交互权限判定 按用户权限和 DiagramType 判断 UI 交互是否可用 permissions/，由 UI 入口调用 能否创建图形、能否删除、能否设置包含关系、能否操作某类节点 不直接操作组件，不写死展示逻辑
权限展示 根据判定结果决定展示方式 ui/ 按钮置灰、菜单隐藏、节点禁用、提示文案、无权限 tooltip 不自己重新计算权限，不直接读后端原始授权结构
判断原则：用户交互资格由 permissions/ 提供给 UI；授权信息来源由基础设施或页面会话提供；领域规则只回答数据结构是否合法。

服务边界表

服务 推荐输入 推荐输出 不能做什么
ContainmentService childId、parentId、diagramType、relationType、现有关系信息 是否允许归属、关系变更结果、必要的重挂建议 不直接改 store，不发 UI 事件，不处理拖拽手势

DiagramPolicyService diagramType、shapeType、relationType、节点属性摘要 能力判定、归一化结果、准入结论 不控制 UI 表现，不写 store，不承担事务边界

这张表的判断标准是：服务负责“算清楚”，不负责“落地执行”。只要开始碰 store、事件、视图或权限入口，它就该继续下沉或上移。

服务输入输出规范

domain/services/ 里的服务应当围绕“领域规则与稳定计算”设计，输入尽量小而明确，输出尽量结构化、可解释、可测试。

维度 输入要求 输出要求
形态 优先使用显式参数对象，不直接传组件、store、DOM 或 Konva 实例 优先返回纯对象、结果结构、决策对象或变更集合
稳定性 输入应可序列化、可记录、可回放，少用函数和外部引用 输出应在同样输入下保持确定性，便于测试和重放
语义 参数名要表达业务含义，例如 childId、diagramType、selectedIds 返回值要说明“发生了什么”，不要只返回一个裸布尔值
边界 输入只放本次计算必须的内容，不塞 UI 过程态和临时预览态 输出不要混 UI 文案、路由跳转或组件状态
服务层最重要的约束是“输入小、输出清楚”。一旦服务开始直接改 store、发事件或拼 UI 状态，它就已经偏离领域服务职责了。

5. 应用层用例

应用层不按“增删改查”组织，而按“用户意图”组织。

这里的“用户意图”，指的是用户站在业务层面真正想完成的一件事，而不是系统内部的某个技术步骤。比如“创建图形”“移动选中项”“删除选中项”“设置包含关系”“恢复画布”都是意图；“更新属性”“同步连线端点”“写入存储”“刷新视图”不是意图，而是实现步骤。
用例 职责 说明
CreateShape 创建图形 调用领域服务完成准入、布局和关系创建
MoveSelection 移动选中项 处理批量移动、区域扩展、连线联动
DeleteSelection 删除选中项 负责级联删除、选中态同步和事件广播

HydrateDiagram 恢复画布 处理快照恢复和结构修复

应用层默认只保留命令入口；如果后续出现复合提交或横切装饰需求，再补一个极薄的门面壳。门面只做用例分发、提交边界管理和统一事件出口，不再承担业务规则。这里的“提交边界”指确认落账的时刻，不是鼠标拖拽或按键过程本身。

命令规范

application/commands/ 里的命令统一按“一个命令对应一个用户意图”的原则设计。更细的意图拆解已放在“应用层用例”中，这里只保留命令边界与执行规则。

规则 要求 目的
单一意图 一个命令只表达一个可识别的用户动作，例如创建图形、删除选中项、设置包含关系 避免一个命令混入多个业务目标，降低后续拆分成本
只做编排 命令只负责调用顺序、事务包裹、事件派发和元数据记录，不承载核心规则 把规则稳定沉到领域层，命令保持薄
不碰 UI 不直接读取组件状态，不操作 DOM / Konva，不处理鼠标键盘等交互细节 减少对视图层和具体渲染实现的耦合
可回放 进入历史或协作链路的命令必须尽量确定性，随机值、时间戳、临时标识要统一注入 保证撤销、重做、协作回放结果一致
不直连实现存储 优先依赖应用上下文或命令入口，不直接绑定具体 Store 实现 方便后续替换状态实现或调整协作链路
命名稳定 文件名采用“动词-对象”的形式，类名或导出名与文件名保持一致 让命令语义一眼可读，减少歧义
如果某个命令开始出现大量分支、循环和规则判断，通常说明它已经膨胀了，应把核心逻辑下沉到领域服务，再让命令只保留编排壳。

输入输出规范

  • 输入优先使用稳定的参数对象，不要直接把组件实例、事件对象或 Store 整个传进来。
  • 输入里只保留执行本次意图必须的数据，例如目标标识、位置、关系信息、选择范围、快照版本。
  • 输出优先返回明确结果或执行状态，不要依赖外部副作用来表达结果。
  • 如果命令失败，失败原因应可枚举、可解释，避免只抛出不透明的通用异常。
  • 凡是需要重放的字段，都应从输入里显式传入或由上层统一注入，避免命令内部临时生成后无法复现。

type CommandResult = {
  ok: true;
  meta?: {
    operationId?: string;
    transactionId?: string;
    shapeId?: string;
  };
} | {
  ok: false;
  code: string;
  message: string;
};

type CreateShapeInput = {
  diagramId: string;
  shapeType: string;
  position: { x: number; y: number };
  containerId?: string;
  source?: 'user' | 'collab' | 'replay' | 'import';
};

    async function executeCreateShape(
      input: CreateShapeInput,
      ctx: CommandContext,
    ): Promise<CommandResult> {
      const decision = await ctx.policy.canCreateShape(input);
      if (!decision.allowed) {
        return { ok: false, code: decision.code, message: decision.reason };
      }

      const containmentPlan = input.containerId
        ? await ctx.containmentService.planAfterCreate({
            diagramId: input.diagramId,
            shapeType: input.shapeType,
            containerId: input.containerId,
          })
        : null;
      const layoutPlan = await ctx.regionLayoutService.planAfterCreate({
        diagramId: input.diagramId,
        shapeType: input.shapeType,
        position: input.position,
        containerId: input.containerId ?? null,
      });

      const meta = await ctx.transaction.run(async () => {
        const shape = await ctx.shapeService.create({
          ...input,
          containmentPlan,
          layoutPlan,
        });
        await ctx.shapesStore.add(shape);
        return {
          operationId: ctx.meta.nextOperationId(),
          transactionId: ctx.meta.currentTransactionId(),
          shapeId: shape.id,
        };
      });

      return { ok: true, meta };
    }

与可选门面壳的关系

层级 职责 说明
可选门面壳 对外统一入口 负责命令分发、事务边界、统一事件出口和对外接口稳定
命令 执行单个意图 负责把一个用户动作完整执行完，内部可以调用多个领域服务
领域服务 承载规则 负责图类型差异、包含关系、路由、布局等稳定规则
直观理解就是：如果存在门面壳，它只负责对外说“我要做什么”；命令负责“把这件事做完”；领域服务负责“这件事的规则是什么”。

可选门面规范

规则 要求 目的
只做收口 门面壳只负责对外统一入口、命令分发和编排，不写业务规则 避免它膨胀成第二个控制器
不重复命令逻辑 门面壳不应复制命令内部的执行步骤，只负责组合和转发 减少重复与分叉
稳定对外契约 对外 API 尽量保持稳定，内部命令可以调整而不影响调用方 降低前端、协作、回放和外部适配的耦合
薄到可消失 当系统足够简单时，门面壳可以退化甚至移除，不影响命令层工作 避免为了形式而保留一层空壳
如果门面壳开始出现大量 if 分支、规则判断或状态变更，那说明它已经偏离“薄壳”定位，应该继续下沉到命令或领域服务。

async function executeCreateShape(input, ctx) {
  const decision = await ctx.policy.canCreateShape(input);
  if (!decision.allowed) return { ok: false, code: decision.code, message: decision.reason };

  const containmentPlan = input.containerId
    ? await ctx.containmentService.planAfterCreate({
        diagramId: input.diagramId,
        shapeType: input.shapeType,
        containerId: input.containerId,
      })
    : null;
  const layoutPlan = await ctx.regionLayoutService.planAfterCreate({
    diagramId: input.diagramId,
    shapeType: input.shapeType,
    position: input.position,
    containerId: input.containerId ?? null,
  });

  return ctx.transaction.run(async () => {
    const shape = await ctx.shapeService.create({
      ...input,
      containmentPlan,
      layoutPlan,
    });
    await ctx.shapesStore.add(shape);
    await ctx.eventBus.emit('shape:add', shape);
    return {
      ok: true,
      meta: {
        operationId: ctx.meta.nextOperationId(),
        transactionId: ctx.meta.currentTransactionId(),
        shapeId: shape.id,
      },
    };
  });
}
 先判定，再做归属和布局预计算，最后统一写入和广播。

6. 渐进式迁移策略

阶段 目标 验收方式
阶段一 隔离 debug、示例和生产入口 生产构建不引用调试页
阶段二 拆出只读查询、协作适配、阶段编排 调用方行为不变，内部职责更清晰
阶段三 拆出 containment、line、region 领域服务 控制器体积明显下降，单测按服务收敛
阶段四 收敛 hydration、transaction 回放、历史和协作走统一事务路径；是否引入门面壳视需求决定

反模式与暂缓项

阶段 暂缓项 原因
阶段一 不要顺手改协作协议、状态格式或 store 结构 先隔离边界，再改数据形态，避免一次改太多。
阶段二 不要把工具事件负载直接换成领域 DTO 工具层先保持输入输出稳定，内部再逐步转向命令。
阶段三 不要为领域服务额外引入 DI 容器或第二套规则引擎 先把规则收进服务，再考虑是否需要更重的装配方式。

阶段关键用例

阶段 必测用例 通过标准

阶段二 工具切换、拖拽创建、协作消息回放、只读查询 输入形式可以调整，交互结果和回放结果不变。
阶段二 快捷键、滚轮缩放、选中态同步 事件路由拆开后，用户可见行为保持一致。
阶段三 创建图形、移动选中项、删除选中项、设置包含关系 命令能稳定串起领域服务，单测可以直接覆盖结果。
阶段三 连线移动、区域扩展、孤儿重挂 核心规则已沉到底层，控制器不再承接复杂分支。
阶段四 快照恢复、事务记录、协作同步 恢复、历史和协作走统一事务路径，回放结果可对齐。

停止条件

检查项 建议阈值 含义
目录深度 ≤ 3 层 再往下通常只会增加心智负担，不会继续提升边界清晰度。
命令文件数量 ≤ 10 个核心命令 如果继续增长，先检查是否有命令粒度过细的问题。
单文件体积 ≤ 500 行 超过后优先拆分职责，不要再往一个文件里叠规则。
关键路径覆盖 100% 核心用例必须有单测或回归验证，不能只靠人工确认。
只要这四项都稳定，就不再主动增加抽象层。若后续新增抽象不带来边界收敛、测试简化或入口减少，就视为过抽。

反向指标

信号 说明
服务数量继续增长，但职责没有变清楚 说明拆分正在变成搬运，应该回头合并。
命令越来越薄，但调用链越来越长 说明只是把复杂度移到了别处，没有真正收敛。
目录越来越整齐，但修改一个功能需要动很多层 说明物理结构先行了，边界没有同步收紧。
不建议一口气把所有文件按新目录整体搬迁。正确做法是先迁行为边界，再迁物理目录，最后统一导出入口。

控制器拆分顺序

下面这张表描述的是 canvas-controller.ts 从“单体入口”收敛到“命令 + 领域服务”的推荐顺序。原则是先把可独立验证的动作抽出去，再把稳定规则下沉，最后才清理剩余壳代码。

顺序 先抽内容 目标归位 原因
1 addShape、removeShapes、removeLine、updateShape、updateLine application/commands/ 先把用户意图入口收口，控制器不再直接承担操作执行。
2 setParent、setContainmentRelation、refreshFunctionContainment、applyShapeCreationRelations domain/services/containment.service.ts 包含关系和功能图嵌套是稳定规则，适合最先下沉。
3 applyRegionExpansionForShape、applyRegionExpansionBatchUpdates、reparentOrphanedChildren domain/services/region-layout.service.ts 区域扩展和孤儿重挂属于一类规则，应尽快从控制器剥离。
4 syncConnectedLine、syncConnectedLinesForBatchUpdates、syncConnectedLinesForEndpointRebuild、shiftLines domain/services/line-routing.service.ts 连线联动和路由更新逻辑集中度高，抽出后最能降低控制器复杂度。
5 syncSelectionAfterDeletion、hydrateDiagramData、repairSingleRegionBounds domain/services/selection.service.ts、domain/services/hydration.service.ts 这些属于收尾修复和恢复逻辑，等主流程稳定后再集中处理。
6 残余的元数据、事件广播、回放标记 application/transaction/，必要时补 application/facade/ 最后移除控制器，所有生产调用方改由应用层门面、领域服务和基础设施适配协作完成。
如果拆分过程中发现某段逻辑既不像命令也不像领域服务，通常是因为它同时混了“意图编排”和“规则判断”。这时优先拆出规则，再保留最少量编排代码。

utils/ 的拆分原则和控制器不同，它更适合按“领域规则优先、纯转换保留、适配边界独立”来推进。先把带业务语义的工具上提，再保留纯数学、纯转换、纯定位类工具作为最后一层。

2 line-routing.ts、orthogonal-line-model.ts、polyline-line-model.ts、line-scope.ts domain/services/line-routing.service.ts 连线路由相关逻辑聚合度高，拆出来后收益最大。
3 region-constraints.ts、nesting-drag.ts、quick-add-rules.ts、quick-add-preview.ts domain/services/ + ui/tools/ 包含、推挤、快捷加号都属于规则和交互混合区，需要先把规则剥离。

5 overlay-positioning.ts、canvas-cursor.ts、size-scale.ts、constants/shape-style.ts、canvas-visual-config.ts、CanvasVisualNode.vue ui/ 这些主要是视图定位和视觉配置，可在规则收敛后再调整物理位置。
6 konva-node.ts、connection-point-hit.ts、force/、throttle.ts ui/adapters/ 或独立能力模块 这些更偏适配与支撑能力，放到最后处理对主链路影响最小。

7. 重构原则

以下原则用于约束后续所有迁移和新增能力。若与局部实现便利冲突，优先满足原则，再考虑实现成本。
原则 含义 落地要求
单一职责优先 每一层只做自己该做的事，不同时承担规则、适配和展示 Store 不编排，UI 不落规则，Domain 不依赖框架
不过度设计 只为已经存在且明确的复杂度增加抽象，不为未来可能的需求预先堆叠层次 优先复用已有边界；仅有一层转发、没有独立职责或没有稳定复用场景的门面、适配器和服务不新增，重复包装应合并
不过度拆分 文件边界服务于业务职责和依赖隔离，不以函数数量、代码行数或形式上的单一职责为目标 禁止一函数一文件和同一 feature 内的薄模块堆叠；仅在职责独立、稳定复用、可替换依赖或独立测试价值明确时拆文件，其余职责在同一业务文件内组织
用例驱动优先 功能组织方式以用户意图为中心，不以技术动作或文件大小为中心 新增能力先定义用例，再落到服务和适配器
规则下沉优先 稳定且可测试的判断逻辑优先沉入领域层 图类型、连线、区域、嵌套、选择规则优先进入 domain
边界隔离优先 调试、示例、生产、协作、回放边界清晰可分 debug 与生产分离，协作与回放通过适配层接入
渐进迁移优先 先抽壳，再拆分，再改目录，避免一次性大爆炸 保持调用方行为稳定，按阶段完成收敛和验证
显式协议优先 事件、命令、协作载荷和元数据必须显式定义 禁止散落裸字符串和隐式约定，所有协议集中管理

8. 建议的落地顺序

以下计划遵循“先定边界，再拆实现，最后收敛目录”的顺序推进。每个阶段都以行为稳定为前提，避免在结构调整中引入未验证的变化。

阶段 建议周期 重点事项 阶段产出 依赖前置
阶段一 1 周 完成文档落地、目录边界确认、调试页与生产页隔离 共识统一，生产链路更干净 无
阶段二 1 周 收敛查询、协作和阶段编排，先把主入口周边抽薄 只读服务、协作适配、交互编排边界清晰 阶段一完成
阶段三 1 至 2 周 拆出 containment、line、region 三类领域服务，迁移高风险规则 核心规则进入 domain，主入口明显瘦身 阶段二完成
阶段四 1 周 整理 hydration；事务记录和历史回放仅在出现实际需求时建设 恢复边界清晰，后续历史能力可按需接入 阶段三完成
阶段五 满足停止条件后收口 统一目录、文件命名、测试组织和导出入口 目录与边界一致，后续维护成本下降 前四阶段稳定且停止条件达标

  1. 先把查询、协作和阶段编排抽薄。
  2. 再拆关系、连线和区域布局。
  3. 用单测锁住新边界后，再统一目录和命名。

UI / Tool

层级 职责 禁止事项
application command 表达用户意图、权限前置判断、组织一次用例和事务上下文。 不直接操作 store，不实现几何或包含关系规则。
domain service 执行纯规则计算，生成校验结果、变更计划和影响范围。 不依赖 Vue、Pinia、事件总线或协作连接。

阶段四-三收口要求：在进入阶段四-四前，必须完成现有迁移期 adapter 的归并评审，并先完成网关职责拆分。具有独立业务职责的 adapter/command 应归位到对应领域服务；仅负责 store 写入、事件发布或协作接线的基础设施适配器才允许并入薄网关。不得以“迁移方便”为理由把临时 adapter 固化为新的巨型领域边界。

9. 结论

ICCE 现有实现有分层基础，当前重点是把边界继续收紧。方案采用保守迁移、持续收敛的策略，先让系统朝目标架构移动，再逐步替换旧形态。

最终目标是让每一层只做自己该做的事。

预期收益

  • 控制器收敛，新增功能更容易归位。
  • 领域、UI、协作边界更清晰，测试更好组织。
  • 调试与生产隔离后，维护成本下降。

风险提示

  • 阶段切分过粗会放大回归风险。
  • 一次性搬迁目录会让调用方同时适配多个变化点。
  • 领域规则没先沉淀成可测服务，复杂度只会扩散。

验收口径

  • 生产构建不再依赖调试与示例页面。
  • 查询、协作、阶段编排、领域服务和事务边界可清楚描述。
  • 关键迁移点有单测或回归验证。
  • 新功能能自然落入目标目录树。

1. 规则与服务边界

v0.1 把"图类型差异、嵌套限制"放到 domain/rules/，又把 ContainmentService、RegionLayoutService、DiagramPolicyService 放到 domain/services/。两个层级之间没有显式分工，容易出现同一判定在两处重复实现。

domain/rules/ 只放纯判定函数：输入领域对象 + 上下文，输出布尔或枚举，不产生任何变更，不引用服务。 domain/services/ 负责调用规则、拼装结果、组织领域对象之间的协作，必要时为命令层准备"决策对象"或"变更前置清单"。
问题类型 放哪 示例
某图类型是否允许某类节点存在 domain/rules/ canShapeExistInDiagram(diagramType, shapeType)
父子归属是否合法 domain/rules/ canSetContainment(parent, child, diagramType)
区域是否需要扩展、扩展多少 domain/services/region-layout.service.ts 组合多个规则计算扩展量并生成变更前置
归属变更的最终动作清单 domain/services/containment.service.ts 调用规则、合并判定、返回决策对象
一条经验法则：能用一行表达式说完的判定，放 rules；要拉多个对象做组合运算的，放 services。一旦 services 里出现"先判 true 再判 false"的复杂分支，优先把分支拆回 rules。

2. 协作链路硬约束

4. 命令签名规范

v0.1 给出了 CommandResult 形状，但没规定命令函数的签名形态和"命令能否 await 其它命令"。这是异步嵌套下事务边界混乱的根因。

命令统一为异步函数，输入为显式参数对象，返回 Promise<CommandResult>。命令内部不 await 其它命令；复合流程必须由应用层薄编排承接，若后续出现稳定复用，再收口为 facade。 
type CommandContext = {
  // 由 application 注入：事务、recorder、evaluator、当前用户、时钟等
};

type CreateShapeInput = {
  diagramId: string;
  shapeType: string;
  position: { x: number; y: number };
  containerId?: string;
  source?: 'user' | 'collab' | 'replay' | 'import';
  // 标识类字段由 ctx 注入，禁止在命令内自造
};

async function executeCreateShape(
  input: CreateShapeInput,
  ctx: CommandContext,
): Promise<CommandResult> {
  const decision = await ctx.policy.canCreateShape(input);
  if (!decision.allowed) {
    return { ok: false, code: decision.code, message: decision.reason };
  }

  const containmentPlan = input.containerId
    ? await ctx.containmentService.planAfterCreate({
        diagramId: input.diagramId,
        shapeType: input.shapeType,
        containerId: input.containerId,
      })
    : null;
  const layoutPlan = await ctx.regionLayoutService.planAfterCreate({
    diagramId: input.diagramId,
    shapeType: input.shapeType,
    position: input.position,
    containerId: input.containerId ?? null,
  });

  const meta = await ctx.transaction.run(async () => {
    const shape = await ctx.shapeService.create({
      ...input,
      containmentPlan,
      layoutPlan,
    });
    await ctx.shapesStore.add(shape);
    return {
      operationId: ctx.meta.nextOperationId(),
      transactionId: ctx.meta.currentTransactionId(),
      shapeId: shape.id,
    };
  });

  return { ok: true, meta };
}
  • 同步命令不允许存在，避免 facade 编排时被误以为可"立刻拿到结果"。
  • 命令内部禁止 await executeXxxCommand(...)。如果需要组合，先写在应用层薄编排里，后续若形成稳定复用点再收口到 facade。
  • 复合流程在 facade 未出现前，由 application 层的薄编排用例或工作流承接，不允许塞回单个命令内部。
  • 未来改为命令式协作后，再评估是否引入 source 字段区分用户、协作、回放和导入来源；当前协议不添加该字段。
  • 所有 id、timestamp、userId 一律从 ctx 注入，命令内不调用 Date.now()、crypto.randomUUID()、useUser().value 等。
一旦命令开始自造标识或 await 其它命令，事务边界就破了。出现这种情况应当立即调整：标识上提到 ctx，组合下移到应用层薄编排；若复合流程成为稳定复用点，再收口到 facade。

3. 验证用例与命令衔接

应用层新增一个用例 ValidateDiagram，专门承接"对当前图执行一次完整性校验"的意图，与 v0.1 既有的六个用例并列。校验是只读行为；权限判断可以作为应用层前置策略，但不能让规则服务承担路由、界面显隐或状态写入。

type ValidateDiagramInput = {
  diagramId: string;
  diagramType: 'activity' | 'function' | 'flow' | 'logic';
  shapes: ReadonlyArray<Shape>;
  treeNodes: ReadonlyArray<TreeNode>;
  regionIndex?: RegionIndexSnapshot;
  currentUserId?: string | null;
  ruleCodes?: ReadonlyArray<DfdValidationRuleCode>;
};

type ValidationOutcome = {
  passed: boolean;
  ruleCode: DfdValidationRuleCode;
  diagramType: ValidateDiagramInput['diagramType'];
  level: 'error' | 'warning';
  targetType: 'canvas' | 'tree-node' | 'region' | 'shape' | 'line';
  targets: ReadonlyArray<DfdValidationTarget>;
  message: string;
};

type ValidationReport = {
  passed: boolean;
  outcomes: ValidationOutcome[];
};

type ValidateDiagramResult =
  | { ok: true; report: ValidationReport }
  | { ok: false; code: string; message: string };

async function executeValidateDiagram(
  input: ValidateDiagramInput,
  ctx: CommandContext,
): Promise<ValidateDiagramResult> {
  const outcomes = await ctx.validationService.validate({
    diagramType: input.diagramType,
    shapes: input.shapes,
    treeNodes: input.treeNodes,
    regionIndex: input.regionIndex,
    currentUserId: input.currentUserId,
    ruleCodes: input.ruleCodes,
  });

  return {
    ok: true,
    report: {
      passed: outcomes.every((outcome) => outcome.passed),
      outcomes,
    },
  };
}

与协作链路的关系

远端消息落地到本地状态后，若本次变更属于"会影响负责人提交态"的范围，本地命令在完成写入前必须先调用 ValidationService.findOwnersToReset，把被失效的负责人与区域作为命令返回值的一部分交给事务层。这里的服务只计算影响范围，不直接修改提交态；提交态写入由命令和事务层完成。传输适配器仍然不直接调用 ValidationService，只负责把远端载荷交给对应命令。

严禁在 ui/、infrastructure/collab/ 或 debug/ 中直接调用 ValidationService.findOwnersToReset。一旦发现这种调用，必须下沉为命令前置调用，否则事务边界会出现"前置判定落在 UI 侧"的破口。
