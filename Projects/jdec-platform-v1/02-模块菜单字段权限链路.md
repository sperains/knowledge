# jdec-platform-v1 02 模块菜单字段权限链路

> 当前结论：平台将菜单、模块、字段和权限拆成不同的配置对象，通过菜单绑定模块、表头选择字段、角色关联权限，最终由动态数据引擎生成查询或保存计划。本页是基于当前源码、配置中心和 `company` 项目配置的事实梳理，不是新的架构决策。

## 1. 总体关系

```text
项目编号 + 主体编号 + 用户登录上下文
  ↓
用户与角色
  ├─ 菜单权限：角色可以看到哪些菜单
  ├─ 字段权限：字段能否申请、查看、编辑
  ├─ 数据权限：允许访问哪些业务数据范围
  ├─ 交互权限：允许执行哪些业务操作
  └─ 特殊权限：独立的特殊操作能力
        ↓
菜单
  ↓ module_id
模块树
  ↓
模块字段
  ↓
物理表、物理列和表关系
  ↓
菜单表头选择字段
  ↓
动态查询计划或保存计划
```

核心边界可以概括为：

```text
菜单负责“从哪里进入”
模块负责“操作什么业务对象”
字段负责“读写哪些数据列”
权限负责“谁能看到或执行什么”
数据引擎负责“如何根据配置访问业务库”
```

## 2. 模块：业务数据模型

模块配置位于 `sys_module`，模块字段配置位于 `sys_module_field`。

### 模块定义

`sys_module` 主要描述：

- 项目和主体归属；
- 模块编码、名称、层级和排序；
- 业务模块或系统模块分类；
- 父模块；
- 对应的主表 `primary_table`。

模块可以是有物理表的实体模块，也可以是仅用于组织层级的虚拟模块。虚拟模块没有主表，但可以包含有物理表的子模块。

以 `company` 项目为例：

```text
外部对象管理（info）
├─ 基本信息（basic_info）
├─ 人员构成-组织架构（member）
│  └─ 人员构成-个人通讯录（member_contact）
├─ 联系方式（虚拟模块）
│  ├─ 公司地址（address）
│  └─ 公司联系方式（company_contact）
├─ 财务信息（虚拟模块）
│  ├─ 银行卡（financial_account）
│  └─ 电子账户（digital_account）
└─ 信用等级（credit_rating）
```

### 模块字段

`sys_module_field` 将模块字段映射到物理表和物理列：

```text
模块字段编号
  → module_id
  → table_name
  → column_name
  → 展示名称、排序和业务键配置
```

配置中心的模块树接口会同时返回模块、字段及其父子关系。数据引擎使用字段归属校验请求范围，再根据 `sys_table_relation` 解析模块之间的父键和子表外键。

## 3. 菜单：页面入口和导航结构

菜单配置位于 `sys_menu`，主要描述：

- 父子菜单关系；
- 菜单类型和页面结构；
- 是否显示、是否启用；
- 项目和主体归属；
- 页面详情菜单；
- 绑定的模块 `module_id`。

菜单与模块不是同一棵树：

```text
sys_menu.module_id → sys_module.id
```

这个绑定表示菜单进入哪个数据模块，但不代表模块由菜单拥有。一个模块可以被多个菜单引用，菜单层级也可以和模块层级不同。

角色菜单权限通过 `sys_role_menu` 建立：

```text
角色 → sys_role_menu → sys_menu
```

认证和角色切换流程会根据角色菜单映射过滤可用菜单。菜单权限解决的是“是否能进入页面”，不等于已经拥有该页面所有字段的读写权限。

## 4. 字段、表头与实际查询字段

> 字段配置菜单的独立代码梳理见 [[04-字段配置代码梳理|04 字段配置代码梳理]]；本节保留它与菜单表头、字段权限和动态查询之间的关系摘要。

### 全局字段配置和模块字段配置的区别

字段配置页面不是模块字段绑定页面。当前代码需要区分三类字段对象，以及一张字段扩展值表：

- `sys_field`：以项目、主体、物理表和物理列为范围的全局字段配置，维护字段显示名称、关系配置、加密、引用、数据权限标记和组合字段配置；该实体本身没有 `module_id`。
- `sys_module_field`：模块范围内的字段定义，维护字段属于哪个模块、对应哪张表哪一列、显示顺序和业务唯一标识顺序，是动态查询和模块字段权限使用的字段对象。
- `sys_field_value`：字段配置的扩展值，使用 `field_id` 关联 `sys_field`，同时保存 `module_id`、字段值和 `approval_chain_type_id`，用于表达某个字段值在某个模块下关联哪类审批链。

因此，字段配置和模块关联是间接关系：

```text
物理表 + 物理列
  ↓
sys_field：字段公共属性
  ├─ sys_field_value：模块级字段值和审批链扩展配置
  └─ sys_module_field：模块实际使用该字段的关系
```

`sys_field` 和 `sys_module_field` 不是同一层配置，也没有直接的模块外键。`SysFieldService` 查询字段列表时，会按表名读取 `sys_module_field`，再按列名把字段映射到使用它的模块，组装到 `SysFieldResp.modules` 中。这是代码层的表名/列名语义关联，不是数据库声明的外键。

### 字段配置页面的实际内容

截图中的列表首先从项目业务库的 `INFORMATION_SCHEMA.COLUMNS` 获取物理表和列，再合并 `sys_field` 中已有的配置。编辑弹窗主要对应：

| 页面项 | 代码字段 | 作用 |
|---|---|---|
| 字段显示名称 | `sys_field.display_name` | 覆盖数据库列注释，作为前端展示名称 |
| 关系名称 | `relation_business_no`、`relation_name` | 绑定外部关系词或业务关系 |
| 字段存储是否加密 | `encrypted` | 标记字段存储是否加密 |
| 是否生成数据权限节点 | `data_right_flag` | 变更为启用时生成 `表名*列名` 数据权限节点 |
| 是否来自其他业务数据引用 | `refer` | 当前代码注释为“是否引用”，页面文案与代码命名仍需运行时确认 |
| 是否组合字段 | `combine_info` 是否为空 | 保存字段来源映射和转换方法 |
| 字段值关联审批链 | `sys_field_value` | 按模块和字段值关联审批链分类 |

保存 `sys_field` 时，`SysFieldService` 会同步处理字段扩展值、数据权限节点、外部关系绑定和字段审计日志；不会直接修改 `sys_module_field` 的模块字段归属。

### 菜单表头

`sys_menu_header` 负责把菜单展示和模块字段连接起来：

```text
菜单
  → 菜单表头节点
  → 模块字段编号
  → QueryReq.fieldIds
  → 动态查询计划
```

表头节点可以表示菜单节点，也可以表示字段节点；字段节点包含模块、字段、列名、显示名称、排序、搜索和选中状态等信息。

用户可以保存个人表头配置，业务库中的 `user_menu_header` 通过用户编号、菜单编号、模块编号和项目编号与配置中心对象建立逻辑关联。

因此，菜单聚合查询的实际流程是：

```text
菜单编号
  → 获取默认表头或用户个性化表头
  → 提取选中的模块字段编号
  → 组装 QueryReq
  → 校验字段是否属于模块树
  → 编译并执行查询计划
```

## 5. 权限分类

| 权限类型 | 主要配置 | 作用 | 当前理解 |
|---|---|---|---|
| 菜单权限 | `sys_role_menu` | 控制角色可见和可进入的菜单 | 已参与认证和菜单树过滤 |
| 字段权限 | `sys_role_module_field_permission` | 控制模块字段的申请、查看、编辑 | 以字段编号和角色为维度配置 |
| 数据权限 | `sys_data_permission`、`sys_role_data_permission` | 控制业务数据范围 | 权限类型使用 `表名*列名` 形式关联业务值 |
| 交互权限 | `sys_interaction_permission`、`sys_role_interaction_permission` | 控制申请、编辑、查看等操作类别 | 与模块和交互类型关联 |
| 特殊权限 | `sys_special_permission`、`sys_role_special_permission` | 控制独立的特殊能力 | 独立于普通菜单和字段权限 |
| 审批权限 | 审批链配置及运行时表 | 控制提交、审批人、审批按钮和状态流转 | 属于业务流程权限，不等同于菜单权限 |

字段权限通常包含三个位：

```text
apply：允许申请或创建
view：允许查看
edit：允许编辑
```

配置中心的模块权限接口会读取角色、模块和字段权限，并将字段权限汇总为模块级的申请、查看、编辑状态。

## 6. 两条主要运行链路

### 6.1 菜单聚合查询

```text
用户请求菜单数据
  → 读取用户默认或个性化表头
  → 生成字段编号列表
  → 调用动态数据查询接口
  → 根据模块树和表关系编译查询计划
  → 读取项目业务库
  → 组装父子模块数据
  → 返回表头、权限摘要、审批按钮和数据
```

这条链路面向页面展示，除了数据本身，还会返回前端需要的模块权限摘要和审批按钮信息。

### 6.2 直接数据引擎查询或保存

```text
直接调用数据引擎
  → DataController
  → DataService
  → DataQueryService 或 DataPersistenceService
  → QueryPlanCompiler 或 SavePlanCompiler
  → 访问项目业务库
```

当前源码中，查询编译器明确校验字段是否属于根模块及其子树，并解析模块关系；但在这条直接数据引擎链路中，尚未看到统一传入 `roleId` 并强制执行角色字段权限和数据权限的代码。这个结论属于静态源码观察，仍需通过真实接口和不同角色进行运行时验证。

## 7. 当前已确认的边界与待核验项

### 已确认

1. 菜单权限和模块字段权限由不同配置关系维护，不能用菜单权限替代字段权限。
2. 菜单通过 `module_id` 绑定数据模块，菜单树和模块树可以不同。
3. 菜单表头是页面展示字段进入动态查询请求的桥梁。
4. 模块查询和保存依赖模块字段、模块树和表关系配置，不直接依赖数据库物理外键。
5. `company` 项目的虚拟模块只负责组织层级，查询计划会继续向下寻找实际物理表。
6. 字段配置页面以物理表和物理列为查询范围，字段公共属性保存在 `sys_field`，不要求在主字段实体中选择模块。
7. 模块字段关系保存在 `sys_module_field`；字段服务通过表名和列名查询模块使用情况，并将结果组装到字段响应中。
8. 字段值与模块、审批链分类的关联保存在 `sys_field_value`，它是字段配置的扩展关系，不等同于 `sys_module_field`。

### 待核验

1. 字段配置页面是否展示 `SysFieldResp.modules` 返回的模块列表，以及“是否引用”在前端实际对应“脱敏”还是“来自其他业务数据引用”。
2. 直接查询、详情和保存接口是否由其他拦截器、网关或调用方补充角色字段权限和数据权限。
3. 菜单表头的角色过滤：默认表头服务中的角色过滤开关当前关闭，用户个性化表头的角色过滤代码当前被注释。
4. 模块写权限判断中 `apply` 与 `edit` 的业务语义是否有意区分。
5. 数据权限在动态查询条件中的完整注入位置，以及不同主体和角色切换场景的实际效果。

- 菜单及表头：`SysMenuService`、`SysMenuHeaderService`、`UserMenuHeaderService`。

- 动态保存：`SavePlanCompiler`、`SavePlanExecutor`、`DataPersistenceService`。
