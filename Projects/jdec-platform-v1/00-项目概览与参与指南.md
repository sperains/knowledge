# jdec-platform-v1 00 项目概览与参与指南

> 当前结论：这是一个基于 Spring Modulith 的模块化单体平台。项目的核心不是普通后台增删改查，而是“配置中心维护元数据，数据引擎根据元数据动态生成查询和保存计划”。本文是参与开发的代码事实参考，不是架构决策记录。

## 1. 项目定位

平台通过项目编号和主体编号确定请求上下文，再根据配置中心中的模块、字段、表关系和权限元数据访问不同项目业务库。

主要技术基线包括：

- Spring Boot 3.2.5、Spring Modulith。
- Java 21 编译目标。
- MyBatis-Plus 负责部分固定表访问。
- jOOQ 负责动态查询和动态保存。
- JWT、Redis 和线程上下文负责登录态及请求身份。
- MySQL、Redis、动态数据源和缓存组成运行时基础设施。

核心组合关系如下：

```text
HTTP 请求
  → JWT 与项目/主体上下文
  → 配置中心读取模块、字段、表关系和权限
  → 数据引擎编译查询或保存计划
  → 动态切换项目业务数据源
  → 菜单聚合、审批和监控日志等业务能力
```

## 2. 模块职责

| 模块 | 职责 |
|---|---|
| `jdec-platform-shared` | JWT、请求上下文、动态数据源、统一响应、异常、缓存、Redis 和外部服务 |
| `auth-api / auth-biz` | 登录、登出、当前用户、权限检查和角色切换 |
| `config-api / config-biz` | 配置中心、模块、字段、菜单、角色、权限、表关系和审批配置 |
| `hr-api / hr-biz` | 用户、部门、主体和组织等人事基础数据 |
| `common-api / common-biz` | 通用用户树、学生及外部文档能力 |
| `data-api / data-biz` | 动态查询、动态保存、菜单聚合、用户表头和监控日志 |
| `approval-api / approval-biz` | 审批列表、审批节点、提交、通过、驳回和审批事件 |
| `jdec-platform-app` | Spring Boot 启动模块，组装全部业务模块 |

根模块和子模块定义见源码仓库的 `pom.xml`；应用入口为 `jdec-platform-app/src/main/java/com/jdec/platform/PlatformApplication.java`。

## 3. 请求上下文和数据源

请求通常经过 `WebMvcConfig` 注册的 JWT 拦截器和项目上下文拦截器：

- `Authorization: Bearer ...`：恢复登录用户。
- `X-Project-No`：确定当前项目和业务数据源。
- `X-Subject-Id`：确定当前主体或组织范围。
- 角色、模拟用户等信息：由 JWT 和请求头共同提供。

上下文分别由 `UserContext`、`AppContext` 和 `DataSourceContextHolder` 保存。数据源解析主要经过 `DataSourceAspect` 和 `DataSourceResolver`。

当前可见的数据源边界包括配置中心库、人事库和项目业务库。配置中心服务通常访问 `config_center`，HR 服务访问人事库，动态数据引擎根据项目上下文访问业务库。

这里有一个重要约束：跨数据源调用不能随意增加外层事务。事务一旦先绑定默认数据源，内部的动态切库可能无法达到预期；部分跨库读取服务因此使用非事务传播。修改相关代码前必须先确认数据源切换和事务建立的先后顺序。

## 4. 配置中心与数据引擎

### 配置中心

配置中心维护平台运行所需的元数据，包括：

- 模块树和模块字段。
- 物理表、物理字段和表关系。
- 菜单、菜单表头和按钮。
- 角色、用户、字段权限和数据权限。
- 审批配置、搜索配置和特殊权限。

`ConfigApi` 对外提供模块树、项目表关系、模块权限和缓存清理等能力。`ConfigServiceImpl` 负责从配置库读取这些信息，并通过缓存和 Redis 配置变更消息降低重复读取。

初始化入口和 `init/*.json` 属于种子数据能力，不能在不了解目标项目和主体的情况下随意调用。

### 查询链路

数据模块的查询入口位于 `DataController`，主要链路为：

```text
DataQueryService
  → QueryPlanCompiler
  → QueryPlanExecutor
  → TreeResultAssembler
```

查询计划会完成字段归属校验、模块树展开、表关系解析、筛选和排序、分页、子模块筛选以及批量加载。最终结果会组装为前端需要的父子树形结构，以避免逐条查询造成的 N+1 问题。

### 保存链路

保存链路通过保存计划编译器和执行器递归处理父子数据：

- 根据模块和表关系生成保存计划。
- 自动传递父子外键。
- 补充主体、创建人、更新时间和删除标记等平台字段。
- 在一个动态数据源事务中执行批量新增或更新。
- 返回与输入数据形状对应的标识结果。

数据引擎相关测试重点覆盖嵌套一对多查询、筛选条件下推、作用域校验和父子保存。

### Company 业务库核验

2026-09-22 已使用开发配置建立只读连接，对 `company` 业务库和配置中心中的 `company` 元数据进行了交叉核对，未执行写入、修改或删除操作。

配置中心中的公司模块树与物理表关系如下：

```text
1001 外部对象管理 → info
├── 1002 基本信息 → basic_info              1:1
├── 1003 组织架构 → member                  1:N
│   └── 1004 个人通讯录 → member_contact    1:N
├── 1020 联系方式                               虚拟模块
│   ├── 1005 公司地址 → address              1:1
│   └── 1006 公司联系方式 → company_contact  1:N
├── 1007 财务信息                               虚拟模块
│   ├── 1008 银行卡 → financial_account       1:N
│   └── 1009 电子账户 → digital_account       1:N
└── 1010 信用等级 → credit_rating             1:1
```

当前 `company` 业务库共有 20 张表。核心主数据表的记录规模为：`info` 15 条、`basic_info` 14 条、`member` 72 条、`member_contact` 37 条、`address` 9 条、`company_contact` 8 条、`financial_account` 8 条、`digital_account` 8 条、`credit_rating` 4 条；此外还包含审批、模块变更、监控日志和用户表头等平台表。

数据库没有声明物理外键，关系由配置中心的 `sys_table_relation` 和业务字段、索引共同维护。一对一关系通过 `company_id` 唯一索引体现，一对多关系通过 `company_id` 或 `member_id` 普通索引体现。`info.parent_id` 表示公司父级关系，`member.parent_id` 表示组织人员树，`member.leader_id` 表示部门负责人。

全部 20 张 company 表的关系图、关系证据和逻辑关联边界见 [[05-company业务库全表关系图|05 company 业务库全表关系图]]。

代码与数据库的查询链路已经对齐：`QueryPlanCompiler` 根据字段归属重建模块树，通过 `sys_table_relation` 严格解析父键和子表外键；`QueryPlanExecutor` 先分页读取 `info`，再按主键集合批量读取 `member` 和 `member_contact`，最后由 `TreeResultAssembler` 在内存中按外键装配，虚拟模块则透传父级主键。

只读完整性统计未发现 `company_id` 或 `member_id` 关联的孤儿记录；但发现 5 条 `info.parent_id` 和 14 条 `member.parent_id` 找不到父记录。由于数据库没有外键，这些结果暂记为待核验的数据质量问题，不能直接判定为业务错误。

## 5. 菜单、权限和审批

数据聚合层会在数据引擎结果上继续叠加菜单表头、用户自定义表头、权限摘要和审批按钮。

审批模块通过审批事件驱动提交、编辑、通过、驳回和撤销等后续处理，部分处理在事务提交后执行。

参与权限相关开发时，不能只看控制器。应完整追踪：

```text
请求头
  → UserContext
  → ConfigApi
  → 权限摘要
  → QueryPlanCompiler
  → 最终查询条件或返回字段
```

当前代码表现出两个需要重点确认的边界：

1. 直接数据引擎查询明确校验模块树和字段归属，但角色字段权限是否在所有查询路径中完整生效，需要结合真实接口继续验证。
2. 用户菜单表头服务中的角色权限过滤仍有暂时注释，不能默认已完成角色级过滤。

以上属于待核验风险，不应直接表述为已确认的安全缺陷。

### 审批链详细核验

2026-09-22 已对审批代码、配置中心和 `company` 业务库进行了只读交叉核对。审批链可以分为四层：

```text
配置中心审批模板
  → company 运行时审批步骤
  → 当前业务审批状态与版本记录
  → 实际业务表记录
```

配置中心的审批模板主要由 `sys_approval_chain_config`、审批按钮配置和状态节点组成。当前 `company` 配置只有一条信息模块（模块 `1001`）审批模板：第 1 步使用角色组中任意一人审批的规则，配置通过和驳回按钮，当前状态节点为 `3`，下一状态节点为 `4`，下一步骤编号为 `2`。

单据创建时，审批引擎会把配置复制为业务库中的运行时快照：

- `approval_business`：当前业务审批指针，记录模块、业务记录、版本、步骤、状态、审批角色和审批人。
- `approval_chain`：当前单据的审批步骤实例，记录规则、前后步骤、状态转换、审批人和审批结果。
- `approval_chain_button`：当前步骤可执行的通过、驳回等操作。
- `approval_chain_status`：当前步骤的状态节点和下一状态节点。
- `approval_version_record`：审批版本历史、来源版本和驳回原因。

这些表与真实业务表之间没有数据库外键，主要通过 `module_id + record_id`、业务编号、流水编号、版本号和步骤号进行逻辑关联。审批配置是模板，运行时审批表是单据创建时的审批快照，已有单据不会直接跟随最新模板改变。

当前 `company` 数据库中存在一条信息模块审批实例：业务记录为 `100`，第 1 版、第 1 步，当前状态为“等待信息审批”，状态值为 `2`，审批规则为角色组中任意一人审批，尚未指定具体审批人；当前运行时步骤绑定通过和驳回两个按钮，下一状态为“启用”，状态值为 `99`。数据库中暂时只有一个实际运行时步骤，因此当前实例可还原为：

```text
提交
  → 信息审批
      ├─ 通过 → 启用
      └─ 驳回 → 返回可编辑或重新提交状态
```

上述通过后的状态切换是根据当前配置和代码路径推导出的结果，尚未通过真实接口执行通过或驳回操作验证。

审批事件由 `ApprovalEvent` 表达，当前支持创建、提交、编辑、变更、通过、驳回和撤销。`ApprovalEngineImpl` 在事务提交后分发事件：创建进入初始化审批链逻辑，提交或编辑进入版本和流水处理逻辑，通过进入下一步骤或下一状态，驳回回退到起始或指定步骤，撤销则取消当前版本或恢复来源版本。当前检索到的显式事件入口为 `POST /api/data/approval/ApprovalEvent`，控制器将其标记为测试审批事件；生产业务模块是否在真实保存、提交和修改流程中统一发布事件，仍需继续追踪。

主要状态流转如下：

- 通过：校验角色后记录审批人；存在下一步骤时进入下一步骤，不存在下一步骤时切换到当前步骤配置的下一状态。
- 第一步驳回：将当前步骤设为 `0`，切换到状态值 `1`，等待申请人重新提交。
- 中间步骤驳回：按上一审批步骤或指定步骤回退，并清理受影响步骤的审批结果和审批人。
- 撤销：初始版本进入状态值 `-99`；后续版本根据 `source_id` 恢复到来源版本。

当前仍需保留为待核验事项：

1. 会签百分比规则的实现使用整数除法，`percent_of_group` 需要通过专项测试确认实际比例判断是否正确；当前 company 样本使用“一人审批”，未触发该路径。
2. `ApprovalEvent` 同时包含当前用户和申请人字段，但通过审批路径主要使用申请人字段记录实际审批人，需要确认所有调用方的字段传值约定。
3. 代码中存在映射 `approval_action_log` 的操作日志实体，但当前 company 数据库表清单未发现对应表，需要确认它是遗留实体、其他数据库表还是未完成初始化。
4. 审批列表部分主体过滤条件仍处于注释状态，需要结合真实权限链路确认数据隔离是否由其他层保证。

审批链本轮仅完成静态代码和数据库只读核验，没有执行真实审批操作，也没有修改源码或数据库。

## 6. 工程基线与文档差异

截至 `feature/base @ de58bf68`：

- 项目编译目标是 Java 21，但当前本机运行环境是 Java 25，正式开发前应先对齐 Java 21。
- `mvnw` 当前没有执行权限，直接使用 `./mvnw` 会失败；使用 `bash mvnw` 可以启动 Maven。
- Maven 初始化阶段会设置 Git hooks 路径，执行构建前应确认这类工作区副作用。
- README 中仍保留 Sa-Token、SSO 和旧接口路径等历史描述，当前认证实现实际是 JWT、Redis 和线程上下文。
- README、Docker 配置和部署脚本的端口配置存在差异，需要以部署环境实际约定为准。
- 开发和测试配置中包含内网地址以及默认凭据或密钥，不能把这些内容带入文档、日志或提交；后续应优先使用环境变量或密钥管理。

本次已完成静态代码、工程文件以及配置中心和 `company` 业务库的只读结构核验；尚未执行完整构建、应用端到端接口、浏览器联调和权限运行时验证，因此这些验证项仍处于待核验状态。
