# jdec-platform-v1 01 系统设置模块代码熟悉规划

> 规划范围：根据系统设置页面截图和当前后端源码，逐个熟悉状态配置、模块配置、字段配置、权限节点、菜单、人员、角色、角色权限、消息、按钮、通用配置和审批链配置。
>
> 当前基线：`feature/base @ de58bf68`。本页是代码阅读和核验计划，不代表所有运行时行为已经验证。

## 1. 先建立整体心智模型

系统设置不是 12 个互相独立的后台页面，而是围绕“配置中心驱动业务数据和业务流程”组成的一条链：

```text
项目 + 主体 + 请求上下文
  ↓
模块与物理数据模型
  ├─ 模块树
  ├─ 表关系
  ├─ 字段配置
  └─ 状态配置
        ↓
页面组织
  ├─ 菜单
  ├─ 菜单表头
  ├─ 按钮
  └─ 通用配置
        ↓
身份与权限
  ├─ 人员
  ├─ 角色
  ├─ 权限节点
  └─ 角色权限分配
        ↓
业务流程
  ├─ 审批链
  └─ 消息模板与通知记录
        ↓
动态查询、保存、审批和通知运行时
```

最重要的依赖关系是：

```text
项目/主体
  → 模块
  → 字段、状态、表关系
  → 菜单和页面展示
  → 用户、角色和权限分配
  → 审批链、按钮和消息
  → 业务数据运行时
```

截图中的页面顺序是产品导航顺序，后续代码熟悉顺序按上述依赖关系安排。

## 2. 截图模块与源码初步映射

| 页面模块 | 后端入口 | 主要配置对象或表 | 在系统中的作用 |
|---|---|---|---|
| 状态配置 | `SysStatusController`、`SysStatusService` | `SysStatus`、`SysModuleStatus`；`sys_status`、`sys_module_status` | 定义状态树，并把状态绑定到具体模块 |
| 模块配置 | `SysModuleController`、`SysModuleService` | `SysModule`、`SysModuleField`；`sys_module`、`sys_module_field` | 定义业务模块、层级、主表和模块字段 |
| 字段配置 | `SysFieldController`、`SysFieldService` | `SysField`、`SysFieldValue`；`sys_field`、`sys_field_value` | 读取业务库表列元数据，维护字段展示、关联和数据权限标记 |
| 权限节点配置 | `SysRightController`、`SysRightService`；三类权限各自的控制器和服务 | 列表合并读取 `sys_data_permission`、`sys_interaction_permission`、`sys_special_permission`；另有旧的 `sys_right` 路径 | 汇总展示数据、交互和其它权限定义；角色授权由独立关系表维护，详见 [[06-权限节点配置功能梳理]] |
| 菜单管理 | `SysMenuController`、`SysMenuService` | `SysMenu`、`SysMenuHeader`；`sys_menu`、`sys_menu_header` | 维护导航树、页面入口、模块绑定和表头节点 |
| 人员管理 | `SysUserController`、`SysUserService` | `SysUser`；`sys_user`，并关联主体和组织服务 | 维护可被分配角色的人员及其状态、主体范围 |
| 角色配置 | `SysRoleController`、`SysRoleService` | `SysRole`、`SysRoleUser`、`SysRoleSubject`；角色及其人员/主体关系表 | 定义角色，并维护角色成员、主体范围和有效期 |
| 角色权限分配 | `SysRolePermissionController`、`SysRolePermissionService` | `sys_role_menu`、`sys_role_module_field_permission`、`sys_role_data_permission`、`sys_role_interaction_permission`、`sys_role_special_permission` | 将菜单、字段、数据、交互和特殊权限分配给角色 |
| 消息配置 | `SysWechatTemplateController`、`SysWechatTemplateService` | `SysWechatTemplate`、`SysWechatTemplateParam`、`SysMessageRecord` | 配置企业微信消息模板、模板参数并记录发送结果 |
| 按钮配置 | `SysButtonController`、`SysButtonService` | `SysButton`；`sys_button` | 定义按钮名称、别名、类型、样式、显示和启用状态 |
| 通用配置 | `SysConfigCategoryController`、`SysConfigCategoryService` | `SysConfigCategory`、`SysConfigItem`；`sys_config_category`、`sys_config_item` | 提供列表、树、键值等通用选项，供其他配置和业务运行时引用 |
| 审批链配置 | `SysApprovalConfigController`、`SysApprovalChainConfigService` | 审批链类型、步骤、按钮关联；`sys_approval_chain_*` | 按模块定义审批步骤、审批规则、状态流转、按钮和消息模板 |

### 支撑模块

以下模块虽然不一定在截图中单独出现，但阅读时不能跳过：

- `SysProjectSubjectController`：项目与主体范围，是所有配置隔离的基础。
- `SysTableRelationController`：维护物理表之间的关联关系，直接影响动态查询和保存。
- `SysMenuHeaderController`：维护菜单表头和字段展示树。
- `SysModuleFieldPermissionController`：提供模块、表和字段的权限展示树。
- `SysInteractionPermissionController`、`SysDataPermissionController`、`SysSpecialPermissionController`：分别维护不同权限类型的定义。
- `SysSearchConfigController`：维护下拉和搜索条件配置，属于字段和页面查询的辅助能力。

## 3. 推荐学习顺序

### 第 0 阶段：公共上下文和配置基座

先回答“配置属于谁、请求如何找到配置”的问题：

1. `AppContext`、`UserContext` 和 `AppContextInterceptor` 如何提供项目编号、主体编号、用户和角色。
2. `config-api` 与 `config-biz` 如何分离接口契约、请求响应对象和业务实现。
3. MyBatis-Plus 实体、逻辑删除、审计字段和事务边界如何统一处理。
4. 配置变更消息、缓存清理和审计日志如何贯穿各个配置服务。

重点产出：画出“请求上下文 → 配置库 → 业务库”的公共调用链。

### 第 1 阶段：模块、表关系、状态和字段

这是动态数据引擎的基础，建议按以下顺序：

#### 1. 模块配置

阅读入口：

- `jdec-platform-config-biz/.../controller/SysModuleController.java`
- `jdec-platform-config-biz/.../service/SysModuleService.java`
- `jdec-platform-config-biz/.../entity/SysModule.java`
- `jdec-platform-config-biz/.../entity/SysModuleField.java`
- `jdec-platform-config-api/.../dto/request/SaveModuleReq.java`

重点理解：

- 模块树、父子模块和虚拟模块；
- `primary_table` 如何确定模块主表；
- 完整保存为何同时处理模块、关联表、字段和状态；
- 删除模块前的引用检查；
- 模块变更后的缓存失效和消息广播；

#### 2. 表关系配置

重点理解：

#### 3. 状态配置

- `SysStatusController`、`SysStatusService`

重点理解：

- `sys_status` 的状态树和主状态/子状态；
- `sys_module_status` 如何把状态绑定到模块；
- 状态值、启用状态、审批显示标记和排序；
- 状态配置如何被审批链和业务记录使用。

#### 4. 字段配置

阅读入口：

- `SysFieldController`、`SysFieldService`
- `SysField`、`SysFieldValue`

重点理解：

- 数据库表列元数据从哪个数据源读取；
- 物理字段配置与模块字段配置的区别；
- 字段显示名称、引用关系、组合字段和数据权限标记；
- 字段如何进入菜单表头、查询条件和动态查询计划；

阶段产出：完成一张“模块 → 模块字段 → 物理表列 → 菜单表头 → 查询字段编号”的链路图。

## 4. 每个模块统一采用的阅读方法

后续每次只深入一个页面模块，固定按以下顺序：

```text
页面操作
  → Controller 路由
  → API 接口和 DTO
  → Service 事务与校验
  → Entity / Mapper / 数据表
  → 引用检查、缓存和审计
  → 事件或消息通知
  → 下游运行时调用方
  → 数据库实际配置核验
  → 测试和待核验项
```

每个模块最终形成一页笔记，至少包含：

1. 页面目标和核心概念；
2. Controller、API、Service、Entity、Mapper 文件入口；
3. 主要接口及请求响应对象；
4. 配置表和关键字段；
5. 与其他设置模块的关系；
6. 保存、删除、拖拽、启停等写操作的副作用；
7. 缓存、审计、事件和消息边界；
8. 已通过数据库或接口确认的事实；
9. 尚未运行时验证的结论。

## 5. 第一轮建议从哪里开始

第一轮建议从“模块配置”开始，顺序如下：

```text
模块配置
  → 表关系
  → 状态配置
  → 字段配置
  → 菜单与表头
  → 角色权限分配
```

原因是模块配置是其他页面的共同上游：状态需要绑定模块，字段需要挂在物理表和模块上，菜单需要绑定模块，字段权限需要引用模块字段，审批链也需要绑定模块。

第一轮先不急着深入人员、消息和审批的全部实现，等模块和权限主链稳定后，再沿着真实的 `company` 模块跑一遍页面查询、详情、保存和审批流程。

## 6. 当前待核验边界

1. 截图是系统设置前端视图，当前代码仓库主要提供后端配置中心和业务能力；前端路由、组件状态和按钮显隐需要继续定位对应前端仓库或通过真实页面联调确认。
2. `sys_field` 与 `sys_module_field` 的完整映射关系需要单独核验，不能仅凭页面名称推断。
3. 角色字段权限、数据权限在直接查询和保存接口中的服务端强制校验仍需真实角色接口验证。
4. “消息配置”当前源码主要对应企业微信模板，不宜直接等同于所有站内消息或消息中心能力。
5. “按钮配置”是按钮定义和样式配置，审批按钮的业务可用性还要结合审批链、状态和权限运行时确认。
