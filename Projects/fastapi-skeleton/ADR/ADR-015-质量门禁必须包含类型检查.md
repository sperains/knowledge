# ADR-015 质量门禁必须包含类型检查

- 状态：Accepted
- 日期：2026-08-07
- 作者：WorkBuddy（Python 全栈工程师）
- 相关领域：工程实践 / 代码质量门禁

---

## 背景（Context）

骨架交付后，IDE（Pylance）报出 `@asynccontextmanager` 函数标注 `-> AsyncIterator[T]` 已弃用，应使用 `-> AsyncGenerator[T, None]`。该问题暴露了验证链路缺口：当时的质量门禁只有 ruff（lint/format）与 pytest（运行测试），两者都覆盖不了类型标注规范，导致这类问题在交付时漏出。

约束：

- 门禁必须与 IDE 提示一致，避免「IDE 报错、CI 全绿」的分裂。
- 不能只靠人工看 IDE，需要有命令行可执行、可进 CI 的检查。

## 考虑方案（Options）

### 方案 A：门禁加入 pyright（与 Pylance 同源）

优点：

- pyright 与 VS Code 的 Pylance 共用同一类型推断引擎，IDE 报什么 CI 就查什么，规则一致。
- 命令行可执行、可进 CI、可进 Makefile，支持 `pyproject.toml` 配置。

缺点：

- 类型检查首次接入会暴露存量问题，需要一次性修复。

### 方案 B：仅依赖 IDE（Pylance）提示

优点：

- 零配置。

缺点：

- 不可进 CI，换编辑器/换人即失效，无法形成门禁。

### 方案 C：使用 mypy

优点：

- 老牌成熟，生态大。

缺点：

- 配置与严格度与 Pylance 不一致，容易产生「mypy 通过但 IDE 仍报错」的割裂。

## 决策（Decision）

最终选择：**方案 A：质量门禁加入 pyright**。

> `make check` = ruff check + pyright（src、tests）+ pytest，全绿才算过。
> pyright 配置在 `pyproject.toml` 的 `[tool.pyright]`，standard 模式（含 reportDeprecated）。

原因：

1. 与 Pylance 同源，IDE 与门禁规则天然一致。
2. 首次接入即挖出 11 个真实标注问题，证明覆盖价值。
3. 一次接入、长期受益，可进 CI。

## 后果（Consequences）

### 正面影响

- 捕获三类 ruff/pytest 覆盖不到的问题：
  1. yield 函数（`@asynccontextmanager` / `@pytest_asyncio.fixture`）返回标注应为 `AsyncGenerator[T, None]`；
  2. 路由返回 ORM 对象但函数标注为 Schema，要求显式 `UserRead.model_validate(orm)`；
  3. `model_fields_set` 判断分支内可选字段仍为 `Optional`，需要 `assert x is not None` 收窄。
- 交付质量基线从「能跑」提升到「类型精确」。

### 负面影响

- 类型检查首次接入需要一次性修复存量问题（本项目为 11 个）。
- 增加一次门禁执行耗时（秒级，可接受）。

### 后续约束

以后需要遵守：

- 所有 `@asynccontextmanager`、async fixture 等 yield 函数，返回标注一律使用 `AsyncGenerator[YieldType, SendType]`。
- 任何改动必须通过 `make check`（lint + types + test）才能视为完成。
- 新项目脚手架默认包含 pyright 配置与门禁，不省略。

## AI 指导原则

实现相关功能时：

- 必须：yield 函数（asynccontextmanager / async fixture / 依赖生成器）标注 `AsyncGenerator[T, None]`，禁止使用 `AsyncIterator[T]`。
- 必须：修改代码后运行 `make check`（ruff + pyright + pytest）全绿才算完成。
- 必须：`model_fields_set` 分支内对可选字段加 `assert x is not None` 以完成类型收窄。
- 禁止：交付前只跑 ruff + pytest 而不跑类型检查。
