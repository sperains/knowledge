# 简易低代码项目技术选型与目录设计

> 本文是技术背景和详细设计说明，正式架构决策见 [[ADR/ADR-013-采用前后端分离的最小单体架构]]。

## 适用范围

本文适用于个人或小团队开发的简易低代码项目，目标是快速验证可视化编辑、页面配置和页面预览能力，不提前覆盖复杂企业级场景。

## 设计目标

- 优先保证开发效率和功能可验证性。
- 控制技术数量，减少基础设施维护成本。
- 保留清晰的升级路径，但不为暂时不存在的复杂场景预留过多抽象。
- 将页面编辑器和页面运行时建立在同一套组件配置之上。

## 推荐技术栈

```text
前端：Vue 3 + TypeScript + Vite
界面组件：Arco Design Vue
状态管理：Pinia
后端：FastAPI
数据模型：Pydantic
数据访问：SQLModel
数据库：SQLite
部署：开发阶段直接运行，后续按需引入 Docker
```

前后端采用不同语言并不影响当前方案：前端负责可视化编辑和页面渲染，后端负责页面配置的保存与读取，两者通过 HTTP 和 JSON 交互。

## 界面组件库选择

项目采用 Arco Design Vue 作为基础界面组件库。选择原因是组件风格相对现代，企业后台常用组件较完整，适合作为低代码编辑器的基础组件来源。

低代码系统不直接把 Arco Design Vue 的全部属性暴露给使用者，而是在组件库之上增加一层自定义组件元数据：

```text
低代码组件
    ↓
自定义组件适配层
    ↓
Arco Design Vue
```

页面配置保存项目自己的属性名称和数据结构，例如使用 `variant`、`size`、`text` 等稳定字段，而不是直接依赖组件库的全部原始属性。这样未来更换组件库时，可以只调整适配层。

组件元数据至少应描述：

- 组件类型和显示名称。
- 可配置属性及其编辑器类型。
- 属性默认值。
- 可触发事件。
- 组件是否允许包含子组件。
- 组件在编辑态和预览态下的渲染方式。

## 最小系统架构

```text
Vue 编辑器
    │
    │ HTTP / JSON
    ▼
FastAPI 单体应用
    │
    ▼
SQLite
```

第一阶段只需要实现页面的创建、读取、更新和删除，以及页面预览。暂时不拆分服务，不引入独立网关、缓存、消息队列或异步任务系统。

## 页面配置模型

页面可以使用一条记录保存完整配置：

```text
pages
├── id
├── name
├── schema_json
├── created_at
└── updated_at
```

`schema_json` 保存组件树、组件属性和组件样式：

```json
{
  "components": [
    {
      "id": "text-1",
      "type": "text",
      "props": {
        "text": "欢迎使用"
      },
      "style": {
        "left": 40,
        "top": 30
      },
      "children": []
    }
  ]
}
```

第一版建议使用绝对定位保存组件位置和大小，不急于实现复杂网格、响应式布局或自由画布引擎。

## 推荐目录

```text
lowcode/
├── apps/
│   ├── web/                    # 可视化编辑器和页面预览
│   │   ├── src/
│   │   │   ├── app/            # 应用初始化、路由和全局配置
│   │   │   ├── pages/          # 页面级视图
│   │   │   ├── features/       # 编辑器、预览等业务功能
│   │   │   │   └── editor/
│   │   │   │       ├── components/
│   │   │   │       ├── stores/
│   │   │   │       ├── models/
│   │   │   │       └── utils/
│   │   │   ├── components/     # 通用组件
│   │   │   ├── services/       # 接口请求
│   │   │   ├── styles/
│   │   │   └── main.ts
│   │   └── package.json
│   └── api/                    # FastAPI 应用
│       ├── app/
│       │   ├── main.py
│       │   ├── config.py
│       │   ├── db/
│       │   │   ├── database.py
│       │   │   └── session.py
│       │   ├── models/         # 数据库模型
│       │   ├── schemas/        # 请求和响应模型
│       │   ├── api/
│       │   │   └── routes/
│       │   │       └── pages.py
│       │   └── services/       # 业务逻辑
│       └── pyproject.toml
├── docs/                       # 项目设计说明和接口文档
├── scripts/                    # 初始化和构建脚本

├── .env.example
├── .gitignore
└── README.md
```

使用 `apps/web` 和 `apps/api` 表示两个可运行应用，既比 `frontend` 和 `backend` 更明确，也为将来增加管理端、运行时或其他应用保留空间。

## FastAPI 内部组织原则

早期采用简单分层：

```text
app/
├── main.py
├── db/
├── models/
├── schemas/
├── api/routes/
└── services/
```

只有在页面、数据源、组件或用户等业务模块明显增多后，再调整为按业务模块组织：

```text
app/
└── modules/
    └── pages/
        ├── router.py
        ├── model.py
        ├── schema.py
        └── service.py
```

不提前增加领域层、仓储层或复杂依赖注入结构。

## 第一阶段接口

```text
GET    /api/pages
POST   /api/pages
GET    /api/pages/{id}
PUT    /api/pages/{id}
```

用户系统、发布接口和版本管理可以在确实需要时再增加。

## 暂不引入的能力

- 微服务
- Redis
- 消息队列
- 独立认证服务
- 复杂权限体系
- 多租户
- 插件市场
- 文件服务
- 多仓库管理
- 复杂领域层和仓储层

## 演进路径

```text
SQLite
  ↓ 多人使用或数据量增加
PostgreSQL

无用户系统
  ↓ 需要区分使用者
简单登录和基础权限

直接运行
  ↓ 需要稳定部署
Docker Compose

单体应用
  ↓ 出现明确的性能或团队边界
按模块拆分服务
```

演进应由真实需求触发，不以“未来可能需要”为理由提前引入基础设施。

## 不应沉淀到通用知识库的内容

- 当前项目的具体页面名称。
- 临时接口地址和本地文件路径。
- 某个组件的一次性字段设计。
- 只适用于本项目的业务代码。

这些内容应放在项目源码或项目自身的 `docs/` 目录中。

## 核心结论

对于简单低代码项目，应优先采用 Vue 3 + Arco Design Vue + FastAPI + SQLite 的单体架构，以 `apps/web` 和 `apps/api` 组织应用，页面配置使用 JSON 保存，并通过自定义组件元数据层隔离低代码配置与具体组件库，根据真实复杂度逐步演进，而不是提前引入复杂基础设施。
