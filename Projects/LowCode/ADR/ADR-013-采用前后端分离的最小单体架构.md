# ADR-013 采用前后端分离的最小单体架构

- 状态：Accepted
- 日期：2026-08-03
- 作者：LowCode 项目组
- 整理工具：Codex
- 相关领域：技术选型、应用架构、项目目录
- 所属项目：LowCode

## 背景（Context）

当前项目的目标是快速验证低代码页面编辑、配置保存和页面预览能力，不需要一开始覆盖复杂权限、多租户、工作流、消息驱动和高并发场景。架构需要有清晰的前后端边界，同时控制基础设施和维护成本。

## 考虑方案（Options）

1. 前后端合并为一个应用，减少项目数量，但会让界面工程和接口工程边界不清晰。
2. 采用前后端分离的最小单体架构，前端和后端分别开发，通过 HTTP 和 JSON 协作。
3. 从一开始拆分为多个服务，边界更细，但会引入部署、通信、监控和数据一致性成本。

## 决策（Decision）

采用前后端分离的最小单体架构：

- 前端使用 Vue 3、TypeScript、Vite、Pinia 和 Arco Design Vue。
- 后端使用 FastAPI、SQLModel 和 SQLite。
- 代码目录使用 `apps/web` 和 `apps/api`，不使用笼统的前端、后端目录名。
- 前后端通过统一的 HTTP 接口和 `code`、`message`、`data` 响应结构交互，成功状态使用 200。
- 第一阶段不引入微服务、缓存、消息队列和复杂权限体系。

## 后果（Consequences）

正面影响：前后端职责清晰，便于并行开发；单体后端保持简单，适合快速验证核心流程；后续可以在真实边界出现后再拆分。

负面影响：前后端需要维护接口契约和类型同步；SQLite 和单体结构不适合作为长期高并发方案；部署时需要同时管理两个应用。

## AI 指导原则

- 新功能优先放入现有前后端边界，不为了抽象而增加服务数量。
- 前端不得直接访问数据库，所有持久化通过后端接口完成。
- 引入缓存、消息队列、微服务或复杂权限前，必须说明当前业务痛点和收益。
- 当数据规模、团队协作或部署边界发生实质变化时，新增 ADR 评估是否调整架构。
