智能检索体验优化方向

在现有搜索能力之上，增加更符合业务表达的检索入口和条件编排能力，让用户更快找到想要的信息。

01 / CORE JUDGEMENT

不是替代现有搜索，而是让检索更容易开始、更容易完成

现有搜索解决的是“系统能够按哪些条件查”，智能检索要解决的是“用户如何更自然地表达想查什么”。两者的关系是增强，不是替换：传统筛选继续承担确定性查询，智能能力负责理解业务表达、组合条件和降低操作成本。

推荐定位：在既有搜索之上增加一层检索体验

用户可以继续使用熟悉的列筛选，也可以从更自然的入口开始。智能层将用户表达转换为可查看、可修改的条件，确认后仍由原有查询系统执行。

判断标准不以“有没有 AI 入口”作为目标，而以是否减少理解、查找和组合条件的成本作为目标。
02 / CURRENT STATE

以 ICCE 当前列表为例：搜索能力已经存在

当前列表已经具备待办、已办、全部等业务视图，并在列级提供人员、日期等筛选入口。截图中可以看到，人员筛选支持关键词查找、多选和确认；日期筛选支持起止日期、日历选择和确认。这些能力能够准确执行查询，是后续体验增强的基础。

01

按字段逐项筛选

用户可以从 ICCE 编号、项目名称、客户、负责人、申请时间、状态等字段进入筛选。

02

不同字段使用不同控件

人员、日期、文本和其他字段有各自的选择方式，能够满足确定性输入要求。

03

查询结果继续使用原列表

筛选后的数据仍在原表格中呈现，分页、状态和办理入口不需要改变。

现状证据来自当前 ICCE 列表截图及对应页面实现；本方案关注的是已有能力之上的检索体验，而不是重新建设一套搜索系统。

03 / PROBLEM

真正的成本在于“把想法翻译成条件”

当用户只查一个字段时，现有筛选足够直接；当问题变成多个条件的组合，用户需要先理解系统字段，再逐个打开筛选、选择值、确认并观察结果。检索本身没有失效，但完成一次检索的认知和操作成本会变高。

01

业务表达和字段表达有距离

用户想查“最近负责的、还没完成的项目”，需要自己拆解为负责人、时间和状态等字段。

02

多个条件分散在多个入口

每个字段都要单独打开、填写和确认，组合关系主要依靠用户记忆，条件全貌不够直观。

03

试错成本随条件增加

结果为空或过多时，用户需要回到不同筛选入口逐项排查，难以判断应该调整哪个条件。

因此，优化重点不是再堆叠筛选控件，而是帮助用户从业务问题出发，快速得到一组可检查、可调整的检索条件。

04 / DIRECTION

把检索过程从“找控件”变成“表达、确认、执行”

建议建设一个可叠加在现有搜索之上的检索增强层。入口可以是自然语言，也可以是推荐条件、常用查询模板或统一搜索框；无论从哪里开始，最终都要回到结构化条件和原有查询执行链路。

STEP 01

表达检索意图

用业务语言描述目标，也可以继续从列筛选或查询模板开始。

STEP 02

生成检索条件

把表达映射为字段、关系、操作符和值，并标出无法确定的部分。

STEP 03

查看并调整条件

以条件条目展示完整查询，支持删除、修改、补充和回到手工筛选。

STEP 04

沿用现有搜索执行

经确认的条件转换为已有查询参数，继续遵守权限、分页和排序规则。

现有搜索的价值

条件明确、结果可控、行为稳定，是确定性检索的基础。

增强层新增的价值

降低字段记忆和入口查找成本，让复杂检索更接近用户的业务表达。

05 / CAPABILITY MODEL

智能层负责理解，业务系统负责判断和执行

智能检索不应直接面对数据库，也不应成为一个无法解释的黑盒。它需要建立在字段语义、可选值、权限和现有查询协议之上，把不确定性留在确认环节，把确定性留在业务系统。

能力层主要职责结果
业务语义维护字段名称、别名、状态含义、人员和日期等可检索信息系统知道用户说法对应哪些字段
意图理解识别查询对象、条件、关系和歧义项形成可解释的条件草稿
条件确认展示识别结果，支持修改、删除、补充和回退用户知道系统将要查什么
业务校验校验字段、值、权限和当前接口是否支持不支持或不明确的条件不进入执行
查询适配将确认后的条件转换为已有搜索参数复用原有列表数据和查询链路

自然语言只是入口之一。相同的条件模型也可以服务于查询模板、常用条件推荐和不同页面之间的搜索体验统一。

06 / VALIDATION PATH

先验证检索问题，再选择最合适的增强方式

是否采用自然语言、模板或其他智能交互，应由真实检索样本决定。建议以 ICCE 当前列表作为一个具体样本，先测量现有方式的成本，再比较不同增强方式带来的收益。

阶段一

收集真实问题

访谈使用者，记录高频查询、常用字段、组合方式和空结果场景。

阶段二

建立检索基线

记录完成时间、操作步骤、首次成功率和用户需要回退的环节。

阶段三

比较增强方案

对比筛选布局优化、查询模板、条件编排和自然语言入口的适用性。

阶段四

小范围验证

选择高频且可解释的查询，验证条件理解、确认体验和实际效率。

观察维度需要回答的问题建议指标
效率完成一次复杂检索是否更快完成时间、操作步骤、回退次数
理解用户是否能确认系统将要查询的内容条件修改率、确认通过率、歧义处理率
结果是否更容易得到可用结果首次成功率、空结果调整次数
兼容增强入口是否影响原有搜索传统入口可用性、权限和查询结果一致性
07 / IMPLEMENTATION PRINCIPLES

以复用现有能力为前提控制投入

落地重点不是重做列表，而是补齐字段语义、统一条件表达、增强确认交互和完成现有接口适配。先把“检索条件”从页面控件中抽出来，后续才能同时支持手工筛选、模板和智能入口。

复用

沿用现有搜索执行

继续使用既有分页、排序、权限和列表接口，智能层不直接访问业务数据库。

可解释

条件必须可见可改

不把模型输出直接当作最终查询，用户需要看到字段和值，并拥有确认和回退入口。

可扩展

建立统一条件模型

让筛选器、模板和智能入口共享字段语义和查询协议，避免每个页面单独建设。

风险控制方式落地要求
理解错误条件展示、用户确认、歧义项要求选择不确定时宁可提示补充，不直接执行
越权查询服务端按权限生成可用字段并在执行前校验不依赖前端隐藏控件或模型判断
结果不一致统一条件模型并与现有参数转换规则对照同一条件从不同入口执行结果应一致
使用率不足先从高频复杂检索切入，并保留传统入口用真实数据决定继续投入的场景
08 / DECISION

下一步需要确认的不是功能清单，而是验证方向

建议先形成一个小而完整的验证闭环，再根据证据决定产品形态、技术投入和适用范围。

确认是否进入智能检索体验方向的样本研究

以当前 ICCE 列表作为可观察样本，收集真实查询任务和用户操作基线。

确认现有搜索作为统一执行基础

无论入口是手工筛选、模板还是智能表达，最终都通过可校验的结构化条件执行。

确认产品、前端、后端和安全共同定义边界

共同确定字段语义、权限规则、敏感数据处理、验证指标和后续技术路线。

09 / TECHNICAL APPENDIX

技术方案承接产品方向

  • 统一查询协议作为传统筛选、智能查询和查询模板之间的中间层。
  • 条件只在能够无损转换为现有搜索参数、且通过权限和业务校验时进入执行。
  • 列表查询与画布节点搜索保持各自作用域，避免把数据检索和画布定位混为一谈。
