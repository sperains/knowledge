# ICCE 视口实时表现态设计方案

## 当前结论

- `viewport store` 只保存动作结束后的可信提交态。
- `viewport-runtime` 和舞台承载连续手势中的实时表现态。
- 当前只接入确有逐帧视觉需求的消费者；新增消费者必须说明为什么不能读取提交态或在事件中即时计算。

## 1. 文档状态

- 当前状态：已完成选中控制元素的最小实现。
- 当前范围：滚轮连续缩放发布实时快照，连线端点、连线控制点以及图形和区域的缩放手柄按实时比例保持固定屏幕尺寸；其他元素尚未接入。
- 当前策略：连续手势优先直接变换 Konva Stage，动作结束后再将最终视口状态提交到 `viewport store`。
- 关联文档：[画布大规模节点性能优化方案](./画布大规模节点性能优化方案.md)。

本次只实现首个真实场景所需的实例级运行时和订阅链路，不提前接入其他候选元素。

## 2. 背景

连续缩放和平移属于高频表现行为。如果每一帧都更新响应式 `viewport store`，所有读取视口位置或比例的组件都可能重新计算，进而触发大范围 Vue 更新、富文本布局和 Konva 配置重建。

当前采用“连续过程直接变换舞台、动作结束提交 Store”的方向，可以将高频变化限制在 Konva 内部。部分界面元素可能要求在动作过程中实时响应视口，例如：

1. 选中框缩放手柄需要保持固定屏幕尺寸。
2. 连线端点和连接指示点需要保持固定屏幕尺寸。
3. 区域标题需要在缩放过程中维持稳定的屏幕像素大小。
4. 舞台外的富文本编辑器或其他 HTML 覆盖层需要实时跟随舞台位置和比例。

这些场景不应迫使全局视口 Store 恢复为逐帧响应式更新。因此后续需要时，可引入只服务表现层的轻量实时视口运行时。

## 3. 设计目标

1. 保持 `viewport store` 为动作完成后的正式视口状态。
2. 允许少量明确的表现元素选择性消费实时位置和比例。
3. 实时更新不得触发整棵画布组件树的响应式刷新。
4. 实时视口不能成为业务判断、持久化或协作同步的正式数据源。
5. 支持未来同一页面存在多个画布实例，避免不同画布共享实时状态。
6. 复用现有动画帧合并，不为实时视口额外创建一套高频调度循环。

## 4. 非目标

1. 不用实时视口替代 `viewport store`。
2. 不将实时比例写入 Pinia 或其他全局响应式状态。
3. 不要求所有画布元素订阅实时视口。
4. 不在连续缩放期间重新计算全部富文本布局。
5. 不用实时视口承载视口持久化、协作广播或业务命令参数。
6. 不因为已经存在运行时就提前接入没有明确实时需求的元素。

## 5. 双状态模型

### 5.1 提交态

提交态由 `viewport store` 持有，表示已经完成一次视口操作后的可信状态。

适用范围：

- 视口位置和比例持久化。
- 工具栏缩放百分比。
- 动作结束后的命中容差和控制点尺寸。
- 业务命令、视口适配、聚焦和恢复。
- 需要稳定快照的测试和调试信息。

提交时机：

- 连续缩放结束。
- 手形、中键或触摸板平移结束。
- 自适应、重置、聚焦等离散命令完成。

### 5.2 实时表现态

实时表现态由 `viewport-runtime` 持有，只反映当前舞台在这一帧已经应用的变换。

适用范围：

- 固定屏幕尺寸的少量 Konva 控制节点。
- 当前唯一打开的 HTML 编辑器或覆盖层。
- 缩放过程中需要跨比例阈值切换的低细节表现。

实时表现态可以被丢弃，不参与状态恢复。动作结束时，提交态与实时表现态必须收敛到同一份最终位置和比例。

## 6. 使用决策

新增场景应按以下顺序判断：

| 场景 | 推荐处理 |
| --- | --- |
| 普通图形、连线、只读富文本随舞台一起缩放 | 不读取比例，交给 Stage 自然变换 |
| 指针事件中临时计算吸附距离或命中容差 | 直接读取当前 Stage 的位置或比例 |
| 只需要动作结束后的最终尺寸或位置 | 读取 `viewport store` |
| 少量元素必须在连续过程中保持固定屏幕尺寸 | 订阅 `viewport-runtime` |
| HTML 覆盖层必须在连续过程中跟随舞台 | 订阅 `viewport-runtime` |
| 只在特定缩放档位切换细节 | 订阅经过分档后的实时比例，不消费每个连续比例 |

只有最后三类场景需要考虑引入实时运行时。

## 7. 实例范围与装配位置

`viewport-runtime` 应当是界面层的画布实例级服务：

1. 在 `DfdCanvas.vue` 中随画布实例创建。
2. 通过 Vue `provide/inject` 或显式依赖传递给手势控制器和消费者。
3. 画布卸载时销毁订阅和内部引用。
4. 不创建模块级单例，不放入 Pinia。

建议位置：

```text
src/views/icce/ui/viewport/viewport-runtime.ts
```

建议装配关系：

```text
DfdCanvas
├── 创建 viewport-runtime
├── 提供给 viewport-gesture-interaction
└── 提供给少量实时表现消费者
```

## 8. 接口草案

当前最小实现遵循以下接口：

```ts
import type { Point } from '@/views/icce/domain/model/geometry';

export type LiveViewportPhase = 'active' | 'settled';

export type LiveViewportSource =
  | 'wheel'
  | 'trackpad'
  | 'hand'
  | 'middle'
  | 'programmatic';

export interface LiveViewportSnapshot {
  position: Point;
  scale: number;
  phase: LiveViewportPhase;
  source: LiveViewportSource;
}

export interface ViewportRuntime {
  getSnapshot(): LiveViewportSnapshot;
  publish(snapshot: LiveViewportSnapshot): void;
  subscribe(listener: (snapshot: LiveViewportSnapshot) => void): () => void;
  destroy(): void;
}
```

约束：

1. `publish` 只保存普通对象并通知当前订阅者，不写入响应式 Store。
2. `subscribe` 必须返回精确取消订阅函数。
3. `getSnapshot` 只用于读取当前帧快照，不提供状态修改能力。
4. `destroy` 必须释放全部订阅者，避免画布反复挂载后残留回调。

## 9. 发布流程

### 9.1 连续手势帧

实时快照应在舞台完成当前帧变换后发布：

```ts
stage.position(nextPosition);
stage.scale({ x: nextScale, y: nextScale });

viewportRuntime.publish({
  position: nextPosition,
  scale: nextScale,
  phase: 'active',
  source: 'wheel',
});
```

发布必须复用已有的动画帧合并结果，不能直接响应每个原始滚轮或指针移动事件。

### 9.2 动作结束

动作结束时先提交正式状态，再发布最终快照：

```ts
viewportStore.setViewport(finalPosition, finalScale);

viewportRuntime.publish({
  position: finalPosition,
  scale: finalScale,
  phase: 'settled',
  source: 'wheel',
});
```

此时工具栏、持久化和其他正式消费者统一从 `viewport store` 获取最终状态。

## 10. 消费方式

### 10.1 事件中的即时计算

如果只在事件处理函数中需要当前比例，不需要订阅运行时，应直接读取 Stage：

```ts
const scale = stage.scaleX();
const snapDistance = 10 / Math.max(scale, 0.01);
```

这类读取不会建立响应式依赖，也不会产生持续通知成本。

### 10.2 少量 HTML 覆盖层

例如当前唯一打开的富文本编辑器，可以在挂载期间订阅实时快照：

```ts
const liveViewport = shallowRef(viewportRuntime.getSnapshot());

const unsubscribe = viewportRuntime.subscribe((snapshot) => {
  liveViewport.value = snapshot;
});

onUnmounted(unsubscribe);
```

只有确实需要 Vue 模板或计算属性驱动的少量组件才能使用这种方式。禁止让每个图形或每条连线都持有实时响应式快照。

### 10.3 Konva 控制节点

选中手柄、端点等少量 Konva 节点优先使用命令式更新：

```ts
const unsubscribe = viewportRuntime.subscribe(({ scale }) => {
  const node = controlPointRef.value?.getNode();
  if (!node) return;

  const size = 9 / Math.max(scale, 0.01);
  node.size({ width: size, height: size });
  node.offset({ x: size / 2, y: size / 2 });
  node.getLayer()?.batchDraw();
});
```

多个节点位于同一图层时，应集中更新并只调用一次 `batchDraw`，避免每个订阅者分别调度绘制。

### 10.4 区域标题

如果区域标题必须保持固定屏幕尺寸，优先将标题内容放入独立 Group，并对 Group 应用实时反向缩放：

```ts
headerGroup.scale({
  x: 1 / Math.max(scale, 0.01),
  y: 1 / Math.max(scale, 0.01),
});
```

标题内部字体、头像、间距等可以直接使用屏幕像素尺寸，避免每一帧重新生成所有标题配置和重复测量文字。区域数量较多时，只为视口内区域标题注册实时更新。

## 11. 元素策略建议

| 元素 | 建议策略 | 原因 |
| --- | --- | --- |
| 普通图形 | 跟随舞台 | 不需要额外计算 |
| 普通连线 | 跟随舞台 | 缩放期间不需要调整业务几何 |
| 连线命中宽度 | 动作结束更新 | 连续变换期间主图层可关闭命中 |
| 只读富文本 | 冻结布局并跟随舞台 | 避免批量测量和换行 |
| 编辑中的 HTML 富文本 | 实时表现态 | 通常只有一个实例，且位于舞台外 |
| 选中缩放手柄 | 实时表现态 | 数量少，需要固定屏幕尺寸 |
| 连线端点和控制点 | 实时表现态 | 已接入，连续缩放时保持固定屏幕尺寸 |
| 图形和区域缩放手柄 | 实时表现态 | 已接入，连续缩放时保持固定屏幕尺寸和命中宽度 |
| 区域标题 | Group 反向缩放 | 避免逐字段重新计算配置 |
| 上下文工具栏和快捷新增 | 缩放期间隐藏，结束后更新 | 当前不必承担实时跟随成本 |
| 低细节渲染 | 比例分档 | 避免响应每个连续比例 |

## 12. 性能约束

1. 实时快照每个动画帧最多发布一次。
2. 未订阅实时运行时的组件不得因为快照发布而重新计算。
3. 普通图形、普通连线和只读富文本不得批量订阅实时比例。
4. 优先读取 Stage 完成事件内的一次性计算，只有持续视觉更新才订阅。
5. 多个命令式消费者的图层绘制应合并为一次 `batchDraw`。
6. 比例变化不足以产生视觉差异时，可以使用最小差值或比例分档抑制更新。
7. 视口外消费者应暂停订阅或退出实时更新集合。
8. 动作结束后，运行时快照必须与 Store 最终状态一致。

## 13. 与现有视口能力的边界

### 13.1 `viewport store`

继续负责正式状态、离散命令、持久化和结束态读取。不得为了单个实时元素重新改为逐帧写入。

### 13.2 `viewport-controller`

继续负责自适应、聚焦、重置、按钮缩放等离散视口用例。连续手势可以在最终提交时调用其正式入口，但不通过它逐帧驱动响应式状态。

### 13.3 `viewport-gesture-interaction`

当前由该交互控制器在滚轮缩放合并帧中更新 Stage 并发布实时快照，在手势结束时提交 Store。后续其他连续手势如需实时消费者，再沿用同一发布入口。

### 13.4 事件总线

实时视口不通过全局事件总线广播。高频全局事件难以约束消费者数量和生命周期，也不利于多画布实例隔离。正式的视口结束事件仍可沿用现有事件总线。

## 14. 扩展条件与实施步骤

选中态的连线端点、连线控制点以及图形和区域缩放手柄已经完成最小实现。其他元素只有满足以下任一条件时才继续接入：

1. 产品明确要求缩放过程中其他表现元素保持固定尺寸。
2. 产品明确要求编辑器或 HTML 覆盖层在连续视口变换中保持可见并实时跟随。
3. 区域标题在连续缩放中的尺寸变化已经成为可复现的视觉问题。
4. 低细节渲染需要在连续缩放过程中跨档切换。

建议实施顺序：

1. 以新的真实消费者为范围复用画布实例级运行时。
2. 复用现有动画帧合并后的快照，不新增高频调度入口。
3. 只接入目标消费者，不顺带迁移其它元素。
4. 验证动作结束后 Store 与运行时快照一致。
5. 记录一千节点场景下的 Vue 更新次数、脚本耗时和 Konva 绘制耗时。
6. 确认收益后，再逐个评估其他候选消费者。

## 15. 验证范围

实现运行时后至少验证：

1. 连续缩放期间不逐帧写入 `viewport store`。
2. 实时消费者能收到动画帧合并后的最新位置和比例。
3. 非实时消费者不会因运行时发布而触发 Vue 更新。
4. 动作结束后 Store、Stage 和运行时三者状态一致。
5. 画布卸载后订阅全部释放。
6. 两个画布实例的实时状态互不影响。
7. 缩放中断、组件卸载和工具切换后不会保留活动态。
8. 选中手柄、区域标题或 HTML 编辑器的实时调整不会触发全部富文本重新布局。

## 16. 当前结论

当前继续使用“Stage 承担连续变换、Store 保存结束态”的方案。实例级 `viewport-runtime` 已接入滚轮缩放过程，当前只有选区层和选中连线控制点组件订阅实时快照，用于重算少量控制元素。

普通画布元素继续依靠舞台自然变换，其他元素在没有明确实时需求前不增加订阅，也不改变现有 Store 职责。
