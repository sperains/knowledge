# 一、结论摘要

推荐采用“自然语言 → 统一查询描述协议 → 校验归一化 → 既有列表接口”的增量方案：

1. 传统筛选继续负责确定性查询，AI 只负责把自然语言翻译成结构化查询草稿。
2. AI 不能直接生成或执行 SQL，也不能绕过字段权限、查询接口和既有业务状态参数。
3. 用户必须看到并确认 AI 识别出的条件；条件以可编辑的筛选项展示，确认后才执行查询。
4. 统一查询描述协议是传统筛选、AI 查询、高级查询、保存查询和后续报表能力的共同中间层。
5. 首期只落地 ICCE 列表查询的可验证纵向切片；ICCE 画布节点搜索继续使用现有文本匹配、高亮和视口定位链路，不与列表查询强行合并。

本文是实施方案，不代表已接受的架构决策。完成首期验证后，再根据真实接口和使用数据决定是否新增 ADR。

# 二、背景与当前代码事实

## 2.1 用户问题

ICCE 列表的字段、状态、时间、人员和业务条件持续增加。用户通常知道业务意图，却不一定知道对应字段、筛选入口和操作符。例如“查最近三个月未完成的重点项目”需要用户自行拆成多个筛选项。

共享对话提出的核心方向是：

```text
自然语言
  ↓
模型理解
  ↓
统一查询描述协议
  ↓
字段与值校验
  ↓
既有查询接口
```

## 2.2 ICCE 列表当前链路

当前源码已确认以下事实：

| 环节 | 当前实现 | 对方案的影响 |
| --- | --- | --- |
| 页面入口 | `src/views/icce/index.vue` | 页面负责调用 `BaseTable`、标签切换、清除条件和详情跳转 |
| 表格组件 | `src/components/BaseTable/index.vue` | 表格内部持有查询状态，并将列搜索交给 `ColSearch` |
| 查询状态 | `type`、`search`、`order` | 需要保留待办、已办、全部和排序语义 |
| 请求编排 | `src/hook/useTableData.ts` | 请求体会合并分页、查询状态、自定义参数和强制参数 |
| 列元数据 | 后端返回 `column_data` | 已有字段标题、字段名、搜索字段、搜索类型、操作符和数据源线索 |
| 列搜索 | `src/components/ColSearch/index.vue` | 已支持文本、单选、多选、人员、树形、数字范围和日期范围等类型 |
| 下拉数据源 | `getSearchSourceFun` | AI 识别出的枚举、人员和树节点必须使用真实值，不得只传展示名称 |
| 列表接口 | `bus/icce/get-list` | 现有后端查询契约可以作为首期执行出口，但完整服务端语义尚未从本仓库核验 |

当前列搜索项大致形态为：

```json
{
  "field": ["status"],
  "search_type": "singleSelect",
  "column_id": 10001,
  "op": "eq",
  "value": ["completed"]
}
```

数字和日期范围使用带开始、结束值的对象；多选和树形条件使用真实选中值。具体字段和接口语义以服务端契约为准，不能仅根据页面字段名称推断。

## 2.3 ICCE 画布搜索当前链路

当前 `src/views/icce/ui/components/canvas/CanvasTop.vue` 的搜索是另一种能力：

- 通过 `canvasQuery.findTargetsByText` 查询已加载的图形和富文本标签；
- 通过 `highlightStore` 写入搜索高亮；
- 通过 `viewportController.zoom('fit')` 定位命中对象；
- 受 `icce_search_nodes-view` 权限控制；
- 未绑定节点高亮与普通搜索共享搜索来源，但仍分别维护目标集合。

这条链路不请求列表接口、不改变领域实体、不产生 `CanvasChangeSet`，也不应被首期列表智能查询改写。后续若增加“用自然语言定位画布节点”，应另建画布查询模型，不能把列表字段条件直接投递给 `canvasQuery`。

# 三、目标与非目标

## 3.1 目标

1. 让用户可以用自然语言表达 ICCE 列表查询意图。
2. 将 AI 输出限制在当前模块、当前用户可见字段和允许操作符内。
3. 让用户能够查看、删除、修改和补充识别出的条件。
4. 让确认后的查询复用现有 `getListFun` 和列表分页、标签、排序能力。
5. 让传统列筛选、AI 查询、高级查询和保存查询最终共享同一种规范化查询表达。
6. 为上下文查询、空结果解释和查询模板提供稳定扩展点。

## 3.2 非目标

- 首期不替换传统列筛选。
- 首期不让模型直接访问数据库、生成 SQL 或调用任意内部接口。
- 首期不将自然语言查询接入画布变更、协作消息、撤销重做或提交态失效。
- 首期不把 `LogicCanvas`、`DfdCanvas`、列表数据和画布实体统一成一个查询模型。
- 首期不根据 AI 猜测补齐缺失业务字段；缺失值保持空值并要求用户确认或重新输入。
- 首期不承诺跨模块、跨租户、跨权限域搜索。

# 四、核心边界

```text
界面层：输入、条件卡片、确认、编辑、错误提示
    ↓
应用层：组织解释、校验、合并、执行和保存查询
    ↓
查询协议：规范化字段、操作符、值和逻辑关系
    ↓
适配层：协议查询 → ICCE 既有 search/order 请求格式
    ↓
既有列表接口：分页、标签、权限过滤和业务数据查询
```

边界规则：

- 模型只产生查询草稿，不能成为业务查询执行器。
- 查询协议只描述查询意图，不携带数据库表名、SQL 片段或内部实现细节。
- 字段权限在 Schema 发给模型前过滤一次，在服务端执行前再校验一次。
- `BaseTable` 继续是通用表格组件，不引入 AI、模型供应商或 ICCE 业务判断。
- `useTableData` 继续负责分页和列表请求；查询协议适配不应复制一套请求生命周期。
- 传统筛选和 AI 查询最终必须落到同一个“已应用查询”状态，清除操作也必须只有一个事实来源。
- 查询行为是只读操作，不进入 ICCE 的 Plan → Commit → CanvasChangeSet → Publish 链路。

# 五、统一查询描述协议

## 5.1 规范化模型

协议建议使用版本化、模块化的树形结构：

```ts
type QueryOperator =
  | 'eq'
  | 'neq'
  | 'gt'
  | 'gte'
  | 'lt'
  | 'lte'
  | 'contains'
  | 'startsWith'
  | 'in'
  | 'between'
  | 'isNull'
  | 'isNotNull';

type QueryValue = string | number | boolean | null | string[] | number[] | {
  start?: string | number | null;
  end?: string | number | null;
};

interface QueryCondition {
  kind: 'condition';
  field: string;
  operator: QueryOperator;
  value: QueryValue;
}

interface QueryGroup {
  kind: 'group';
  logic: 'and' | 'or';
  children: Array<QueryCondition | QueryGroup>;
}

interface SearchQuery {
  schemaVersion: string;
  scope: 'icce-list';
  moduleId: string | number;
  root: QueryGroup;
  sort: Array<{ field: string; order: 'asc' | 'desc' }>;
}
```

协议中不放置 `page` 和 `pageSize` 的 AI 结果。分页是列表界面状态，由 `useTableData` 管理；保存查询可以保存排序，但不能让自然语言覆盖当前用户的分页偏好。

## 5.2 示例

以下示例仅用于说明结构，字段编号、状态值和日期都必须由实际 Schema 与时间上下文解析，不能直接当作 ICCE 当前业务字段：

```json
{
  "schemaVersion": "icce-list-1",
  "scope": "icce-list",
  "moduleId": "icce",
  "root": {
    "kind": "group",
    "logic": "and",
    "children": [
      {
        "kind": "condition",
        "field": "status",
        "operator": "neq",
        "value": "closed"
      },
      {
        "kind": "condition",
        "field": "createdAt",
        "operator": "between",
        "value": {
          "start": "2026-06-17",
          "end": "2026-09-17"
        }
      }
    ]
  },
  "sort": []
}
```

## 5.3 版本与能力降级

规范化协议可以表达 `or` 和嵌套分组，但当前 ICCE 既有 `search` 数组是否支持复杂逻辑尚未核验。因此适配器必须声明能力：

- 首期只允许可无损转换为既有 `search` 数组的平面 `and` 条件。
- `or`、嵌套分组和跨字段计算条件暂不执行，返回“当前列表暂不支持该组合条件”，不得静默改成 `and`。
- 服务端确认支持复杂逻辑后，再提升 `schemaVersion` 或增加后端查询协议版本。
- 协议未知字段、未知操作符、值类型不匹配和空的范围端点均在适配前拒绝。

# 六、Schema 驱动的字段模型

## 6.1 字段来源

分两步实施：

### 首期兼容来源

使用 ICCE 列表接口返回的 `column_data` 作为字段注册表的初始来源，由前端转换为统一字段模型。可使用的信息包括：

- `dataIndex`：页面显示字段标识；
- `title`：用户可见标题；
- `search_field`：实际查询字段；
- `search_type`：输入和取值方式；
- `op`：当前后端操作符线索；
- `source_field`、`depend_model`：动态数据源线索；
- `is_view`、`noSearch`：显示和搜索限制线索。

首期只支持后端明确标记为可搜索且用户有查看权限的字段。隐藏列不因为 AI 能识别其中文名称就自动开放搜索。

### 稳定来源

后端补充独立的 ICCE 查询 Schema 接口，由服务端按模块、角色、数据权限返回权威字段定义。建议接口形态如下，接口名称只是提案，待后端确认：

```text
POST bus/icce/search/schema
```

```ts
interface SearchFieldSchema {
  key: string;
  label: string;
  aliases?: string[];
  type: 'text' | 'number' | 'date' | 'datetime' | 'enum' | 'user' | 'tree' | 'boolean';
  operators: QueryOperator[];
  searchable: boolean;
  visible: boolean;
  valueSource?: 'static' | 'search-source' | 'user' | 'tree';
  optionValueKey?: string;
  optionLabelKey?: string;
  relation?: { module: string; field: string };
  nullable?: boolean;
  timezone?: string;
}
```

## 6.2 字段语义规则

- `key` 是实际查询字段的稳定标识，不使用中文标题替代。
- `label`、`aliases` 只用于帮助模型理解，不可作为请求字段发送。
- `operators` 是字段允许的操作符白名单，不由模型自由决定。
- 枚举、人员和树节点必须返回真实值与展示文本的明确映射。
- 相对日期在服务端或统一时间上下文中解析，并记录解析时区和基准时间。
- `contains`、大小比较、空值判断等语义必须由后端 Schema 明确声明。
- 关联字段必须声明关系来源；未声明的字段不允许通过名称猜测关联路径。
- 缺少真实值时保留空值或进入待确认状态，不用编号、名称、负责人或其他字段冒充。

# 七、查询处理流程

## 7.1 首次自然语言查询

```text
输入自然语言
  ↓
读取当前模块 Schema、用户权限、当前时间和当前已应用查询
  ↓
请求 AI 解释服务
  ↓
服务端校验输出格式和字段白名单
  ↓
前端再次校验并生成查询草稿
  ↓
展示条件卡片、歧义和无法识别项
  ↓
用户编辑或确认
  ↓
规范化查询
  ↓
转换为既有 search/order
  ↓
复用 getListFun 请求列表
```

推荐的 AI 返回结果不是直接返回 `SearchQuery`，而是带解释状态的草稿：

```ts
interface SearchInterpretation {
  status: 'ready' | 'needs_confirmation' | 'unsupported' | 'invalid';
  query: SearchQuery | null;
  conditions: Array<{
    field: string;
    label: string;
    operator: QueryOperator;
    value: QueryValue;
    displayValue?: string;
    confidence?: 'high' | 'medium' | 'low';
  }>;
  ambiguities: Array<{
    text: string;
    candidates: Array<{ value: string | number; label: string }>;
  }>;
  unsupported: string[];
}
```

前端不得仅根据 `confidence` 自动执行。只要存在歧义、未解析值或不支持条件，就必须阻止查询或要求用户处理。

## 7.2 与传统筛选合并

首期建议将查询状态分成三个概念，但只保留一个执行快照：

| 状态 | 作用 | 是否请求接口 |
| --- | --- | --- |
| 自然语言输入 | 用户正在输入的原始文本 | 否 |
| AI 查询草稿 | 模型解析出的待确认条件 | 否 |
| 已应用查询 | 用户确认后的规范化条件 | 是 |

应用规则：

1. 用户从空白状态发起 AI 查询时，默认替换当前 AI 草稿，不直接覆盖已应用的手工条件。
2. 用户明确说“在当前条件上增加……”时，才把 AI 结果作为增量合并；合并后仍需确认。
3. 用户直接操作传统列筛选后，已应用查询以传统筛选的真实状态为准，AI 草稿标记为过期并要求重新解释。
4. “清除搜索条件”同时清理输入文本、AI 草稿、已应用查询和表格列搜索状态，但不清理固定业务参数和当前标签，除非页面现有行为明确要求清理。
5. AI 不能隐式删除用户已经确认的条件；替换、删除和放宽条件都必须在条件卡片中可见。

为避免页面组件直接改写 `BaseTable` 内部响应式对象，建议给 `BaseTable` 增加通用、非 AI 专用的查询控制入口，例如“应用外部查询”和“读取当前查询”。该入口只接收既有查询结构，不了解模型和自然语言。若首期不扩展通用表格组件，也可以在 ICCE 页面先使用明确的适配器封装现有暴露的查询状态，但不应让 AI 逻辑散落在 `BaseTable` 或 `ColSearch` 中。

## 7.3 上下文查询

上下文查询放在第二阶段：

- 当前已应用查询作为只读基线传给解释服务；
- 解释结果必须标记 `replace` 或 `merge`，不能由前端猜测；
- 只允许对当前 Schema 中的字段生成增量；
- 合并结果在界面展示“保留条件”和“新增条件”；
- 用户确认后才执行；
- 解析服务不可访问历史对话以外的业务数据。

# 八、界面方案

## 8.1 布局

ICCE 列表页保留现有标签、清除条件和新建按钮，在列表上方增加 AI 查询栏：

```text
[ 搜索：查最近三个月未完成的 ICCE ] [解析]

已识别：
[创建时间 最近三个月 ×] [状态 未完成 ×] [添加条件]
                       [应用并搜索]

[传统列筛选表格]
```

推荐交互：

- 输入阶段只做解析，不刷新列表；
- 解析失败显示原因和可用字段提示；
- 条件卡片支持删除、重新选择枚举、修改范围和补充条件；
- 用户确认后才刷新列表；
- 已应用的 AI 条件与传统列筛选保持同一视觉语义，不额外制造第二套筛选结果；
- 当前 AI 查询可保存为模板，模板保存规范化协议，不保存模型原始回复作为唯一事实。

## 8.2 空结果解释

首期不让模型根据列表数据猜测原因。列表返回空结果时，先展示确定性内容：

- 当前已应用条件；
- 当前标签、分页和排序；
- 可由协议安全生成的放宽操作，例如删除某个条件、扩大日期范围、改为包含匹配。

只有后端提供逐条件统计或对比查询能力后，才展示“哪个条件可能导致结果减少”的说明；否则必须标注为建议，不能写成事实。

# 九、后端与接口建议

以下接口是待确认的后端协作清单，不代表当前仓库已有实现。

## 9.1 查询 Schema

```text
POST bus/icce/search/schema
入参：module_id、当前业务标签、必要的上下文标识
出参：schemaVersion、scope、fields、supportedGroups、serverTime、timezone
```

服务端按当前用户权限过滤字段和可选值；前端不能通过修改请求参数自行扩大字段范围。

## 9.2 AI 解释

```text
POST bus/icce/search/interpret
入参：scope、module_id、schemaVersion、text、baseQuery、timezone、referenceTime
出参：结构化草稿、歧义、未支持内容、解释版本和请求编号
```

服务端负责：

- 模型调用和密钥管理；
- Schema 注入和字段白名单；
- 结构化输出格式约束；
- 字段、操作符和值的二次校验；
- 敏感字段和用户输入的脱敏策略；
- 超时、重试、限流和审计。

前端负责：

- 输入节流和取消过期请求；
- 展示草稿和错误；
- 用户确认与编辑；
- 最终协议校验和列表请求编排。

## 9.3 查询执行

首期继续调用 `bus/icce/get-list`。建议服务端在兼容旧 `search/order` 的同时，预留明确的规范化查询入口或版本字段；在后端确认前，前端适配器不得伪造复杂逻辑能力。

## 9.4 查询模板

第二阶段可增加：

```text
POST bus/icce/search/templates/list
POST bus/icce/search/templates/save
POST bus/icce/search/templates/delete
```

模板至少保存：模块标识、Schema 版本、规范化查询、排序、名称、创建人、可见范围和更新时间。原始自然语言可以作为辅助展示文本，但不能替代规范化查询。

# 十一、分阶段实施计划

## 阶段零：契约盘点与样例冻结

产出：

1. 盘点 ICCE `column_data` 的真实字段、权限、操作符、动态值源和空值语义。
2. 从后端确认 `get-list` 的 `search/order` 语义，特别是数组值、日期范围和多条件逻辑。
3. 冻结一组脱敏的查询 Schema 和解析样例，不使用真实业务数据作为模型上下文。
4. 明确模型部署位置、数据保留、限流、审计和失败降级策略。

退出条件：字段白名单、操作符白名单、值编码和“不支持即拒绝”规则有明确责任人确认。

## 阶段一：不接 AI 的统一协议纵向切片

产出：

1. 建立 ICCE 列表查询协议类型和运行时校验。
2. 实现“协议查询 ↔ 现有 `search/order`”适配器。
3. 让传统列筛选可以转换为规范化查询，再转换回既有请求格式。
4. 覆盖单值、多值、数字范围、日期范围、人员和树形值。
5. 对 `or` 和无法无损转换的条件明确拒绝。

退出条件：传统筛选行为不变，协议转换具备可重复测试，`clearAll`、标签切换、分页和排序行为不回归。

## 阶段二：AI 解释与人工确认

产出：

1. 接入 Schema 和解释接口。
2. 增加 AI 查询栏、条件卡片、歧义选择和应用按钮。
3. 模型结果必须经过服务端和前端双重校验。
4. 失败时保留传统筛选，AI 失败不阻断列表页面。
5. AI 查询应用后走阶段一的同一适配器和列表请求出口。

退出条件：至少覆盖文本、枚举、人员、日期范围和无结果场景；未知字段、越权字段、错误值和不支持组合均不会发出列表请求。

## 阶段三：上下文、模板和确定性空结果建议

产出：

1. 增量合并和替换模式。
2. 保存、加载、删除查询模板。
3. 显示当前条件并提供协议可证明的放宽操作。
4. 增加查询版本、请求编号和审计记录。

退出条件：模板在 Schema 变化后能被检测为过期，并要求重新确认；旧模板不能静默使用错误字段。

## 阶段四：画布自然语言查询（可选）

仅在列表能力稳定、用户明确需要时实施：

- 单独定义 `scope: icce-canvas` 的查询模型；
- 将自然语言限制为节点、标签、区域和关系的只读定位条件；
- 复用 `canvasQuery`、`highlightStore` 和 `viewportController` 的既有职责；
- 不把画布定位结果写入 `Shape`、协作消息或变更集；
- 对空间关系、区域包含和端点关系建立独立的领域谓词；
- 大规模画布必须遵守现有空间索引和裁剪方案，不因 AI 搜索回退全量扫描。

# 十二、测试与验收标准

## 12.1 协议与适配器

- 文本、数字、枚举、人员、树形、日期和日期时间条件能正确归一化。
- 空值、零值、负数、边界日期和部分范围不会被误判为无条件。
- `search_field` 与页面显示字段不一致时，使用真实查询字段，不用显示字段冒充。
- 多值保持真实值集合，显示文本只用于界面。
- 未知字段、越权字段、未知操作符、错误值类型和不支持的逻辑结构被拒绝。
- 协议转换不会丢失 `type`、固定参数、排序或标签语义。
- 传统筛选清除后，协议查询、条件卡片和表格查询状态一致。

## 12.2 AI 交互

- 输入不会自动刷新列表；只有用户确认后才执行。
- 模型返回歧义时显示候选，不猜测唯一值。
- AI 服务超时、错误或返回非法结构时，传统列表仍可用。
- 用户删除一个条件只删除对应条件，不影响其他条件。
- 手工修改条件后，AI 草稿不会继续覆盖手工结果。
- Schema 变化或模板过期时，用户能看到原因并重新确认。

## 12.3 ICCE 边界

- 智能列表查询不产生 `CanvasChangeSet`，不调用画布提交和协作发布。
- 智能列表查询不修改 `shapeStore`、`relationStore`、`highlightStore` 或视口状态。
- 画布现有文本搜索、高亮、未绑定节点清单和定位功能保持原行为。
- 只有获得列表模块权限和字段权限的内容可以进入解释和执行链路。

## 12.4 体验和运行质量目标

以下是待产品确认的目标值，不是当前系统已有指标：

- 解释请求可取消，过期响应不能覆盖新输入。
- 常见解释请求在三秒内返回可确认结果；超时提供重试和传统筛选入口。
- 列表查询耗时和结果一致性不劣于直接使用现有筛选。
- 记录解析成功率、用户修改率、确认率、拒绝原因、空结果率和模板使用率，但不记录不必要的业务原文或敏感数据。

# 十三、安全、权限与数据治理

1. 模型调用放在服务端或受控网关，前端不保存模型密钥。
2. Schema 必须按当前用户和模块权限裁剪；前端隐藏字段不是唯一安全边界。
3. 业务数据默认不随解释请求发送；只发送字段定义、必要的选项和用户输入。
4. 人员、客户、项目等敏感枚举值按权限提供；无法确认权限时不返回候选。
5. 服务端执行前重新校验模块、字段、操作符、值和数据权限，不能信任前端返回的规范化查询。
6. 记录模型版本、Schema 版本和协议版本，便于重现解析结果；原始自然语言按数据保留策略处理。
7. 限制输入长度、请求频率和单次条件数量，防止提示注入、资源滥用和超大查询。
8. 模型输出中的 SQL、接口地址、脚本和系统指令全部当作普通文本或非法字段处理，不执行。

# 十四、风险与待确认事项

| 事项 | 当前状态 | 处理方式 |
| --- | --- | --- |
| `bus/icce/get-list` 对复杂逻辑的支持 | 未从仓库核验 | 阶段零向后端确认；首期只支持可无损转换的平面条件 |

# 十五、决策门槛与实施状态

本文当前为 `draft`，不是已接受的架构决策。进入编码前至少需要确认：

1. 首期范围是 ICCE 列表页，不包含画布自然语言定位。
2. 后端认可 Schema、解释结果和执行校验的责任边界。
3. 既有列表接口是否能承载首期协议；不能承载的逻辑必须明确拒绝。
4. 字段权限、枚举值、时区和空值语义有可验证契约。
5. 模型部署、敏感数据、限流和审计方案通过评审。

完成阶段一并通过真实字段样例验证后，才适合把“查询协议与执行链路分离”“AI 只能生成草稿”“列表查询不进入画布变更链路”等稳定边界提升为新的 ICCE ADR。当前不创建 ADR，避免把未验证的接口草案写成长期约束。

# 十六、AI 实施指导原则

- 必须先读取实际 ICCE 列表调用链、列 Schema 和测试，再修改代码。
- 必须保持自然语言解释、查询协议校验、旧请求适配和列表执行四个职责可区分。
- 禁止让模型直接生成 SQL、数据库字段、任意接口调用或画布变更载荷。
- 禁止用展示标题、人员名称或其他字段冒充真实查询值；缺失值保持空值并进入待确认或拒绝状态。
- 优先复用现有 `BaseTable`、`ColSearch`、`useTableData` 和 `getSearchSourceFun` 的确定性能力。
- 不得把 AI 查询逻辑放进通用表格组件，也不得复制另一套分页、加载和错误处理生命周期。
- 不得把列表查询接入 Plan → Commit → CanvasChangeSet → Publish 或协作回放链路。
- 复杂逻辑不能在适配器中静默降级；无法无损表达时明确提示不支持。
- 新增测试统一放在 ICCE 测试目录并使用 Vitest；验证报告必须区分聚焦通过项、仓库基线噪声和未执行的浏览器验收。
