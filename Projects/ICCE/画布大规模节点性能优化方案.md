# ICCE 画布大规模节点性能优化方案

## 1. 背景

当画布包含一千个以上节点时，仅进行画布平移或缩放就会出现明显卡顿。浏览器控制台可见以下长任务：

- `mousemove` 处理耗时约 200 至 524 毫秒
- `mouseup` 处理耗时约 241 毫秒

本方案针对 `src/views/icce/ui/components/canvas/DfdCanvas.vue` 及其视口、图形和富文本渲染链路进行优化，保持现有图形交互和协作事件语义不变。

## 2. 排查结论

### 2.1 平移热路径重复驱动 Konva 和 Vue

手形工具在每个 `dragmove` 中将 Konva 舞台坐标写入视口状态。Konva 本身已经完成舞台移动和绘制，随后 Pinia 状态变化又会触发 `DfdCanvas` 重新渲染，并由 `vue-konva` 再次同步舞台配置。

因此平移链路近似为：

```text
Konva 舞台移动
→ dragmove
→ 响应式视口更新
→ Vue 组件更新
→ vue-konva 同步舞台配置
→ Konva 再次调度绘制
```

普通 `pointermove` 的节流不会覆盖 `dragmove`，所以当前手形拖拽没有获得这部分节流收益。

### 2.2 平移导致所有富文本节点重复做布局和页面测量

只读富文本的布局计算间接依赖视口的 `x`、`y` 和 `scale`。平移时 `scale` 没有变化，但视口坐标变化会使每个富文本组件重新计算覆盖层位置，并触发：

- 获取画布和覆盖层的页面矩形
- 查询覆盖层节点
- 富文本令牌布局
- 内容高度和缩放样式计算

这些计算对每个节点独立执行，在一千个节点时会放大为明显的主线程长任务。

### 2.3 主图层始终渲染全部图形和连线

主图层会同时创建所有区域、普通图形、连线、连线控制点和连线文本。当前没有视口裁剪、空间索引或低细节渲染，舞台平移和缩放都需要重新绘制整层内容。

### 2.4 缩放事件缺少帧合并

触控板或高频滚轮会连续触发缩放事件，每个事件都会更新视口位置和比例，并使区域标题、富文本尺寸和相关覆盖层重新计算。

### 2.5 标签点击触发大量全局指针监听

每个富文本节点原先都会注册一个文档级 `pointerdown` 监听器。画布包含大量富文本时，点击单个标签会让同一个原生指针事件依次调用大量监听器；同时画布文档监听器还会先清空选区，标签点击随后再次选中图形，形成一次点击内的重复响应式更新。

### 2.6 选中框覆盖标签导致全舞台命中扫描

图形或区域已经选中时，选中框位于富文本画布上方。标签点击和悬停首先命中选中框，如果继续调用 `stage.getAllIntersections()`，会在大图上产生数百毫秒级延迟。

区域空白处拖拽也会命中区域选中框。若此时为了判断内部图形继续执行全舞台交集扫描，即使最终没有命中业务图形，也会阻塞 `pointerdown`。因此区域选中框的按下路径应优先按图层从上到下读取当前位置的单点命中，空白处直接保留区域拖拽。

## 3. 实施范围和优先级

### 第一阶段：平移和富文本热路径

1. 手形拖拽改为自定义指针手势，动画帧内直接更新 Konva 舞台位置，拖拽结束时再写入持久化视口状态。
2. 平移期间进入视口平移交互状态，隐藏不必要的 HTML 覆盖层。
3. 只读富文本布局只依赖缩放比例；页面矩形测量仅在编辑器或标签操作浮层实际显示时执行。

### 第二阶段：缩放和交互节点

1. 使用动画帧合并滚轮缩放输入，连续缩放期间直接更新舞台变换，停止后一次性回写视口状态。
2. 仅为选中的连线创建控制点组件。
3. 平移和连续缩放期间关闭主图层命中检测，并只保留选中连线的控制点组件。

### 后续阶段：渲染架构

1. 将静态内容、交互内容和选区内容拆分到不同图层。
2. 对静态图层使用缓存或快照，但必须先完成真实大图和首帧体验验证。
3. 引入视口裁剪和空间索引，只维护视口附近节点。
4. 对远离视口或低缩放比例下的节点使用低细节渲染。

## 4. 验收指标

使用同一份一千个以上节点的图形数据，在相同浏览器和缩放比例下对比优化前后：

- 平移时主线程单帧脚本耗时目标低于 16 毫秒，优先达到低于 8 毫秒。
- 连续平移不再出现 200 毫秒以上的 `mousemove` 长任务。
- 平移期间富文本布局函数不因视口 `x`、`y` 变化而重复执行。
- 缩放连续输入应合并到动画帧内执行，不为每个原始滚轮事件单独触发完整视图更新。
- 松开鼠标后的最终位置、视口保存和协作事件保持现有行为。

另外，首次交互不应因为同步执行静态图层缓存而出现首帧卡顿；缓存方案必须满足“缓存未准备好时不阻塞当前交互”的约束。

## 5. 验证方式

使用浏览器性能面板录制以下场景：

1. 手形工具连续平移三秒。
2. 触控板连续缩放三秒。
3. 平移后快速松开鼠标。

重点观察 `dragmove`、富文本布局、页面布局测量、Vue 更新和 Konva 绘制耗时。代码层面的视口交互和富文本行为使用 `vitest` 定向测试验证。

## 6. 当前实施状态

- 方案文档：已完成。
- 第一阶段：已完成手形自定义指针平移、原生舞台拖拽关闭、富文本视口依赖优化。
- 第二阶段：已完成滚轮缩放帧合并、连续缩放响应式更新收口、未选中连线控制点裁剪，以及交互期间的主图层命中检测关闭。
- 主图层缓存：已暂时移除 `MainLayer.vue` 中的 `Layer.cache()` 处理。原因是缓存生成发生在平移或缩放首帧，会抵消其它优化收益；后续如重新引入，应采用空闲预热、缓存就绪后再使用，并结合权限和缓存失效策略验证。
- 交互事件：已完成富文本编辑器按需注册文档级指针监听，并移除画布文档级重复清空选区逻辑。
- 标签命中：已增加富文本标签的直接目标解析，避免按下标签时扫描整个舞台交集节点；性能日志可通过地址参数 `iccePerf=1` 或本地存储开关开启。
- 命中解析：普通图形目标也优先通过当前节点及祖先直接解析业务编号，仅无法解析时才回退到全舞台交集扫描。
- 选中框标签：已为当前选中图形增加基于富文本布局坐标的标签直达命中，避免选中框覆盖标签时再次执行全舞台交集扫描。
- 区域选中框：区域覆盖层点击内部图形、连线和富文本标签时，统一通过共享区域命中解析器按缓存后的区域后代候选进行坐标命中，避免区域级覆盖层扫描整张舞台。
- 选中框悬停：选中图形或区域的覆盖层指针移动改为坐标命中并直接更新标签悬停态，舞台级监听跳过覆盖层目标。
- 标签点击：已停止精确命中矩形向画布级兜底监听冒泡，并为只读画布控制器增加编号索引，避免重复舞台命中和控制器全量遍历。
- 性能计时：已拆分指针移动的节流排队时间与工具实际处理时间，避免将固定节流等待误判为业务耗时。
- 高亮更新：聚焦标签改为增量维护响应式集合，避免点击单个标签时让所有富文本组件重新同步高亮。
- 选区更新：已选中图形再次点击其标签时不重复写入相同选区，减少无意义的全画布响应式更新。
- 富文本布局收口：只读布局改为由父组件生成并传递给只读画布子组件，编辑测量布局仅在编辑状态按需计算，消除只读父子组件重复布局。
- 富文本高亮隔离：几何令牌不再携带当前高亮状态，标签悬停、焦点和搜索状态由只读子组件按绘制阶段解析，避免高亮变化触发文本测量和换行布局。
- 富文本缩放热路径：只读布局固定使用组件创建时的初始比例，连续缩放只交给舞台变换处理，避免每个缩放比例变化使全部富文本布局失效。
- 富文本布局埋点：新增只读布局批量汇总日志，所有富文本实例共享同一命名空间计数器，性能开关开启时可通过 `iccePerf=1` 观察 500 毫秒时间窗口内的布局次数、总耗时、平均耗时、最大耗时和片段数量；`icceDebug=1` 只开启普通调试日志，不会开启性能汇总。
- 双击编辑：增加跨舞台图形与选中框的双击判定，解决第一次点击后选中框覆盖原图形导致原生双击事件无法连续命中的问题。
- 选中框点击延迟：区域空白选中后再点击内部菱形标签，改为先按区域后代图形的几何范围直接命中，避免全舞台交集扫描。
- 区域空白拖拽：选中框按下时按图层读取单点底图命中，避免空白点击执行全量交集扫描；内部图形、连线和富文本标签仍按命中语义透传。
- 统一命中内核：新增共享命中结果、命中来源和节点解析入口，覆盖选中覆盖层、普通画布选中、富文本编号解析、图层单点命中、区域后代几何命中和全舞台交集候选生成；业务动作仍由调用方执行。
- 命中重复收敛：统一富文本坐标命中和交集节点结果转换，区域、选中覆盖层和普通画布入口复用同一套基础解析函数，避免组件内重复遍历和重复构造命中结果。
- 旧命中入口：已迁移拖拽投放和连线目标解析，删除旧的全舞台最佳业务编号解析入口；基础业务编号解析仍保留给不涉及交集排序的创建和快捷操作流程。
- 命中模块边界：不将覆盖层命中策略与通用命中解析器合并为单文件；通用解析器负责节点解析、候选构造和命中来源，覆盖层模块负责透传过滤、命中优先级和拖拽意图，避免后续策略分支重新污染通用扫描路径。
- 富文本编辑器提示：双击标签进入编辑器时出现的非被动触摸监听提示来自编辑器列表格式内部监听器，其处理逻辑需要阻止默认行为，不能简单改为被动监听；该提示不是当前长任务根因。
- 视口裁剪：已完成主图层的图形、区域和连线裁剪，仅挂载视口及三百二十像素缓冲区内的元素；当前选中图形和连线始终强制保留。
- 空间索引：已完成图形与连线的均匀网格索引，并在创建、更新、删除和清空数据时增量维护；范围选择和画布查询已复用同一索引入口。
- 裁剪窗口更新：平移和缩放期间使用实时视口状态，仅在视口接近缓冲区边缘时刷新挂载集合；手形和触控板平移均已补齐活动态与落稳态发布。
- 富文本虚拟化：图形与连线的只读文本只在视口及九十六像素文本缓冲区内挂载；当前选中、文本高亮和富文本标签高亮目标始终强制保留完整内容。
- 连续缩放降载：连续缩放期间暂停非强制文本，缩放落稳后恢复视口内完整文字；不再按固定缩放比例隐藏富文本。
- 视口外模型更新：功能组件删除不再依赖已挂载的富文本控制器，视口外图形仍能直接更新领域数据。
- 富文本结构减负：已移除片段级分组和独立透明命中矩形，每个只读富文本只保留一个整体命中矩形，视觉背景和文字节点均不参与命中。
- 富文本冗余节点清理：已彻底移除只读画布外层的基础文字节点；纯普通文本和缺少富文本增量数据的历史内容统一转换为只读文字令牌，不再维护第二套文字渲染路径。
- 富文本坐标命中：普通画布、选中覆盖层和区域覆盖层复用同一份稳定布局坐标；标签点击、悬停与条件双击不再依赖片段节点编号。
- 富文本控制器索引：整体命中矩形携带稳定只读画布编号，普通点击和悬停直接从编号映射获取控制器，并统一使用画布世界坐标解析缩放、平移后的标签位置，不遍历全部富文本实例。
- 后续阶段：继续收口统一语义命中；静态图层缓存只有在真实大图性能面板确认存在稳定收益后再评估，不继续推进富文本视觉节点合并。

- 交互和工具相关测试已通过，覆盖平移、缩放、选区、标签命中和富文本交互。
- 当前版本已通过生产构建。
- 全量类型检查已通过；全量单元测试共一百二十四个文件、五百二十七个用例通过。
- 清理透明基础文字节点后，固定二千一百乘九百八十九视口重新加载并采样：确定性千节点场景由二千五百二十二个场景节点降至二千三百一十三个，减少约百分之八点三；七十五号真实单据功能图在百分之十六比例下由四千六百六十六个降至三千八百九十三个，减少七百七十三个，约百分之十六点六。
- 七十五号真实单据在百分之十六比例下仍展示完整画布内容，确认富文本不再受早期百分之四十五固定阈值控制。浏览器固定视口采样的帧间隔受当前运行环境影响较大，本轮只将场景节点数量作为结构减负结论，帧率收益需在同一浏览器会话和交互序列下重复对照。
- 后续性能验证应重点记录 `selected-overlay-pointerdown`、`pointerdown`、`pointerup`、编辑器挂载和富文本布局耗时，并区分缓存生成耗时与实际平移绘制耗时。

### 7.1 可复现性能基线

开发环境通过 `/icce-demo` 进入统一的大规模节点基线场景。默认场景固定生成 1000 个业务图形、20 个区域、975 条连线和 1000 条包含关系；所有图形包含文本，其中每 5 个图形包含一组标签和条件富文本。数据编号、位置、连线和富文本内容均为确定性生成，同一参数每次加载结果一致。

真实业务单据可以在详情页地址追加 `iccePerf=1` 打开同一采样面板，例如 `/icce_detail/75?from=index&iccePerf=1`。真实单据报告直接读取当前图形、区域、连线、关系和富文本数量，不复制或改写业务数据。确定性场景用于优化前后严格对比，真实单据用于确认优化收益能够覆盖实际数据分布，两类报告不应混为同一组对照数据。

地址参数：

- `nodes`：业务图形数量，范围 100～5000，默认 1000。
- `columns`：每行图形数量，范围 10～业务图形总数，默认 40。
- `richEvery`：每多少个图形生成一次标签和条件富文本，默认 5。
- `iccePerf=1`：在统一报告之外开启既有富文本布局和交互慢调用日志。

基线记录步骤：

1. 使用同一浏览器版本、窗口尺寸和系统缩放打开基线页面。
2. 等待面板中的“渲染落稳”出现数值；首次记录冷加载结果，再点击“重新加载”记录一次热加载结果。
3. 点击“采样 5 秒”，在采样期间连续执行固定顺序的缩放、平移和节点点击。
4. 复制报告，保存加载耗时、帧间隔平均值与九十五分位、超预算帧、长任务和 Konva 场景节点数量。
5. 优化前后必须使用完全相同的地址参数和交互顺序；报告中的场景编号不一致时不得直接比较。

报告只负责浏览器侧可重复采样，不替代性能面板火焰图。出现五十毫秒以上长任务时，仍需使用浏览器性能面板区分 Vue 更新、Konva 绘制、富文本布局和命中扫描成本。

## 8. 下一步优化计划

缩放性能按照以下顺序推进。视口裁剪、空间索引、富文本视口虚拟化、富文本片段结构减负、冗余透明节点清理和控制器直接索引已经完成，下一步继续收口统一语义命中。富文本视觉节点合并已经完成收益评估并决定不实施，按固定缩放比例隐藏富文本的低细节策略也已经移除。

### 8.1 视口裁剪与空间索引（最高优先级）

实施状态：已完成。

本阶段引入视口裁剪，只渲染视口范围内以及少量缓冲区范围内的节点，避免画布始终挂载全部区域、图形、连线及富文本内容。

实施内容：

1. 根据视口边界查询可见图形、区域、连线和富文本节点。
2. 使用四叉树或其他空间索引，避免每次缩放都遍历全部节点。
3. 图形位置、区域移动、创建和删除后增量更新索引。
4. 选中框、普通画布选择和区域内部命中统一复用空间索引。
5. 视口裁剪需要保留缓冲区，避免节点刚进入视口时出现明显闪烁。

实测结果：

- 确定性千节点场景在相同参数下，场景节点由一万四千三百四十八个降至三千三百四十一个，减少约百分之七十六点七；渲染落稳由约六千一百八十二毫秒降至约一千九百一十三毫秒。
- 七十五号真实单据在功能图百分之四十三缩放比例下，场景节点由六千二百一十个降至三千六百八十二个，减少约百分之四十点七。
- 千节点场景连续缩放采样中，平均帧率由约十九点三六提升至约二十七点四九，九十五分位帧间隔由约一百六十六点六毫秒降至约一百点三毫秒；两次采样仍受浏览器调度影响，节点数量和渲染落稳时间是本阶段更稳定的对比指标。

涉及范围：

- `MainLayer.vue`
- `ShapeRenderer.vue`
- `canvas-query.ts`
- 新增视口空间索引模块

### 8.2 富文本按视口虚拟化

实施状态：已完成。

富文本只读画布包含独立的布局和命中节点，是缩放过程中的重点开销。应将富文本的显示和命中数据拆开，避免为了命中信息而挂载全部富文本组件。

实施内容：

1. 视口外节点只保留图形外框，不挂载富文本只读画布。
2. 不按固定缩放比例隐藏标签、条件或普通文字，视口内图形在任意落稳比例下均展示完整富文本。
3. 连续缩放期间可以临时暂停非强制文本，缩放停止后立即恢复完整富文本渲染。
4. 富文本标签的命中索引独立保留，不依赖富文本组件是否已经挂载。
5. 编辑中的富文本、当前选中节点和当前悬停节点必须加入强制保留集合。

实测结果：

- 确定性千节点场景在完成视口裁剪后，场景节点由三千三百四十一个进一步降至二千六百零五个，本阶段再减少约百分之二十二；相较最初的一万四千三百四十八个累计减少约百分之八十一点八。
- 早期百分之四十五固定阈值虽然能够进一步减少场景节点，但会在低比例下错误隐藏仍具备可读空间的大图形富文本，因此该策略已移除，不再作为当前性能结果。
- 七十五号真实单据在功能图百分之十六缩放比例下仍展示视口内完整文字，场景节点为四千六百六十六个；五秒静置采样平均帧率为五十五点九九，九十五分位帧间隔为十七点七毫秒，未出现长任务。
- 确定性场景的帧间隔采样受到并行页面加载和浏览器调度干扰，本阶段只将稳定的场景节点数量作为前后对比指标。

### 8.3 富文本内部结构与布局收口

富文本优化不能只把多个 Konva 节点机械合并成一个自定义绘制节点。节点合并虽然能够降低场景树遍历和命中画布成本，但如果仍在缩放期间为全部图形重复构造令牌、测量文本和计算换行，只会把节点遍历成本转移为自定义绘制和布局计算成本。因此富文本内部优化按照“结构减负、布局收口、缩放解耦、视觉合并”的顺序实施。

完整的现状分析、目标架构、缓存失效规则、编辑器策略、回归矩阵和发布方案见“富文本节点专项优化方案”章节。本节只保留总体路线和实施顺序。

#### 8.3.1 结构减负

实施状态：已完成。

当前只读富文本已经存在一个覆盖完整文本区域的命中矩形，同时每个片段还会创建片段分组、背景矩形、文本节点和独立命中矩形。第一步复用已有整体命中矩形，不再为每个片段创建独立命中节点，并移除没有独立变换意义的片段分组。

目标结构先收敛为：

```text
富文本分组
├── 整体命中矩形
├── 片段背景
└── 片段文本
```

具体约束：

1. 整体命中矩形只负责确认当前位置属于哪个图形的富文本区域，不直接判定具体标签。
2. 点击、悬停和双击统一将舞台坐标转换为富文本局部坐标，再根据布局片段解析标签、条件或普通文本。
3. 只有实际命中标签或条件时才阻止事件继续传播；命中普通文本和空白区域时保留图形、区域和连线的既有选择语义。
4. 选中框覆盖下的标签命中继续复用统一坐标解析入口，不重新引入舞台全量交集扫描。

实测结果：

- 七十五号真实单据在功能图百分之四十七完整文字模式下，场景节点由三千零十九个降至二千四百一十六个，本阶段减少约百分之二十；五秒静置采样平均帧率为五十六点七八，九十五分位帧间隔为十七点六毫秒，未出现长任务。
- 确定性千节点场景的场景节点由二千六百零五个降至二千五百二十三个；该场景只有每五个图形包含复杂富文本，因此结构减负收益低于全部图形均包含多个片段的真实单据。
- 确定性场景已验证标签悬停、点击选中和焦点高亮，普通文字视觉与结构减负前保持一致。

#### 8.3.2 控制器直接索引

实施状态：已完成。

删除片段命中节点后，不能让舞台指针事件退化为遍历全部富文本控制器。整体命中矩形应携带所属图形编号或稳定的富文本节点编号，注册表根据该编号直接获取控制器。

推荐在 Konva 节点属性中记录富文本所属图形编号，命中后直接执行映射查询：

```text
舞台单点命中
→ 读取富文本所属图形编号
→ 从控制器映射中直接获取控制器
→ 解析当前图形的布局片段
```

正常点击和悬停路径不得使用字符串前缀逐个匹配一千多个控制器。兼容旧节点编号的遍历逻辑只能作为迁移期间的临时兜底，并应记录触发次数，完成迁移后删除。

#### 8.3.3 只读布局单次计算

当前父级富文本组件和只读画布组件分别计算测量布局与渲染布局。只读状态下应由父级生成唯一的只读布局结果，并将同一份结果传递给视觉绘制、标签命中、标签操作按钮定位和选中覆盖层命中。

布局职责调整为：

```text
富文本父组件
├── 只读布局：只读绘制和全部坐标命中共同使用
└── 编辑测量布局：仅在编辑器打开时创建和更新
```

只读子组件不再独立调用布局函数。编辑测量布局在编辑器未打开时不得参与响应式依赖，避免一千个只读图形持续承担编辑器测量成本。

#### 8.3.4 几何布局与绘制状态分离

标签悬停、焦点和搜索高亮只改变颜色，不应触发文本测量、换行和片段坐标重建。富文本数据拆分为稳定几何布局和动态绘制状态：

```ts
interface RichTextGeometryLayout {
  contentHeight: number;
  segments: RichTextGeometrySegment[];
}

interface RichTextPaintState {
  hoveredTagId: string;
  focusedTagIds: Set<string>;
  searchedTagIds: Set<string>;
}
```

稳定几何布局只在富文本内容、图形尺寸、字体样式或有效布局比例变化时重新计算。悬停、焦点和搜索变化只更新当前富文本的动态绘制状态，不重新执行文本测量和换行。

#### 8.3.5 缩放热路径解耦

标签内边距、间距和圆角当前依赖连续缩放比例，导致每次滚轮缩放都可能使全部富文本布局失效。实施时按以下方案择一，并通过同一份大图数据比较视觉和性能：

1. 优先评估移除连续比例依赖，让标签尺寸随舞台自然缩放。该方案能够彻底阻断缩放对富文本布局的连续触发，但需要确认小比例下的可读性。
2. 如果必须维持标签最小视觉尺寸，采用比例分档，只有跨越档位时重新布局，不响应每一个缩放比例变化。
3. 如果比例分档仍不能满足视觉要求，缩放期间冻结稳定布局比例，缩放结束后再刷新布局；结束后的刷新需要分批执行，不能在同一帧同步重算全部富文本。

缩放期间富文本悬停本身已经暂停，因此冻结布局不会造成交互命中风险。缩放结束后必须保证视觉布局和命中布局同时切换，不能出现显示位置与点击位置不一致。

#### 8.3.6 合并视觉节点

实施状态：已完成收益评估，当前不实施。

完成结构减负、布局收口和缩放解耦后，曾评估使用自定义 Konva Shape 合并片段视觉节点。目标结构为：

```text
富文本分组
├── 稳定视觉节点，不参与命中
├── 动态高亮节点，不参与命中
└── 整体命中矩形
```

稳定视觉节点绘制普通文本、标签基础样式和条件操作符；动态高亮节点只绘制悬停、焦点和搜索状态。这样标签状态变化只重绘当前富文本的动态部分，不重建整份布局。

实验评估中，确定性千节点场景的场景节点由二千五百二十二个降至二千一百个，但平均帧率和九十五分位帧间隔没有改善；七十五号真实单据功能图在百分之十六比例下的场景节点基本不变。该方案还需要重新实现并长期维护字体基线、长标签换行、条件操作符、文字背景和装饰线视觉，风险与真实收益不成比例，因此撤回实验代码并保留现有绘制路径。

若未来出现新的性能证据需要重新评估，自定义绘制仍须通过功能开关与现有多节点绘制进行对比，并同时记录场景树遍历、命中画布、绘制循环和文本绘制耗时，不能只比较节点数量。

#### 8.3.7 富文本统一语义命中

现有仅返回标签的坐标解析接口扩展为统一富文本片段命中，能够区分标签、条件和普通文本，并转换为画布统一命中结果：

```ts
type RichTextPointHit =
  | { kind: 'tag'; shapeId: string; tagId: string }
  | { kind: 'condition'; shapeId: string; conditionUid: string; part: 'left' | 'operator' | 'right' }
  | { kind: 'text'; shapeId: string }
  | null;
```

该入口供普通画布、选中覆盖层、区域覆盖层、悬停、点击和双击共同复用。单个图形的片段较多时，可以在布局生成阶段同时构建按行索引，命中时先根据纵坐标定位行，再根据横坐标定位片段；任何情况下都只能查询当前命中图形的布局，不得扫描全部富文本布局。

#### 8.3.8 分步实施与回归范围

实施顺序：

1. 移除片段分组和片段命中矩形，复用整体命中矩形并建立控制器直接索引。
2. 收口只读布局，编辑测量布局改为按需计算。
3. 分离几何布局与动态绘制状态，阻断高亮引起的布局重算。
4. 移除连续缩放依赖或引入比例分档，验证缩放结束后的布局刷新策略。
5. 在性能开关下引入稳定视觉节点和动态高亮节点，确认收益后再替换现有多节点视觉实现。

每一步都需要验证普通标签悬停与点击、条件双击、选中图形标签、选中区域内部标签、区域空白拖拽、连线选择、搜索高亮、焦点高亮、编辑器进入退出和缩放后的命中位置。

### 8.4 拆分静态层与交互层

将当前画布进一步拆分为以下图层：

1. 背景层。
2. 静态图形层。
3. 富文本层。
4. 选中层。
5. 临时交互层。

平移和缩放期间只变更舞台变换，避免 Vue 重新更新整棵图形组件树。静态图层缓存暂不直接恢复；如果重新引入缓存，必须采用空闲预热、缓存就绪后再启用，并且缓存未准备好时不能阻塞当前交互。

### 8.5 继续收敛命中解析服务

当前命中逻辑已经完成主要入口统一，但仍存在多种命中来源和局部语义判断：普通画布会解析当前节点及祖先，选中覆盖层会读取图层单点命中，区域覆盖层会扫描区域后代做几何命中，富文本控制器会解析标签节点，部分兜底路径仍然依赖全舞台交集。因此需要继续收敛入口，避免新增组件再次自行遍历节点或执行全量命中扫描。

#### 统一命中职责

新增或完善统一命中解析服务，负责获取命中对象和构造标准结果，不直接修改选区、不启动拖拽、不打开编辑器。业务动作继续由画布工具、选中覆盖层和富文本交互模块分别执行。

统一命中服务负责：

1. 从事件目标及其祖先节点解析业务编号。
2. 从指定图层读取当前位置的单点命中节点。
3. 根据当前区域或视口空间索引查询候选图形和连线。
4. 解析富文本标签、条件和普通文本命中。
5. 按统一优先级构造和排序候选结果。
6. 仅在前述路径无法确定结果且业务确实需要时，执行全舞台交集兜底。

覆盖层模块负责：

1. 判断命中对象是否属于当前覆盖层所有者。
2. 过滤允许透传的内部图形、连线和富文本对象。
3. 决定区域拖拽、内部图形拖拽和选中框拖拽意图。
4. 将标准命中结果转换为具体的选中、拖拽或编辑动作。

富文本模块负责：

1. 维护富文本节点编号到控制器的索引。
2. 根据标签节点或坐标解析标签编号及标签数据。
3. 维护悬停、点击和编辑状态。

命中解析服务不应包含上述业务动作，避免命中扫描和交互状态再次耦合。

统一顺序如下：

```text
事件目标及祖先节点
→ 当前图层单点命中
→ 当前区域或视口空间索引
→ 富文本标签索引
→ 全舞台交集兜底
```

#### 统一命中结果

所有命中入口最终返回统一结构，至少包含以下字段：

```ts
type CanvasHitResult =
  | {
      kind: 'shape' | 'line';
      id: string;
      source: 'event-target' | 'layer-point' | 'spatial-index' | 'stage-intersections';
      confidence: 'exact' | 'geometric' | 'fallback';
    }
  | {
      kind: 'rich-text-tag' | 'rich-text-condition' | 'rich-text-text';
      shapeId: string;
      tagId?: string;
      conditionUid?: string;
      source: 'event-target' | 'layer-point' | 'spatial-index' | 'stage-intersections';
      confidence: 'exact' | 'geometric' | 'fallback';
    }
  | { kind: 'none'; source: 'empty' | 'stage-intersections' };
```

实际实现可以根据现有领域类型调整字段名称，但必须保留目标类型、业务编号、命中来源和命中置信度，便于性能日志区分快速路径和兜底路径。

#### 命中来源规则

1. `event-target`：事件目标本身或祖先已经携带业务编号时直接使用，不重新扫描舞台。
2. `layer-point`：选中覆盖层位于舞台上方时，排除覆盖层后按图层从上到下读取单点命中。
3. `spatial-index`：事件发生在区域或视口范围内时，只在对应空间索引候选中进行几何判断。
4. 富文本命中：优先使用富文本节点编号索引；节点未挂载时使用独立标签空间索引。
5. `stage-intersections`：仅当命中对象存在遮挡、优先级无法判断或业务需要完整候选集合时使用，并记录触发原因。

其中，区域空白处必须在单点命中和局部空间索引确认无候选后直接返回 `none`，不得为了确认空白再次执行全舞台交集扫描。

#### 优先级与降级约束

命中优先级应由统一模块维护，建议顺序为：

```text
富文本标签或条件
→ 内部可选图形
→ 连线
→ 区域本体
→ 普通文本或装饰节点
→ none
```

覆盖层透传时还需要叠加所有者关系、层级深度和绘制顺序，不能由各个组件自行实现一套排序规则。

全舞台交集只允许作为明确的兜底路径使用，并记录触发原因和耗时，便于后续继续消除异常扫描。任何新命中逻辑都必须复用统一服务，不应在组件中直接调用 `getAllIntersections()`、遍历全部图形或重复解析富文本控制器。

### 8.6 建立可量化性能指标

后续每次优化都使用同一份一千个以上节点的图形数据，在相同浏览器和缩放比例下进行对比，重点记录：

- 缩放单帧耗时。
- 可见节点数量和实际挂载节点数量。
- 富文本挂载数量。
- 富文本 Konva 节点总数及平均每个图形的富文本节点数。
- 富文本布局函数和文本测量函数每秒调用次数。
- Konva 绘制耗时。
- Vue 组件更新耗时。
- `selected-overlay-pointerdown` 耗时。
- 命中解析来源和耗时。
- 是否触发全舞台交集扫描。

验收目标：

- 缩放单帧脚本耗时控制在 16 毫秒以内。
- 连续缩放不再出现 50 毫秒以上的连续 `requestAnimationFrame` 长任务。
- 区域空白、节点、连线和标签点击不触发全舞台交集扫描。
- 缩放过程中富文本组件数量随视口变化，而不是始终等于全量节点数量。
- 普通指针移动的富文本处理耗时控制在 2 毫秒以内，标签按下处理控制在 16 毫秒以内。
- 缩放期间不因连续比例变化重复执行全部富文本布局。
- 富文本控制器解析不出现全量遍历，单个富文本最终稳定在约三个 Konva 节点。
- 平移、缩放、选择、标签点击和协作状态保持现有行为。

### 8.7 当前实施状态与后续边界

#### 已完成项

1. 已完成命中入口约束、全量扫描监控、富文本结构减负、控制器直接索引和统一命中结果。
2. 已完成只读布局收口、几何布局与动态绘制状态分离，以及连续缩放期间的富文本降载。
3. 已完成视口裁剪、空间索引、富文本按视口虚拟化和强制保留集合。
4. 已完成透明基础文字节点清理，并以确定性场景和真实大图场景完成节点数量验证。
5. 已确认普通文本、标签和条件统一使用只读令牌路径；当前没有第二套普通文本快速路径。

#### 明确不实施项

1. 不实施富文本视觉节点合并。该方案已完成收益与风险评估，当前收益不足以抵消视觉维护成本。
2. 不按固定缩放比例隐藏富文本。低比例下仍可能存在足够大的可读图形，内容可见性应由视口和强制保留规则决定。
3. 不恢复同步主图层缓存。缓存只有在首帧、权限和失效策略均有明确收益证据时才重新评估。

#### 后续可选项

1. 继续收口少量命中兜底路径，但不得重新引入全量控制器遍历或全舞台扫描。
2. 只有真实性能证据明确时，才评估静态层、富文本层和交互层的进一步拆分。
3. 后续性能对比应固定浏览器会话、视口尺寸和交互序列；在此之前不把单次帧率波动当作新的优化结论。

当前不建议继续投入编号响应式、同步静态缓存或单纯增加动画帧节流；这些方向已经验证收益有限，或者会引入首帧体验问题。

## 9. 富文本节点专项优化方案

### 9.1 优化目标与边界

富文本专项优化面向一千个以上图形的平移、缩放、标签悬停、标签点击和双击编辑场景。目标不是单独压缩某一个事件处理函数，而是同时控制组件数量、Konva 节点数量、布局计算次数、命中范围和编辑器挂载成本。

核心目标：

1. 普通平移不触发只读富文本布局和页面矩形测量。
2. 连续缩放不为每一个比例变化重新计算全部富文本换行和标签尺寸。
3. 标签悬停和高亮只更新当前富文本的绘制状态，不重新计算几何布局。
4. 单个富文本从按片段创建多个分组、文本、背景和命中节点，逐步收敛为稳定视觉节点、动态高亮节点和统一命中节点。
5. 标签、条件和普通文本命中只查询当前图形的布局，不遍历全部控制器、不扫描全部图形、不调用全舞台交集确认空白。
6. 视口外富文本最终不挂载只读渲染组件，同时保留必要的业务数据和编辑能力。
7. 双击编辑只初始化当前目标的编辑器，不使全部图形响应选区或编辑状态变化。

本阶段不直接恢复主图层缓存，不使用同步 `Layer.cache()` 或节点缓存解决富文本绘制问题。缓存方案必须独立验证首帧、失效频率和权限场景，不能成为本专项优化的前置条件。

### 9.2 当前实现链路

当前图形富文本的主要链路如下：

```text
ShapeRenderer
├── 读取图形和视觉状态
├── 构建富文本位置与样式配置
└── CanvasShapeRichText
    ├── 从图形数据读取富文本内容
    ├── 构建只读令牌
    ├── 计算内容高度和测量布局
    ├── CanvasShapeRichTextReadonlyCanvas
    │   ├── 接收父组件生成的只读布局
    │   ├── 为每个片段创建视觉节点，并复用整体命中矩形
    │   └── 注册只读画布控制器
    └── 编辑时 Teleport HTML 容器并初始化 Quill
```

### 9.2.1 业务图形与真实 Konva 节点映射

业务图形数据、Vue 渲染组件和 Konva 场景节点不是一一对应关系：

1. `Shape` 业务对象只保存在图形状态仓库中，本身不是 Konva 节点。
2. 一个普通图形由 `ShapeRenderer` 组件编排，通常生成一个外层 `Konva.Group` 和一个主体节点；主体节点根据图形类型为矩形、椭圆、多边形线或图片。
3. `ShapeRenderer`、`CanvasShapeRichText` 等 Vue 组件本身不计入场景节点。只有模板中的 `v-group`、`v-rect`、`v-text`、`v-image`、`v-line` 等元素会生成真实 Konva 节点。
4. 富文本进入详细渲染范围后，在图形组下增加只读富文本组、一个整体透明命中矩形，以及按片段生成的背景和文字节点。普通文本、标签和条件均走同一套只读令牌布局；当前不再额外挂载外层基础文字节点。
5. 富文本编辑时，只读富文本组不显示，Konva 中仅保留编辑占位矩形，实际编辑内容由画布外的网页编辑器承载。
6. 区域、连线和选区分别由区域组、连线组、选区图层生成节点；区域子图形在主图层中与区域平级渲染，不嵌套在区域 Konva 组内。
7. 场景节点统计还包括舞台、图层、区域标题、连线文字、控制点、选区和预览节点，但不包括业务对象、Vue 组件、富文本控制器注册表和网页编辑器节点。因此业务图形数量不能直接等同于 Konva 场景节点数量。

节点标识通过图形编号建立映射：主体节点使用图形编号加主体后缀，富文本只读组使用富文本编号加只读画布后缀，整体命中矩形使用只读命中后缀。命中解析器先从当前节点及祖先节点恢复业务编号，富文本悬停和点击再通过只读画布控制器索引解析到具体标签或条件。

#### 节点存在与监听边界

节点是否存在、是否绘制和是否参与命中是三件不同的事情：

1. 图形级视口裁剪由主图层根据视口及三百二十像素缓冲区查询图形、区域和连线；视口外普通图形不会挂载渲染组件，因此没有外层组、主体节点或富文本节点。当前选中图形和连线会加入强制保留集合。
2. 富文本级视口裁剪使用视口及九十六像素文字缓冲区。图形主体仍然保留，但 `renderRichText` 为假时只读富文本组件不挂载；选中、文本高亮和富文本标签高亮目标会强制保留。连续缩放期间，非强制富文本暂停详细渲染，缩放结束后恢复。
3. 主图层在平移、缩放和拖拽期间会暂时关闭 `listening`，这只会停止该层的命中处理，不会从场景树移除已有节点，也不会自动停止绘制。真正减少节点数量依赖 `v-if` 控制组件或组的挂载。
4. 富文本控制器注册表、业务图形对象和编辑器网页节点不属于 Konva 场景节点。只读画布组被卸载后，控制器也必须同步失活或注销，避免把“没有视觉节点”和“没有交互索引”混为一谈。

相关实现范围：

- `ui/components/shapes/renderers/ShapeRenderer.vue`
- `ui/components/shapes/elements/CanvasShapeRichText.vue`
- `ui/components/shapes/elements/CanvasShapeRichTextReadonlyCanvas.vue`
- `ui/components/shapes/renderers/shape-rich-text-readonly.ts`
- `ui/components/shapes/renderers/use-shape-rich-text-interaction.ts`
- `ui/components/shapes/shape-rich-text-registry.ts`
- `ui/canvas/hit/canvas-hit-resolver.ts`
- `ui/canvas/selection/SelectionLayer.vue`

### 9.3 当前主要成本

#### 9.3.1 组件全量挂载

视口内图形在进入详细文字范围时才挂载富文本组件；视口外图形和详细范围外图形只保留主体节点。即使普通文本不包含标签，也会在详细范围内通过只读令牌路径渲染，因此仍需通过视口虚拟化控制富文本组件总量。

#### 9.3.2 布局重复计算

父组件使用测量布局计算内容高度，只读子组件又根据令牌、尺寸和样式计算一次渲染布局。只读状态下两份布局处理的是高度相关的同一内容，却分别执行文本测量、换行和片段构造。

#### 9.3.3 连续缩放使布局失效

历史实现中标签内边距、间距和圆角依赖当前缩放比例。连续滚轮输入会不断改变比例，从而使全部已挂载富文本的布局计算失效。即使舞台变换已经在动画帧内合并，组件侧仍可能承担大规模响应式更新。

当前只读布局已改为使用组件创建时捕获的初始布局比例，缩放期间不再订阅视口比例，也不再依赖缩放交互状态。舞台变换负责整体缩放；只有内容、尺寸或影响几何的样式变化才会重新生成布局。

#### 9.3.4 片段节点数量放大

当前每个片段包含外层分组、文本节点、可选背景节点和独立命中节点，同时富文本整体还存在一个命中矩形。片段越多，场景树遍历、Vue 虚拟节点同步、Konva 命中画布绘制和销毁成本越高。

#### 9.3.5 高亮状态污染几何布局

悬停、焦点和搜索状态进入只读令牌，令牌再参与布局构造。虽然高亮通常只改变颜色，但状态变化可能导致整份令牌和片段配置更新。

#### 9.3.6 命中入口并存

普通画布、舞台级富文本监听、选中图形覆盖层和区域覆盖层都需要识别富文本。虽然当前已经建立共享命中内核和控制器编号索引，但片段命中节点删除后，如果整体命中节点不能直接定位控制器，仍可能退化为控制器遍历。

#### 9.3.7 编辑器初始化成本

Quill 当前按编辑状态创建，方向正确，但打开编辑器仍会经历 Teleport 挂载、DOM 创建、内容写入、样式同步、焦点设置和后续测量。编辑状态如果与全局选区、高亮或缩放状态耦合，会放大为大量无关组件更新。

### 9.4 目标数据流与职责边界

目标链路拆分为内容快照、稳定几何、动态绘制、命中索引和编辑会话五部分：

```text
富文本内容快照
        ↓
稳定几何布局
├── 片段位置和尺寸
├── 标签与条件语义
├── 内容高度
└── 按行命中索引
        ↓
只读绘制
├── 稳定视觉内容
└── 动态高亮内容
        ↓
统一命中节点
        ↓
富文本语义命中结果

编辑请求
→ 单一编辑会话
→ 当前目标编辑器
→ 保存后回写图形数据
```

各类数据的响应式边界如下：

| 数据类别     | 包含内容                             | 允许触发布局重算   | 允许触发当前节点重绘 |
| ------------ | ------------------------------------ | ------------------ | -------------------- |
| 内容数据     | 文本、标签、条件                     | 是                 | 是                   |
| 几何样式     | 宽高、字体、字号、对齐、稳定比例档位 | 是                 | 是                   |
| 视口位置     | 舞台横纵坐标                         | 否                 | 否                   |
| 连续缩放比例 | 动画帧内临时比例                     | 否                 | 由舞台变换负责       |
| 高亮状态     | 悬停、焦点、搜索                     | 否                 | 仅当前富文本动态层   |
| 选区状态     | 当前图形是否选中                     | 否                 | 仅操作浮层或选中层   |
| 编辑状态     | 当前编辑目标                         | 仅当前目标按需测量 | 仅当前目标           |

### 9.5 稳定几何布局设计

#### 9.5.1 单一布局结果

只读状态由父级生成唯一布局，视觉绘制、坐标命中、标签操作按钮定位和选中覆盖层全部使用同一对象：

```ts
interface RichTextGeometryLayout {
  contentHeight: number;
  segments: RichTextGeometrySegment[];
  rows: RichTextGeometryRow[];
}
```

只读子组件不再独立调用布局函数。编辑器关闭时不创建编辑测量布局；编辑器打开后，才根据当前编辑内容生成编辑专用测量结果。

#### 9.5.2 布局输入

稳定布局只允许依赖：

1. 富文本内容版本或标准化内容摘要。
2. 文本区域宽度和高度。
3. 字体、字号、加粗、斜体、下划线和删除线。
4. 水平与垂直对齐方式。
5. 文本颜色以外真正影响几何的样式。
6. 初始布局比例；若后续产品要求保持屏幕像素尺寸，再单独引入比例档位。

不得纳入布局键：

- 舞台横纵坐标。
- HTML 覆盖层页面位置。
- 当前选区数组。
- 悬停标签编号。
- 焦点和搜索高亮集合。
- 临时平移和连续缩放状态。
- 标签操作按钮是否显示。

#### 9.5.3 布局复用与失效

第一步优先在单个富文本组件内部复用布局，避免立即引入全局无限缓存。只有真实性能数据表明重复内容较多时，再考虑有容量上限的共享布局缓存。

布局失效规则：

```text
内容变化                 → 失效
图形文本区域尺寸变化     → 失效
影响几何的字体样式变化   → 失效
初始布局比例             → 仅在组件创建时确定
缩放过程中的视口比例变化 → 不失效
平移                     → 不失效
缩放结束后的视口比例变化 → 不失效
悬停、选中、高亮         → 不失效
页面覆盖层位置变化       → 不失效
```

共享缓存如后续启用，必须限制容量，并在图形删除、字体资源变化和布局规则版本变化时清理。缓存键不能序列化完整响应式对象，应使用稳定内容摘要和必要的标量字段。

### 9.6 缩放策略

缩放与富文本布局解耦按以下优先级验证：

#### 9.6.1 自然缩放

优先验证标签内边距、间距和圆角使用舞台坐标，由 Stage transform 自然缩放。该方案下连续缩放不会使布局失效，收益最大。

适用前提：低比例下标签仍满足产品可读性和视觉要求。

当前实现采用该策略的第一步：只读布局使用创建时的初始比例，后续缩放只变换舞台，不触发富文本布局响应式更新。这样可以直接消除一次缩放内约三百个富文本实例的布局级联；代价是标签内边距等几何尺寸不再随新的视口比例重新校正，需要通过真实大图验证低比例下的可读性。

#### 9.6.2 比例分档

如果必须保持一定的屏幕视觉尺寸，将连续比例映射为少量稳定档位。只有跨档时重新布局，同一档位内完全复用布局。

档位阈值需要通过真实大图和常用缩放范围确定，不能把每个小数比例映射为独立档位。

#### 9.6.3 交互期间冻结

如果自然缩放和比例分档仍不能满足需求，连续缩放期间使用上一次稳定布局，缩放结束后再更新目标布局。结束刷新应按可见优先级和帧预算分批执行：

```text
编辑目标
→ 当前选中和悬停图形
→ 视口内图形
→ 缓冲区图形
→ 其余图形
```

缩放期间悬停同步已暂停，因此冻结期间不执行标签交互。缩放结束后视觉布局和命中布局必须原子切换，禁止出现显示位置和点击位置不一致。

### 9.7 只读节点结构优化

#### 9.7.1 普通文本快速路径（未采用）

实施状态：已完成收益与风险评估，当前不采用独立普通文本节点路径。以下内容保留为历史方案记录。

当富文本内容不包含标签和条件，并且现有普通文本节点能够完整表达其样式时，不挂载富文本只读画布，直接使用普通 `v-text`。编辑控制器可以继续按需提供，但不创建只读片段节点和只读命中控制器。

启用前需要验证换行、对齐、文本填充、下划线、删除线和溢出裁剪与现有视觉一致。不满足条件的内容继续走完整富文本路径。

当前实现统一由只读令牌布局承载普通文本、标签和条件。增量数据为空但存在普通文本时，由令牌构建器生成普通文字令牌；内容为空时不创建只读视觉节点。

#### 9.7.2 移除片段分组与片段命中节点

第一批结构改动复用现有整体命中矩形，删除每个片段的空分组和独立命中矩形。片段暂时保留背景与文本视觉节点，从而先验证坐标命中语义，不同时改写绘制实现。

阶段目标结构：

```text
富文本分组
├── 整体命中矩形
├── 片段背景节点
└── 片段文本节点
```

#### 9.7.3 合并视觉节点

前述改动稳定后，再通过功能开关验证最终结构：

```text
富文本分组
├── 稳定视觉 Shape，listening=false
├── 动态高亮 Shape，listening=false
└── 整体命中 Rect，listening=true
```

稳定视觉节点负责普通文本、标签基础样式和条件操作符；动态高亮节点只负责悬停、焦点和搜索效果。视觉节点不参与命中画布，避免自定义绘制内容重复生成复杂 hit graph。

自定义 Shape 的绘制函数必须保持稳定，不能在每次 Vue 更新时创建新的函数和完整配置对象。布局变化时更新节点持有的布局引用并请求批量绘制，高亮变化时只更新当前富文本的动态节点。

不为稳定视觉节点调用同步缓存。是否进一步使用离屏位图必须作为独立实验，并满足缓存异步准备、失败可降级和首帧不阻塞条件。

### 9.8 几何状态与绘制状态分离

富文本令牌分为语义令牌和绘制状态。语义令牌包含文本、标签、条件和稳定编号；绘制状态包含悬停、焦点和搜索集合。

高亮更新链路调整为：

```text
高亮状态变化
→ 定位受影响图形
→ 更新当前富文本绘制状态
→ 重绘当前动态高亮节点
```

不得重新执行：

- 富文本内容标准化。
- 文本宽度测量。
- 换行计算。
- 内容高度计算。
- 全部富文本组件的高亮同步。

如果搜索高亮一次影响多个图形，只更新实际包含目标标签的图形集合，并按动画帧合并绘制请求。

### 9.9 统一命中与控制器索引

#### 9.9.1 整体命中节点职责

整体命中节点只提供所属图形信息。节点应通过稳定属性或可直接解析的编号携带 `shapeId`，舞台命中后直接从 `readonlyCanvasRegistry` 获取控制器。

正常路径：

```text
layer.getIntersection(point)
→ 读取命中节点的 shapeId
→ Map 获取控制器
→ 舞台坐标转换为富文本局部坐标
→ 查询当前布局行和片段
```

禁止在普通 `pointermove`、`pointerdown`、`click` 和 `dblclick` 路径遍历控制器注册表。旧编号兼容遍历应增加性能计数，迁移完成后删除。

#### 9.9.2 统一语义结果

富文本坐标解析返回：

```ts
type RichTextPointHit =
  | { kind: 'tag'; shapeId: string; tagId: string }
  | {
      kind: 'condition';
      shapeId: string;
      conditionUid: string;
      part: 'left' | 'operator' | 'right';
    }
  | { kind: 'text'; shapeId: string }
  | null;
```

再由统一画布命中内核转换为 `rich-text-tag`、`rich-text-condition` 或 `rich-text-text`。普通画布、选中覆盖层、区域覆盖层、悬停、点击和双击不得自行实现另一套片段判断。

#### 9.9.3 事件传播规则

1. 精确命中标签时执行标签动作并停止重复画布兜底。
2. 精确命中条件时保留条件双击和标签点击语义。
3. 命中普通文本时按当前图形选择和编辑规则处理。
4. 命中富文本区域空白时不得吞掉图形、区域或连线事件。
5. 选中覆盖层位于上方时使用当前坐标解析，不调用全舞台交集。

#### 9.9.4 片段空间索引

布局生成阶段同时按文本行组织片段。命中先根据纵坐标定位行，再根据横坐标定位片段。单个图形片段很少时可以使用短数组顺序查找，但接口必须只接收当前图形布局，不能接受全量图形集合。

### 9.10 视口虚拟化与低细节预案

富文本内部减负解决单个已挂载组件的成本，视口虚拟化解决组件总量问题，两者需要同时实施。

渲染集合分为：

```text
强制保留集合
├── 当前编辑目标
├── 当前选中图形
├── 当前悬停图形
└── 正在执行富文本拖放的目标

可见集合
├── 视口内图形
└── 视口缓冲区图形
```

只有两个集合的并集挂载完整只读富文本。视口外图形保留领域数据和必要索引，不保留 Vue 富文本组件和 Konva 片段节点。

低缩放比例下曾规划采用分级显示：

1. 正常比例显示完整文本、标签和条件。
2. 中低比例显示简化普通文本或截断摘要，不创建标签交互节点。
3. 极低比例只显示图形轮廓或标题占位。

当前不启用上述分级显示，不设置固定缩放阈值。低细节模式会改变可见内容和交互能力，后续只有在产品规则明确图形屏幕尺寸、图形类型和可读性条件后才能重新评估，不能仅根据全局缩放比例隐藏富文本。

### 9.11 编辑器优化

#### 9.11.1 当前阶段

保持 Quill 按需创建，但进一步收窄更新范围：

1. 只有当前编辑目标挂载 HTML 编辑器。
2. 编辑器打开前不计算编辑测量布局。
3. 编辑器样式同步只在目标内容、目标尺寸、字体样式或稳定缩放状态变化时执行。
4. 焦点设置合并到一次动画帧，不重复调用聚焦、选择和样式同步。
5. 保存前比较标准化内容，内容未变化时不写回图形状态和事务记录。

非被动 `touchstart` 提示来自编辑器内部需要阻止默认滚动的监听器，不能为了消除控制台提示直接改为被动监听。应以实际处理耗时和编辑器挂载火焰图判断是否需要处理。

#### 9.11.2 后续共享编辑器

如果按需创建仍然无法满足双击进入编辑的性能目标，再将编辑器提升为画布级单一实例：

```text
编辑请求
→ 设置目标图形和定位信息
→ 单一 Quill 实例加载目标内容
→ 编辑完成
→ 回写目标图形
→ 清空编辑会话
```

共享编辑器需要解决编辑目标切换、未保存内容、图形删除、协作远端更新、撤销重做、标签拖放和条件弹窗之间的会话边界，因此不与只读节点合并同时实施。

### 9.12 分阶段实施计划

#### 阶段一：建立基线和普通文本快速路径

1. 记录富文本组件数量、Konva 节点数量、片段数量和布局调用次数。
2. 记录缩放期间布局函数、文本测量和组件更新耗时。
3. 对满足条件的普通文本使用普通文本节点，不挂载只读富文本画布。

#### 阶段二：结构减负和直接命中

1. 删除片段分组和片段命中节点。
2. 复用整体命中矩形。
3. 建立整体命中节点到控制器的常数时间索引。
4. 统一标签、条件和普通文本坐标命中。

#### 阶段三：布局收口和缩放解耦

1. 父子组件复用唯一只读布局。
2. 编辑测量布局改为编辑期间按需创建。
3. 分离稳定几何和动态高亮状态。
4. 已优先落地自然缩放的初始比例方案；只有视觉验收不通过时，才评估比例分档或交互冻结。

#### 阶段四：视觉节点合并

1. 在功能开关下增加稳定视觉 Shape 和动态高亮 Shape。
2. 对比现有多节点绘制和自定义绘制的真实耗时。
3. 达到验收指标且视觉回归通过后再删除旧视觉路径。

#### 阶段五：视口虚拟化

1. 接入视口空间索引和缓冲区。
2. 只挂载可见集合与强制保留集合中的完整富文本。
3. 缩放落稳后恢复视口内全部富文本，不设置固定比例隐藏规则。
4. 处理视口进出、选中、悬停和编辑时的稳定切换。

#### 阶段六：编辑器实例复用评估

1. 重新测量双击进入编辑和退出保存耗时。
2. 仅在按需创建仍超出目标时实施画布级共享编辑器。

每个阶段独立提交、独立验证、可单独回退，不将结构减负、绘制替换、虚拟化和编辑器重构合并为一次大改动。

### 9.13 性能埋点与验收指标

需要新增或保留以下统计：

- 当前挂载的富文本组件数量。
- 普通文本只读令牌数量。
- 富文本片段总数。
- 富文本相关 Konva 节点总数。
- 单个富文本平均节点数和最大节点数。
- 只读布局计算次数、总耗时和最大耗时。
- 文本测量次数。
- 缩放期间布局失效次数。
- 富文本控制器直接索引命中次数和兼容遍历次数。
- 标签、条件和普通文本坐标命中耗时。
- 编辑器挂载、内容写入、样式同步和聚焦耗时。

目标指标：

1. 平移期间只读布局计算次数为零。
2. 同一比例档位内连续缩放不触发全部富文本布局。
3. 普通指针移动的富文本处理耗时小于 2 毫秒。
4. 标签按下和点击处理耗时小于 16 毫秒。
5. 正常命中路径的控制器兼容遍历次数为零。
6. 最终完整富文本稳定在约三个 Konva 节点，普通文本只保留普通文本节点。
7. 连续缩放不再产生由富文本布局引起的 50 毫秒以上动画帧长任务。
8. 双击编辑器打开时间需要单独记录基线；完成当前阶段后仍超过 100 毫秒时，再评估共享编辑器。

### 9.15 风险与降级策略

1. 删除片段命中节点后可能改变事件传播。保留旧路径开关，逐项验证标签、条件、图形、区域和连线行为。
2. 自定义 Shape 可能降低节点遍历成本但增加每次绘制循环。只有真实性能数据优于旧实现时才切换默认路径。
3. 比例分档可能在跨档时产生轻微跳变。需要设置合理阈值和滞回范围，避免在边界反复切换。
4. 视口虚拟化可能导致节点进出闪烁。使用缓冲区、稳定编号和强制保留集合降低抖动。
5. 普通文本快速路径已决定不采用；当前普通文本统一走只读令牌路径，避免维护两套换行、对齐和装饰线规则。
6. 共享编辑器会增加会话复杂度。只有当前按需实例仍无法达标时实施，并保留原编辑器路径直至协作和保存语义完成验证。
7. 所有新路径都不得依赖同步图层缓存；功能开关关闭后必须能够恢复当前稳定实现。

### 9.16 完成判定

本节保留专项最初的完成判定。由于视觉节点合并已明确不实施，当前是否完成应以第 8.7 节的实施状态与后续边界为准，自定义绘制不再是当前交付前提。

富文本专项优化在满足以下条件后视为完成：

1. 普通文本、标签和条件统一由只读令牌路径渲染，编辑状态按需切换到网页编辑器。
2. 只读富文本只有一份稳定几何布局，编辑布局按需创建。
3. 平移、高亮和同一比例档位内缩放不会使几何布局失效。
4. 富文本命中使用当前图形布局和控制器直接索引，不出现全量控制器或全舞台扫描。
5. 完整富文本节点数量达到目标；如未来重新评估自定义绘制，仍须经过性能和视觉双重验证。
6. 视口外富文本能够卸载，选中、悬停和编辑目标保持稳定。
7. 所有回归矩阵场景通过，性能指标在同一份一千节点数据上达到目标。
8. 文档、性能数据、测试结果和最终启用策略同步更新。
   如果完全抛开现有实现，我会把整套拖拽设计成一个“小型几何编译器”：

> 输入一次拖拽意图，经过主移动、区域约束、后代传播、连线投影几个纯计算阶段，生成唯一的移动计划。预览和最终提交消费同一份计划。

核心是“一次规划、两种消费”：

```text
拖拽意图
   ↓
不可变画布快照
   ↓
主图形移动
   ↓
区域副作用求解
   ↓
后代位移传播
   ↓
连线几何投影
   ↓
CanvasMovePlan
   ├─ 拖拽预览
   └─ 最终提交
```

## 一、统一输入：MoveIntent

UI 不再告诉领域层应该移动子节点、是否扫描区域连线，也不再传 `MoveStrategy`。

所有入口统一归一成一个意图：

```ts
interface MoveIntent {
  sessionId: string;
  baseRevision: number;

  rootShapeIds: string[];
  delta: Point;

  source: 'pointer' | 'selection-overlay' | 'region-header';
}
```

无论是：

- 单图形拖拽
- 多选拖拽
- 区域拖拽
- 区域标题拖拽
- 选中框拖拽

最终都只是“哪些根图形移动了多少”。

`source` 只用于交互日志，不参与领域规则。是否移动后代、是否触发扩容，由图形类型、关系和图类型规则决定。

## 二、拖拽开始时建立一次快照

拖拽过程中不再反复从响应式 Store 查询图形、关系和连线。

```ts
interface MoveSnapshot {
  revision: number;

  shapesById: Map<string, Shape>;
  linesById: Map<string, Line>;

  parentByChildId: Map<string, string>;
  childrenByParentId: Map<string, string[]>;
  linesByShapeId: Map<string, string[]>;

  regions: Region[];
  regionSpatialIndex: RegionSpatialIndex;
}
```

快照在 `pointerdown/dragstart` 时构建一次。

后续每帧只传入新 `delta`：

```ts
const plan = planCanvasMove(snapshot, {
  ...intent,
  delta: latestDelta,
});
```

这样可以消除拖拽期间的：

- 关系数组反复过滤
- 全量连线扫描
- 区域数组反复构建 Map
- 响应式 Store 深层读取
- 状态写入后再次读取

## 三、规划器采用分阶段管线

### 第一阶段：主图形移动

只计算用户明确拖动的对象。

```ts
interface PrimaryMoveResult {
  directMoves: Map<string, Point>;
}
```

这一阶段不关心：

- 区域是否需要扩容
- 是否推挤其他区域
- 子图形是否跟随
- 连线如何变化

例如多选 300 个节点，只生成 300 个直接目标位置。

区域作为根图形被拖动时，这里也只记录区域的目标位置，不移动其子节点。

### 第二阶段：区域副作用

区域副作用消费主移动结果，但不会反向修改主移动意图。

```ts
interface RegionEffectResult {
  regionBounds: Map<string, RectBounds>;
  regionTranslations: Map<string, Point>;
  expandedRegionIds: Set<string>;
  pushedRegionIds: Set<string>;
  status: 'ready' | 'blocked';
}
```

内部统一处理两种区域变化来源：

#### 节点移动引起的扩容

```text
移动节点按父区域分组
→ 计算节点目标包围盒
→ 检查是否越过区域内容边界
→ 生成区域扩容请求
```

没有越界时立即退出，不进入碰撞和推挤计算。

#### 区域直接移动或扩容引起的推挤

所有区域变化先转换成统一请求：

```ts
interface RegionBoundsRequest {
  regionId: string;
  requestedBounds: RectBounds;
  cause: 'direct-move' | 'content-expansion';
}
```

然后交给同一个区域约束求解器：

```ts
resolveRegionLayout(snapshot, requests);
```

这样不再存在“区域直接拖拽一套推挤、节点扩容又一套推挤”。

### 第三阶段：后代移动传播

等区域最终位置确定后，再移动区域后代。

```ts
interface PropagatedMoveResult {
  inheritedMoves: Map<string, Point>;
}
```

规则明确为：

- 区域扩容只修改区域边界，不移动已有子图形。
- 区域整体移动时，全部后代继承相同位移。
- 区域被推挤时，全部后代继承推挤位移。
- 显式移动的图形先应用自身位移，再叠加祖先区域的整体位移。
- 同一个图形最终只能得到一个合成后的位置。

如果支持嵌套区域，按区域树从父到子传播，不使用零散递归回调。

### 第四阶段：连线投影

连线只根据所有图形的最终位置计算一次。

```ts
interface ShapeGeometryChange {
  shapeId: string;
  before: RectBounds;
  after: RectBounds;
  delta: Point;
}
```

先从 `linesByShapeId` 找到候选连线，不扫描全部连线。

每条连线只进入一次判断：

```text
开始端和结束端位移相同
  → 整条连线平移

只有一个端点移动
  → 更新该端点并调整线型

两个端点位移不同
  → 更新两端并重新投影

两个端点都没移动
  → 跳过
```

这样不再需要：

- 区域内部连线专门扫描
- 批量移动后再次同步端点
- 提交后再次收集受影响连线

## 四、唯一输出：CanvasMovePlan

```ts
interface CanvasMovePlan {
  status: 'ready' | 'blocked' | 'unchanged';
  reason?: string;

  baseRevision: number;
  intent: MoveIntent;

  shapeUpdates: Array<{
    shapeId: string;
    before: Partial<Shape>;
    after: Partial<Shape>;
    causes: Array<'direct' | 'region-expansion' | 'region-move' | 'region-push' | 'ancestor-translation'>;
  }>;

  lineUpdates: Array<{
    lineId: string;
    before: Partial<Line>;
    after: Partial<Line>;
    mode: 'translate' | 'reconnect';
  }>;

  effects: {
    expandedRegionIds: string[];
    pushedRegionIds: string[];
  };

  affectedTarget: {
    shapeIds: string[];
    lineIds: string[];
  };
}
```

这份计划必须满足几个不变量：

- 一个图形最多只有一条最终更新。
- 一条连线最多只有一条最终更新。
- 所有区域最终不重叠。
- 移动后节点仍被父区域包含。
- 同一输入和快照必然产生同一结果。
- 预览结果和最终提交结果完全一致。

## 五、拖拽过程只做预览

拖拽会话只保存：

```ts
interface MoveSession {
  intent: MoveIntent;
  snapshot: MoveSnapshot;
  latestDelta: Point;
  latestPlan: CanvasMovePlan | null;
  frameId: number | null;
}
```

`pointermove/dragmove` 只更新 `latestDelta`，每帧最多规划一次：

```ts
function updateDrag(delta: Point) {
  session.latestDelta = delta;

  if (session.frameId !== null) return;

  session.frameId = requestAnimationFrame(() => {
    session.latestPlan = planCanvasMove(session.snapshot, {
      ...session.intent,
      delta: session.latestDelta,
    });

    preview.apply(session.latestPlan);
  });
}
```

预览层只维护轻量 Map：

```ts
shapeGeometryById: Map<string, Partial<Shape>>;
lineGeometryById: Map<string, Partial<Line>>;
```

然后由以下组件读取最终显示几何：

- 图形渲染器
- 区域渲染器
- 连线渲染器
- 选择框
- resize handle
- hover/hit-test 层

拖拽期间不执行：

- 领域 Store 写入
- 事务
- 快照记录
- 包含关系刷新
- 已提交区域失效检查
- 完整协作变更广播

## 六、最终提交只有一次

```ts
function commitMove(plan: CanvasMovePlan) {
  verifyPermission(plan);
  verifyOrRebaseRevision(plan);

  return runTransaction(() => {
    batchWriteShapes(plan.shapeUpdates);
    batchWriteLines(plan.lineUpdates);

    refreshContainmentOnce(plan.affectedTarget);
    invalidateSubmittedRegionsOnce(plan.affectedTarget);
    recordUndoSnapshotOnce(plan);
    publishCollaborationCommitOnce(plan);
  });
}
```

提交阶段不重新走另一套移动算法。

如果画布在拖拽期间被远端修改：

```text
当前版本等于快照版本
  → 直接提交计划

当前版本发生变化
  → 基于最新快照和原始意图重新规划一次
  → 重新规划成功则提交
  → 规则冲突则取消并提示
```

这能避免长时间拖拽覆盖协作方更新。

## 七、区域推挤求解器设计

现有逐个区域全量扫描的方式需要改成确定性的约束求解。

我会采用：

1. 使用网格空间索引查询碰撞候选。
2. 将直接拖动区域标记为锚点。
3. 按移动方向建立推挤队列。
4. 每次只查询当前区域目标边界附近的区域。
5. 相同优先级按区域稳定编号排序，保证结果确定。
6. 每个区域在一次求解中只保留一个最终边界。
7. 最后只校验发生变化的区域及其邻居。

复杂度从反复全量扫描，收敛为接近：

```text
发生变化的区域数 × 平均邻居数
```

区域数量很大时，这是能否保持拖拽流畅的关键。

## 八、协作设计

实时协作消息只发送：

```ts
{
  kind: ('move-preview', sessionId, baseRevision, rootShapeIds, delta);
}
```

远端使用同一个纯规划器生成预览。

最终只发送一次：

```ts
{
  kind: ('move-commit', operationId, baseRevision, shapeUpdates, lineUpdates);
}
```

如果双方版本不一致，实时阶段可以退化为只展示根图形虚线框，最终以提交结果为准。

## 九、文件控制在四个核心文件

逻辑分层不等于大量拆文件。我会控制为：

```text
ui/canvas/selection/shape-drag-interaction.ts
  拖拽入口适配

ui/canvas/selection/move-session.ts
  会话、逐帧调度、预览状态

application/commands/shape/move-shapes.ts
  移动管线、计划结构、最终提交

domain/services/region-layout-service.ts
  区域扩容、推挤和空间约束
```

连线几何继续使用现有 `line-service.ts`，不额外增加一层包装。

`move-shapes.ts` 内部按函数阶段组织：

```ts
planPrimaryMoves();
planRegionEffects();
propagateRegionTranslations();
mergeShapeGeometry();
planLineGeometry();
planCanvasMove();
applyCanvasMovePlan();
executeMove();
```

只有文件明显失控后，才提取独立模块。

## 十、落地方式

为保证现有功能不丢，我不会一次性替换，而会这样迁移：

1. 给现有行为补齐特征测试，包括单图形、多选、区域扩容、连续推挤、两类连线、推挤失败和取消。
2. 新规划器以“影子模式”运行，只比较新旧结果，不参与渲染和写入。
3. 结果稳定后让预览层消费新计划，提交仍走旧链路。
4. 再切换最终提交到新计划。
5. 删除旧的实时写入、区域推挤分支和重复连线同步。

我认为这套设计最重要的不是用了什么模式，而是三个硬约束：

> 拖拽帧不写领域状态；区域副作用只有一个求解器；连线只基于最终图形几何计算一次。

只要守住这三点，复杂度、性能和后续维护成本都会明显下降。

## 10. 图形移动链路拆分方案

### 10.1 背景

当前图形拖拽、区域拖拽、连线同步、区域扩容和区域推挤集中在同一条移动链路里，导致一次拖拽既承担主图形位移，又承担区域规则、子项继承、连线重算和提交状态写回。对于一千节点以上的画布，这种耦合会把一次简单拖拽放大成多段重复扫描和多次副作用写入。

为了保留现有功能，需要把移动流程拆成两条逻辑链路：

1. 主图形移动链路，只负责“谁在移动、移动多少、最终目标在哪里”。
2. 区域副作用链路，只负责“哪些区域需要扩容、哪些区域需要被推挤、哪些子项需要继承位移”。

连线同步不再作为移动入口里的穿插步骤，而是作为两条链路汇合后的统一结果处理步骤。

### 10.2 设计目标

1. 保留单图形、多图形、区域和选中框拖拽的现有行为。
2. 让主图形移动不再直接依赖区域扩容、区域推挤和连线同步的实现细节。
3. 让区域副作用可以单独演进，不影响主图形位移的基本语义。
4. 让预览态和提交态共用同一套计划逻辑，避免 live 和 commit 出现两套结果。
5. 让所有最终写入只发生一次，不在拖拽过程中反复写正式状态。

### 10.3 推荐的链路分层

推荐把当前移动流程拆成以下阶段：

```text
拖拽意图
→ 统一移动上下文
→ 主图形移动计划
→ 区域副作用计划
→ 位移合并
→ 连线投影
→ 预览或提交
```

#### 10.3.1 统一移动上下文

统一把所有拖拽入口收口为同一种移动意图，至少包含：

1. 本次拖拽的根目标集合。
2. 相对起点的总位移。
3. 触发来源，区分图形拖拽、区域拖拽、框选拖拽和选中框拖拽。
4. 当前快照版本。
5. 是否允许区域副作用。

这一层只负责标准化输入，不做区域判断和连线重算。

三类移动行为统一为“根目标集合 + 拖拽锚点 + 相对起点总位移”，具体映射如下：

| 移动行为     | 根目标集合       | 拖拽锚点                       | 后续规则                                                     |
| ------------ | ---------------- | ------------------------------ | ------------------------------------------------------------ |
| 单图形移动   | 当前图形         | 图形初始位置或指针按下位置     | 根据图类型和包含关系判断是否移动后代、是否触发父区域扩容     |
| 框选批量移动 | 当前所有选中图形 | 选中图形整体包围盒的初始位置   | 所有根图形先保持刚体位移，再按父区域分组计算扩容和推挤       |
| 区域移动     | 当前区域         | 区域初始位置或区域标题按下位置 | 先确定区域最终位置，再把位移传播给区域后代并计算相邻区域推挤 |

交互层统一通过同一套生命周期驱动移动会话：

```text
beginMove
→ updateMove
→ commitMove 或 cancelMove
```

三类入口只负责完成权限、命中、选区语义和拖拽锚点转换，不再分别维护区域扩容、区域推挤、连线同步和最终提交逻辑。需要保留的差异仅包括：

1. 单图形、选中包围盒和区域使用不同的拖拽锚点。
2. 图形、区域空白和区域标题具有不同的命中与准入规则。
3. 图形移动权限和区域移动权限分别在会话开始前校验。
4. 区域推挤无解时允许返回阻止结果，普通节点移动则按父区域扩容结果决定是否可继续。

这些差异只影响是否允许创建移动意图以及如何生成根目标集合，不进入后续移动计划、区域副作用、连线投影和提交管线。

#### 10.3.2 主图形移动计划

主图形移动计划只计算“直接被拖动对象”的目标位移：

1. 单图形拖拽只计算该图形自身的新位置。
2. 多选拖拽只计算直接选中的根对象，不提前把区域规则混进来。
3. 区域拖拽先按区域本体求出基础位移，再交给后续副作用链路处理子项和相邻区域。

这一步的产物应该是纯几何计划，不包含写入、副作用和事件发布。

#### 10.3.3 区域副作用计划

区域副作用计划消费主图形移动后的几何结果，单独处理以下内容：

1. 区域是否需要扩容以容纳直接移动目标。
2. 是否存在被直接推动的相邻区域。
3. 被推挤区域内部的子项是否需要继承区域位移。
4. 区域内部连线是否需要随所在区域一起平移。

这里的关键约束是：

1. 扩容只改变区域边界，不额外平移已经稳定的内部子项。
2. 被推挤区域的内部子项只继承区域位移，不重新参与主图形拖拽逻辑。
3. 区域自身的直接位移和区域推挤位移必须统一折算成最终目标，不能分别写入两次。

#### 10.3.4 位移合并

主图形移动和区域副作用都完成后，需要把所有对象的最终位移合并成一份结果。合并原则如下：

1. 直接拖动对象的位移优先作为基准。
2. 祖先区域带来的位移在基准上累加。
3. 被推挤区域的继承位移在基准上累加。
4. 任何对象都只保留一份最终位移，不保留重复来源的中间状态。

这一步的目标不是保留中间过程，而是得到一份可以直接预览和提交的最终几何结果。

#### 10.3.5 连线投影

连线同步放到位移合并之后统一计算，避免在主图形移动和区域副作用中各自计算一次。

建议规则如下：

1. 两端都随同一位移整体移动的连线，直接平移整条连线。
2. 只有一端受影响的连线，按端点重新投影。
3. 端点所属对象经过区域推挤后发生变化的，按最终对象位置重新计算。
4. 没有实际位移变化的连线不进入写入计划。

这样可以把连线从“移动过程中的穿插副作用”变成“最终几何结果的统一投影”。

### 10.4 执行模型

推荐把移动执行拆成 `preview` 和 `commit` 两个阶段，但两者共用同一套计划生成逻辑。

#### 10.4.1 预览阶段

预览阶段只更新临时状态：

1. 使用统一移动上下文生成计划。
2. 计算主图形移动、区域副作用和连线投影。
3. 只把最终结果写入预览态或交互态。
4. 不更新正式图形 Store，不发布正式事件。

#### 10.4.2 提交阶段

提交阶段只做一次正式写入：

1. 基于最后一次拖拽结果生成最终计划。
2. 合并区域扩容、区域推挤、图形移动和连线同步结果。
3. 一次性写入正式状态并发布统一结果。
4. 只在提交完成后更新选择状态、提交区域影响和后续协作同步。

### 10.5 推荐的模块边界

为了让链路真正拆开，建议保持以下职责边界：

1. 交互层只负责把鼠标和手势转成统一移动意图。
2. 计划层只负责计算主图形移动和区域副作用，不写正式状态。
3. 应用层只负责把最终计划一次性落到正式数据。
4. 领域层只保留区域推挤、包含关系和连线投影的纯规则。

对应到现有代码时，原则上不再让一个函数同时承担“算位移、改区域、同步连线、写正式状态、发事件”五种职责。

### 10.6 迁移顺序

建议按以下顺序落地：

1. 先把移动输入统一成单一意图，消除不同入口各自拼装计划的情况。
2. 把主图形位移和区域副作用拆成两个独立计划，先保证结果和现有行为一致。
3. 再把连线同步移动到最终合并之后，避免重复扫描和重复写入。
4. 最后收敛预览和提交的共用路径，确保 live 和 commit 只存在生命周期差异，不存在结果差异。

### 10.7 验收标准

1. 单图形拖拽、多图形拖拽、区域拖拽和选中框拖拽保持现有可见行为。
2. 区域扩容和区域推挤的结果与现有实现一致。
3. 连线在主图形移动和区域副作用下都能正确同步。
4. 预览态和提交态来自同一份计划，不再出现两套分支逻辑。
5. 拖拽过程中不再出现“主移动写一次、区域副作用再写一次、连线同步再写一次”的重复落库模式。
6. 后续如果要优化区域推挤算法，只需要替换区域副作用计划，不需要改动主图形移动入口。
