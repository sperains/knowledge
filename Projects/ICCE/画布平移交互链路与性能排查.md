# ICCE 画布平移交互链路与性能排查

## 1. 背景

ICCE 画布在大规模节点场景下进行平移时，曾出现“卡卡的”、拖动不跟手的问题。排查重点集中在：

1. `useStageEvents` 是否对高频指针事件进行了不合适的节流或重复处理。
2. 中键平移、手形工具平移和触摸板平移是否使用了不同的更新路径。
3. 平移过程中是否同时驱动了 Konva 舞台和 Vue/Pinia 响应式状态。
4. 平移结束后的视口保存、协作事件和交互状态是否保持原有语义。

相关实现位于：

- `src/views/icce/ui/canvas/useStageEvents.ts`
- `src/views/icce/ui/viewport/viewport-gesture-interaction.ts`
- `src/views/icce/ui/components/canvas/DfdCanvas.vue`
- `src/views/icce/ui/viewport/viewport-store.ts`
- `src/views/icce/ui/viewport/viewport-runtime.ts`

## 2. 核心结论

画布平移的高频阶段不应反复写入响应式视口状态。Konva 已经能够直接完成舞台位置更新和绘制，平移过程中再次写入 Pinia 会触发 Vue 组件更新以及 `vue-konva` 的配置同步，形成重复工作。

推荐的平移模型是：

```text
输入事件
  → 合并到下一帧
  → 直接修改 Konva Stage
  → 平移结束后一次性回写 viewportStore
  → 发布平移完成事件
```

这样可以把高频表现态和低频持久化状态分开：

- 表现态：`stage.position()`，追求当前帧立即响应。
- 提交态：`viewportStore`、用户配置保存和协作事件，手势结束后统一提交。

## 3. 三种平移完整链路

### 3.1 鼠标中键平移

入口是 `DfdCanvas` 的 `pointerdown`、`pointermove`、`pointerup` 和 `pointerleave` 事件。

```text
pointerdown(button=1)
  → useStageEvents.handlePointerDown
  → interactionStore.reset
  → viewportGestures.startMiddlePan
  → startPointerPan('middle')
  → 记录起始指针位置
  → 创建 panning 会话
  → 设置抓取光标

pointermove
  → useStageEvents.handlePointerMove
  → preventDefault
  → moveMiddlePan
  → movePointerPan
  → 保存最新指针位置
  → requestAnimationFrame

动画帧
  → flushPointerPanFrame
  → 计算当前指针与上一帧指针的增量
  → 直接修改 stage.position

pointerup(button=1) 或 pointerleave
  → endMiddlePan(true)
  → 刷新尚未执行的最后一帧
  → 读取舞台最终位置
  → 一次性写回 viewportStore
  → 发布 source='drag' 的 viewport-panned 事件
  → 恢复光标并清理 panning 会话
```

中键平移过去的高频路径是：

```text
pointermove
  → viewportController.pan
  → viewportStore.setPosition
  → Vue 更新
  → vue-konva 同步舞台配置
```

这会让每个指针事件都进入响应式更新链路，是中键平移卡顿的主要风险。

当前实现已经改为与手形工具共用动画帧路径。

### 3.2 hand 工具平移

入口是当前工具为 `hand` 时的左键 `pointerdown`。

```text
pointerdown(button=0 且当前工具为 hand)
  → startHandPan
  → interactionStore.reset
  → startPointerPan('hand')
  → 记录起始指针位置
  → 创建 panning 会话
  → 设置抓取光标

pointermove
  → preventDefault
  → moveHandPan
  → 复用 movePointerPan
  → requestAnimationFrame

动画帧
  → 复用 flushPointerPanFrame
  → 直接修改 stage.position

pointerup 或 pointerleave
  → endHandPan(true)
  → 复用 endPointerPan
  → 最终位置一次性写回 viewportStore
  → 发布 source='drag' 的 viewport-panned 事件
  → 清理会话
```

中键平移和 hand 工具平移现在只在入口和工具标识上有区别，核心移动逻辑统一使用：

- `startPointerPan`
- `movePointerPan`
- `flushPointerPanFrame`
- `endPointerPan`

当前只保留一个 `pointerPanKind` 表示 `middle` 或 `hand`，不再分别维护两套激活状态。

### 3.3 触摸板平移

触摸板平移不经过 `pointermove`，而是通过 `wheel` 事件识别。

判定条件主要是：

- 没有 `ctrlKey`。
- `deltaMode` 为像素模式。
- 存在横向增量，或纵向增量不超过 `24px`。
- 小数像素纵向增量仍视为平移，不能误判为缩放。

链路如下：

```text
wheel
  → handleWheel
  → 判定为触摸板平移
  → queueWheelGesture({ kind: 'pan', deltaX, deltaY })
  → 合并同一动画帧内的滚动增量
  → requestAnimationFrame

动画帧
  → flushWheelFrame
  → 读取当前 stage.position
  → 根据 deltaX / deltaY 计算下一位置
  → 直接修改 stage.position
  → 创建 panning 会话
  → 启动约 200ms 的结束计时器

约 200ms 没有新的触摸板事件
  → viewportStore.setPosition(最终位置)
  → 发布 source='wheel' 的 viewport-panned 事件
  → 结束视口交互状态
```

触摸板与中键、hand 的结束方式不同：

- 中键和 hand 依靠 `pointerup` 或 `pointerleave` 结束。
- 触摸板没有明确的松开事件，依靠一段时间没有新的 `wheel` 输入判断结束。

三者的高频移动阶段仍然遵循同一原则：直接修改舞台，结束后再写入响应式视口。

## 4. 为什么不能只使用普通 pointermove 节流

`useStageEvents` 中的普通 `pointermove` 节流只服务于画布工具的指针逻辑，例如选择、绘制和连接目标判断。

平移分支在入口处提前返回：

```text
中键平移 / hand 平移
  → 直接进入 viewportGestures
  → 不进入普通工具节流
```

因此平移需要在视口交互控制器内部使用动画帧合并，而不能依赖外层的普通工具节流。

原因是两者职责不同：

- 工具节流：限制业务命中、预览和选择逻辑的执行频率。
- 平移动画帧：保证舞台变换与浏览器绘制帧同步。

## 5. 响应式状态与舞台状态的边界

### 平移进行中

只更新：

```ts
stage.position(nextPosition)
```

避免更新：

```ts
viewportStore.setPosition(nextPosition)
viewportController.pan(nextPosition)
```

原因是舞台已经完成当前视觉变换，重复写入响应式状态会触发额外组件更新。

### 平移结束

统一执行：

```text
读取 stage.position
  → viewportStore.setPosition
  → 发布 viewport-panned
  → 由视口持久化监听器保存用户位置
```

平移结束时保存一次位置是正常的。

### 触摸板缩放的区别

滚轮缩放除了改变 `scale`，通常还会改变 `position`，以保持鼠标指针下的内容不跳动。因此缩放结束时保存 `position` 和 `shrink` 各一次是当前设计的预期行为。

## 6. 交互期间的其他性能开关

`MainLayer` 会根据交互状态关闭主图层命中检测：

```text
panning / scaling / dragging
  → layer.listening = false
```

这可以避免平移期间继续为大量图形执行命中处理。平移期间不应新增全舞台交集扫描、富文本页面矩形测量或大规模响应式状态更新。

无限网格虽然会随舞台位置重绘，但应保持在单个网格图形内部完成，避免为每条网格线创建大量响应式节点。

## 7. 当前实现与测试结论

当前已完成：

1. 中键平移改为动画帧直接更新舞台。
2. 中键平移与 hand 工具平移共用同一条指针平移链路。
3. 触摸板平移改为动画帧直接更新舞台，并在输入停止后回写视口。
4. 删除中键平移过程中逐事件调用响应式 `viewportController.pan` 的路径。
5. 使用 `pointerPanKind` 收敛中键与 hand 的激活状态。
6. 保留原有平移完成事件、光标、交互会话和视口保存语义。

- `src/views/icce/tests/ui/viewport/viewport-gesture-interaction.spec.ts`

## 8. 后续排查建议

如果统一链路后仍然感觉卡顿，应使用浏览器性能面板区分以下成本：

1. `flushPointerPanFrame` 或 `flushWheelFrame` 的脚本耗时。
2. Konva 场景树遍历和 Layer 绘制耗时。
3. 富文本绘制和文本测量耗时。
4. 页面布局、样式计算和 HTML 覆盖层定位耗时。
5. 是否仍有其他模块订阅视口状态并在平移期间触发响应式更新。

对于一千个以上节点的画布，后续优化方向应优先考虑：

- 视口裁剪和空间索引。
- 视口外富文本虚拟化。
- 静态层、交互层和选区层拆分。
- 低缩放比例下的低细节渲染。

不建议再次把高频舞台位置写入 Pinia，也不建议只增加固定时间节流来掩盖绘制和布局成本。
