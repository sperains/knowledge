# ICCE 图形缩放预览计划与单次提交方案

> 当前结论：区域与普通图形已统一采用“初始快照、纯计划预览、结束时单次提交”的缩放链路；移动与缩放共用几何快照、区域副作用和几何变更执行骨架。最终提交包含主图形、区域、后代图形和连线等实际影响范围，并通过正式操作同步回放。

> 事实来源：`jd_ipd` 工作区当前未提交代码及 2026-08-14 的完整 ICCE 测试回归。过程态远端目前仍只显示主目标的轻量边界或位移预览，区域扩容、邻域推挤和后代联动的实时远端完整投影属于待定增强项。

## 当前实施结论（2026-08-14）

本节是当前实现的权威摘要；后续第 1—10 节保留实施前的问题、候选方案和迁移记录，用于追溯，不再单独代表当前状态。

### 已落地的统一链路

- 移动和缩放开始时均建立不可变画布几何快照，并构建图形、连线、父子关系和连线关联索引。
- 移动与缩放领域服务均基于快照和用户意图生成纯计划，不读取或写入正式 Store。
- 计划显式返回图形更新、连线更新、区域扩容与推挤效果、实际影响范围及 `ready / blocked / unchanged` 状态。
- 本地过程只更新几何预览；结束时由应用层执行器在单一事务中应用完整计划、刷新必要包含关系并记录最终快照。
- 提交前会重新校验计划内图形是否仍存在；目标被并发删除或最终候选被阻塞时，整体中止，不落无关区域副作用。
- 区域手动扩展只改变区域边界，不按区域起点变化平移既有子图形；区域整体移动才传播到后代；子图形触发父区域扩容时，已有内容保持绝对位置，明确的区域推挤规则除外。

### 协作边界

- `interaction` 只承载移动、缩放等过程预览；过程消息不写正式 Store、不持久化，也不进入正式回放器。
- `OPERATION_SYNC` 只承载应用命令完成后的正式几何结果。区域扩容的最终父区域、后代和连线变化会随提交计划进入 `modify` 结果，远端通过正式回放器直接投影。
- 过程态 `commit / reset` 只负责清理远端预览，不替代正式提交，也不表达业务回滚。
- 当前实时远端预览仍只携带主缩放边界或移动总位移，尚未完整投影区域扩容、邻域推挤、后代和连线联动；这属于后续协议和远端渲染增强，不是当前提交回放缺陷。

### 当前代码职责

- 领域快照与索引：`src/views/icce/domain/services/canvas-geometry-snapshot.ts`
- 区域布局效果与推挤规则：`src/views/icce/domain/services/region-layout-service.ts`
- 移动与缩放纯计划：`src/views/icce/domain/services/move-service.ts`、`resize-service.ts`
- 移动与缩放计划执行：`src/views/icce/application/execution/geometry-mutation-executor.ts`
- 本地几何预览：`src/views/icce/ui/canvas/selection/geometry-preview.ts`

### 并发几何变更：当前问题与待实施方案

当前快照规划解决了过程态污染和单次提交问题，但仍存在一类并发缺口：远端移动区域内图形触发区域扩容并推挤邻域区域时，本地同时移动被推挤区域，双方最终提交后可能出现区域重叠。

问题不在于“谁先按下鼠标谁拥有最终结果”，而在于本地会话继续基于手势开始时的旧快照规划。远端正式提交会直接落入本地正式状态，但不会让活动中的移动或缩放会话重新建立快照；因此本地最终计划可能覆盖远端已经产生的区域扩容、推挤位移或连线变化。当前执行器只校验计划目标是否仍存在，尚未校验计划中的 `before` 几何是否仍与正式状态一致。

建议采用“提交顺序确定基础、后提交操作重基”的处理方式：

1. **远端正式几何变更标记活动会话**：回放器返回本次实际影响的图形、区域、连线和包含关系目标；若影响当前会话目标、父区域、邻域区域或碰撞上下文，则将本地会话标记为需要重规划。
2. **下一帧或提交前重建最新快照**：从正式状态重新生成画布几何快照，清理旧计划中的区域扩容和推挤效果；保留用户当前意图，而不是继续叠加旧位移。移动应根据“期望绝对位置与最新根图形位置”重新计算位移，缩放应保留当前候选的绝对边界，然后在最新快照上重新规划。
3. **提交前增加乐观冲突保护**：比较计划中每个图形和连线的 `before` 几何与当前正式状态；发现仍存在但已被远端改动的目标时，不应用陈旧的绝对坐标，优先重基并重试一次，无法得到可行计划时整体中止。
4. **以完整计划作为原子结果**：重规划成功后，主目标、区域扩容、邻域推挤、后代图形、连线和包含关系必须作为同一计划提交；阻塞时不落无关副作用，避免通过提交后补偿或事后消除重叠来掩盖冲突。

该策略不是简单的“先操作为主”：先提交的操作成为后续规划的最新基础，后提交的操作仍会保留用户当前意图并在新基础上重新计算；只有在新状态下确实无法满足区域约束时，后提交操作才会被阻塞并明确放弃。若要在多客户端和服务端之间提供绝对一致的最终保证，还需要服务端为正式操作提供基础版本或几何版本校验；客户端重基用于解决当前观察到的本地活动会话与远端回放交错问题。

#### 实施边界

- 本节是待实施方案，不代表当前代码已经具备并发重基或版本校验能力。
- 不通过延迟远端回放、提交后强制挪开重叠区域或重新执行一套独立业务规则解决问题，这些做法会改变操作顺序或产生不明确的归属。
- 预期改动集中在远端几何回放通知、移动/缩放会话重规划、几何执行器的 `before` 校验及并发场景测试，不需要重写区域扩容和推挤领域算法。

## 1. 背景（实施前历史记录）

ICCE 的区域图形和普通图形都通过选择覆盖层调整尺寸，但两者曾采用不同的协作流程：

- 普通图形通过轻量 `shape-resize` 过程消息展示远端预览，结束后同步正式结果；
- 区域图形在过程阶段持续广播真实图形变化，远端直接修改正式图形状态；
- 普通图形会进入缩放交互状态并处理 `start / update / commit / reset`，区域缺少相同的会话和异常收尾语义。

工作区当前调整已经将两类缩放收敛到同一协作生命周期：

- 区域和普通图形共享开始、实时更新、提交和重置流程；
- 两者都使用 `shape-resize` 过程消息；
- 本地实时更新都标记为缩放意图，协作层不再广播完整的过程图形数据；
- 远端只显示轻量边界预览，最终状态由正式提交快照落地；
- 区域继续保留子图形边界和区域重叠约束，普通图形继续保留父区域扩容及功能图包含关系刷新。

这解决了当前协作表现不一致的问题，但没有消除“缩放过程实时修改本地正式 Store”的结构复杂度。

## 2. 当前实现模型

当前缩放链路如下：

```text
指针移动
→ 根据手柄和初始边界计算候选边界
→ 应用区域或普通图形约束
→ 实时调用图形更新命令
→ 修改本地正式图形 Store
→ 触发父区域扩容、连线更新等关联变化
→ 缩放会话监听本地变更事件并收集影响范围
→ 协作层过滤缩放过程的完整图形广播
→ 另行发送轻量边界预览
→ 结束时从正式 Store 记录最终快照
```

当前模型的优点是本地渲染天然跟随正式 Store，改动范围较小；代价是过程态、正式状态、受影响对象收集和协作过滤彼此耦合。

### 2.1 实时正式状态写入

每次指针移动都会调用正式图形更新入口。普通图形可能同时触发父区域扩容和连线变化，区域则应用自身边界约束。

为了阻止过程帧进入正式协作回放，实时更新需要携带 `intent: resize` 和 `phase: live`；更新完成后还要重新读取实际落地边界，再发布过程预览。

### 2.2 受影响对象反向收集

实时更新产生关联副作用后，缩放会话通过订阅本地变更事件收集：

- 主图形；
- 自动扩容的父区域；
- 关联连线；
- 其他由更新链路触及的图形。

结束时再根据收集结果读取最终状态并记录快照。这属于“先改变状态，再观察改变结果”的模式。

### 2.3 双过程通道

本地实时更新会产生完整图形变更事件，同时缩放交互还会发送轻量边界消息。协作层需要显式过滤缩放的完整过程变更，才能避免远端重复渲染和正式状态抖动。

### 2.4 提交兜底

提交逻辑依赖过程阶段是否已经收集到目标。若没有产生有效过程更新，还需要在提交阶段补写最终边界、补记主图形并重新读取受影响范围。

### 2.5 取消语义受限

因为过程阶段已经修改正式 Store：

- 退出键当前只能按正常提交收尾，无法真正取消；
- 组件卸载需要提交未完成操作，避免留下未闭合状态；
- 开始新缩放前也需要先提交旧会话；
- 若要真正取消，必须额外保存并恢复完整状态。

### 2.6 多份会话状态

一次缩放同时涉及：

1. 指针缩放会话；
2. 本地交互 Store 中的缩放状态和操作标识；
3. 受影响对象收集会话；
4. 协作过程消息的会话标识。

开始、结束和异常清理需要同步维护这些状态。

## 3. 候选简化方案

候选方案把缩放改为与移动一致的“快照规划、过程预览、单次提交”模型：

```text
按下缩放手柄
→ 保存初始画布快照
→ 根据当前指针生成完整缩放计划
→ 将计划投影为本地预览
→ 广播轻量远端预览
→ 松手后重新计算最终计划
→ 应用命令一次性执行完整计划
→ 清理本地和远端预览
```

### 3.1 缩放意图

缩放意图只描述用户直接输入：

```ts
interface CanvasResizeIntent {
  shapeId: string;
  targetKind: 'region' | 'shape';
  handle: ResizeHandle;
  targetBounds: RectBounds;
}
```

### 3.2 缩放计划

规划器根据初始快照和缩放意图返回完整结果：

```ts
interface CanvasResizePlan {
  status: 'ready' | 'blocked' | 'unchanged';
  shapeUpdates: ShapeUpdate[];
  lineUpdates: LineUpdate[];
  effects: {
    expandedRegionIds: string[];
  };
  affectedTarget: {
    shapeIds: string[];
    lineIds: string[];
  };
  finalBounds: RectBounds;
}
```

具体字段以实现时的领域模型为准，关键约束是计划必须显式包含最终变化和完整影响范围，不能依赖事件总线反向推断。

### 3.3 单一缩放协调器

使用一份会话状态统一维护：

```ts
interface ActiveResizeSession {
  operationId: string;
  shapeId: string;
  targetKind: 'region' | 'shape';
  handle: ResizeHandle;
  snapshot: CanvasResizeSnapshot;
  initialBounds: RectBounds;
  latestBounds: RectBounds;
  latestPlan: CanvasResizePlan | null;
}
```

区域和普通图形的模板入口可以保留，但最终调用同一个协调器。两者只在规划规则上有差异，不再各自维护生命周期。

### 3.4 正式缩放命令

应用命令只接收已经完成准入和规划的最终计划，并在一次事务中：

1. 应用图形和区域更新；
2. 应用连线更新；
3. 刷新必要的包含关系；
4. 根据计划自带的影响范围记录快照；
5. 产生唯一一次正式协作结果。

界面层不再直接调用事务和快照接口，也不再补写遗漏目标。

## 4. 可移除或显著简化的内容

| 当前内容 | 当前存在原因 | 候选方案中的处理 |
| --- | --- | --- |
| 过程阶段实时修改正式图形 Store | 让本地图形自然跟随 Store 重绘 | 改为缩放计划预览，正式 Store 只在提交时更新一次 |
| 实时更新的 `intent: resize` 与 `phase: live` | 让协作层识别并过滤完整过程变更 | 过程不产生正式变更事件后，不再需要该特殊标记 |
| 缩放受影响对象收集模块 | 从实时更新及关联副作用中反向收集最终快照目标 | 影响范围由缩放计划直接返回，模块可整体移除 |
| 协作层过滤缩放实时变更 | 防止完整过程数据与轻量预览双重广播 | 从源头不产生完整过程广播，过滤分支可删除 |
| 提交阶段补写图形和补记目标 | 兼容没有产生过程更新的会话 | 最终计划明确返回 `ready / blocked / unchanged`，不再依赖过程写入 |
| 退出键和卸载时强制提交 | 正式 Store 已经被过程帧修改，无法直接丢弃 | 清除计划预览并发送 `reset`，实现真正取消 |
| 区域和普通图形两份底层缩放实例 | 两类目标曾维护不同生命周期 | 使用一个联合目标和一个缩放协调器 |
| 多处会话标识动态读取 | 指针、交互、影响范围和协作状态分别维护 | 在单一协调器开始时创建并稳定持有标识 |

## 5. 本地与远端 UI 表现

### 5.1 应保持不变的表现

若完整投影缩放计划，本地用户仍应实时看到：

- 主图形或区域边界连续变化；
- 父区域自动扩容；
- 连线端点和路径跟随；
- 选中框及八个缩放手柄跟随目标；
- 上下文工具栏、快捷新增等浮层定位正确；
- 区域标题及负责人信息跟随区域预览边界。

视觉效果不应退化为“只显示一个虚线框，松手后实体突然跳变”。

### 5.2 需要统一接入预览投影的界面

缩放预览不能只接入区域和普通图形渲染器，还必须覆盖：

- 图形渲染；
- 区域渲染；
- 连线渲染；
- 选择覆盖层；
- 上下文工具栏与快捷操作浮层；
- 所有依赖图形边界的定位查询。

建议在现有移动预览基础上收敛通用查询：

```ts
getInteractionPreviewShape(shape)
getInteractionPreviewLine(line)
getInteractionPreviewBounds(shapeId)
```

渲染层只读取正式状态叠加当前交互计划后的投影，不自行推导缩放规则。

### 5.3 有意改变的交互语义

- 退出键可以真正取消缩放并恢复开始前状态；
- 页面或组件卸载时只清理未完成预览，不强制保存；
- 区域边界扩展只改变区域边界，不隐式移动已有内容；
- 区域整体移动才移动区域及其子图形；
- 子图形触发父区域扩容时，只扩展父区域边界，已有内容保持绝对位置；
- 最终结果到达后再清理远端过程预览，避免视觉空档。

## 6. 区域语义边界

缩放规划必须明确区分三类行为：

### 6.1 手动调整区域边界

计划只包含区域自身的边界变化。向上或向左扩展时，子图形绝对坐标不变，不随区域起点变化整体平移。

### 6.2 移动整个区域

区域、后代图形及关联连线按照移动规划整体变化。这属于移动操作，不属于区域缩放。

### 6.3 子图形触发父区域扩容

计划包含父区域边界更新以及必要的连线结果，但不默认移动父区域中的其他图形。只有明确的区域推挤规则才能移动其他区域或图形。

## 7. 与现有架构决策的关系

- [[ADR/ADR-005-移动采用快照规划一次提交]] 已验证移动链路采用快照、计划和单次提交的可行性，本方案建议复用其模式，但不修改该 ADR 的适用范围。
- [[ADR/ADR-006-协作过程态与提交态分离]] 已要求过程帧不得写入正式 Store；当前缩放只保证远端不写正式 Store，候选方案进一步让本地过程态也只进入预览。
- [[ADR/ADR-012-ICCE图形尺寸约束与预览模式]] 要求预览和提交共享同一份尺寸规则；缩放规划器应复用现有领域约束，不在预览层复制最小尺寸或区域边界规则。

如果候选方案被确认实施，应评估是否新增“缩放采用快照规划一次提交”的 ADR，或扩展现有移动 ADR 为更通用的画布几何变换决策。在确认前，本方案保持 Draft。

## 8. 迁移建议

建议分阶段迁移，避免同时重写约束、协作和渲染：

1. 定义纯 `CanvasResizePlan`，先用特征测试锁定普通图形、区域约束、父区域扩容和连线结果；
2. 建立缩放预览映射，让图形、区域、连线和选择覆盖层都能消费计划；
3. 新增正式缩放应用命令，单次执行计划并记录完整快照；
4. 将指针过程切换为只更新计划预览，不写正式 Store；
5. 删除受影响对象反向收集模块、实时缩放协作过滤和提交兜底；
6. 将退出键和卸载行为改为真正取消，并补齐本地及远端预览清理；
7. 验证稳定后再决定是否将移动和缩放预览查询收敛为通用交互投影。

## 9. 验证范围

### 9.1 领域计划

- 普通图形八个手柄和最小尺寸约束；
- 区域子图形边界和区域重叠约束；
- 普通图形触发父区域向四个方向扩容；
- 区域向上、向左扩展时子图形绝对坐标不变；
- 用户图形等特殊尺寸规则；
- 关联连线和包含关系的完整影响范围；
- `ready / blocked / unchanged` 状态。

### 9.2 本地交互

- 实体、连线、手柄和浮层在拖动中保持同步；
- 退出键、工具切换、目标删除和组件卸载可以清理预览；
- 取消后正式 Store 与初始快照一致；
- 提交只产生一次正式业务变更。

### 9.3 协作

- `start / update / commit / reset` 生命周期完整；
- 过程阶段只发送轻量边界，不发送完整正式图形变化；
- 最终快照先到达，过程预览后清理；
- 区域和普通图形使用一致的远端表现；
- 丢帧、目标失效、离开和超时不残留预览。

## 10. 风险与待定事项

### 已知风险

- 完整计划预览需要覆盖图形、区域、连线、选择覆盖层和浮层定位，遗漏任一消费者都会出现视觉错位；
- 父区域扩容和连线规划必须与当前应用命令结果保持一致，否则预览和提交会跳变；
- 正式 Store 从逐帧更新改为单次提交后，提交瞬间的响应式重算峰值需要验证；
- 当前工作区实现尚未形成提交版本，归档中的实施状态需要在提交后复核。

### 待决策

- 是否正式采用快照规划和单次提交替代当前本地实时 Store 写入；
- 是否新增独立 ADR，还是扩展既有移动 ADR 的适用范围；
- 移动和缩放是否共享一套通用交互预览映射，还是只共享底层投影工具；
- 过程会话标识与正式操作标识是否继续分离，或由同一协调器创建但保持不同语义。
