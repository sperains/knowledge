空间索引
与画布裁剪

让大画布只为“附近、需要、正在交互”的内容付出渲染成本：空间索引负责快速找到候选，视口裁剪负责控制挂载规模，两者共同守住交互流畅度。

查得快 · 挂得少 · 不丢状态
为什么做坐标体系空间索引视口裁剪交互一致性验证与演进来源：ICCE 空间索引与画布裁剪设计方案
01

先分清：索引 ≠ 裁剪

大规模画布的问题不是“数据太多”这么简单，而是每次平移、缩放和选择都可能重复触发全量遍历、组件更新、绘制和命中监听。

空间索引

查得快

把无限画布切成网格，先找出可能相交的实体，再做精确矩形判断。

  • 输出候选编号
  • 减少全量遍历
  • 服务范围查询和对齐候选
视口裁剪

挂得少

只把当前视口附近的区域、图形和连线挂载到主渲染树，降低 Vue 与 Konva 的维护成本。

  • 输出当前渲染集合
  • 使用屏幕缓冲避免闪烁
  • 文本再使用更小窗口
强制保留

状态不丢

选中、搜索高亮、编辑中的目标即使暂时离开窗口，也必须继续存在于渲染集合。

  • 不裁剪业务数据
  • 不改变世界坐标
  • 不破坏交互会话

03

坐标体系：所有查询回到世界

业务实体和索引使用画布世界坐标，用户看到的是经过舞台位置与缩放变换后的屏幕坐标。屏幕缓冲要先换算成世界距离。

世界坐标 → 屏幕坐标
屏幕坐标 = 世界坐标 × scale + position 世界左边界 = -position.x / scale 世界上边界 = -position.y / scale 世界宽度 = viewport.width / scale 世界高度 = viewport.height / scale
不能直接拿屏幕像素矩形查询世界坐标索引；必须先调用视口范围换算。
缓冲换算

屏幕距离保持稳定

世界缓冲 = 屏幕缓冲像素 / max(abs(scale), 0.01)

缩放越小，同样的屏幕缓冲对应更大的世界范围；缩放越大，对应的世界缓冲越小。

关键边界 · 镜头不搬索引

平移和缩放为什么不更新空间索引？

空间索引记录的是实体在画布世界坐标中的位置；视口平移和缩放只改变观察方式，不改变实体的世界坐标和几何包围盒。

视口 position / scale 变化 → 换算新的世界可见范围 → 按缓冲区扩展查询范围 → 查询原有图形和连线索引 → 更新渲染集合
例子：实体始终位于世界坐标 x = 100。平移只会让屏幕位置变化，索引中的 x = 100 不变；缩放只会改变范围映射比例，也不应搬移索引条目。
04

空间索引：一张会移动的网格地图

均匀网格 · 只做候选过滤

三组数据，维护一条关系

entries实体编号 → 规范化包围盒
entryCells实体编号 → 它覆盖的网格键列表
cells网格键 → 实体编号集合
实体跨越多个单元时，查询先使用 Set 去重，再做精确相交判断。
单元坐标

负坐标也要正确

minCellX = floor(x / cellSize) maxCellX = floor((x + width) / cellSize) minCellY = floor(y / cellSize) maxCellY = floor((y + height) / cellSize)

使用 floor 而不是截断取整，避免负坐标被错误归入零号网格。

查询链路
查询矩形规范化边界
→
命中网格收集候选编号
→
Set 去重跨格实体只留一次
→
精确过滤返回实际相交项
05

视口裁剪：三层窗口，三种成本

范围屏幕缓冲负责什么为什么这样设
可见视口0用户当前看到的世界区域作为裁剪计算的基准
图形渲染窗口320 px区域、普通图形、连线是否挂载提前挂载，减少边缘闪烁
文字详细窗口96 px图形和连线是否挂载详细文字文字布局结构成本更高
窗口刷新策略

窗口内移动，先复用

视口每移动一点就重建集合，会抵消缓冲区收益。因此只有当视口接近渲染窗口边缘，或进入落稳阶段时才刷新。

安全边距 = 320 px × 35% / scale 视口进入安全边距 → 扩展渲染窗口 → 执行索引查询
连续缩放

文字不跟着抖

连续缩放期间暂缓文字窗口刷新，保留已经挂载的文字，让舞台自然缩放；落稳后再按最终比例恢复完整文字。

06

渲染集合：普通查询 + 强制保留

主图层装配顺序
视口快照提交态 / 实时态
→
索引查询图形 + 连线
→
强制合并选中 / 高亮 / 编辑
→
稳定排序区域 → 图形 → 连线
必须保留

交互目标优先

  • 当前选中图形和连线
  • 文本与富文本高亮目标
  • 正在编辑的图形或连线文字
  • 视口外定位操作的目标
边界原则

裁剪的是“挂载集合”，
不是业务实体；索引的是“边界”，
不是正式数据。

07

交互一致性：查询快，但语义不能变

框选

索引缩小候选

空间索引只负责快速找到候选，最终“相交”还是“完全包含”由既有几何规则决定。

智能对齐

预览不污染索引

移动预览不重建索引；只有移动计划提交、实体几何正式更新后，才同步新的包围盒。

命中检测

裁剪不替代命中内核

精确标签、轮廓、覆盖层和舞台命中仍使用共享几何命中逻辑，不能把“未挂载”当成“不存在”。

写入一致性
实体 Store 写入 + 空间索引 upsert / remove + 对应修订号递增 图形、连线、关联点数组和清空流程都必须遵守同一条链路。
08

验证、排查与后续演进

测试重点
空间索引跨网格去重、负坐标、更新、删除、清空、负宽高。
视口裁剪世界范围换算、缓冲扩展、边缘刷新、文本窗口、强制保留。
Store 集成图形、连线、正交渲染包围盒与索引同步。
浏览器场景千节点基线、稀疏大图、密集网格、连续平移缩放和视口外定位。
性能不要只看帧率

同时记录五类信号

  • 场景节点数量
  • 渲染落稳耗时
  • 索引候选数量
  • 窗口刷新次数
  • 长任务与富文本布局
后续边界

什么时候换更复杂的索引？

只有当均匀网格在真实数据中仍造成明显长任务，或大区域、长连线、极度倾斜的数据分布让候选数量持续失控时，才评估四叉树、矩形树或分层索引。替换实现时保持现有 upsert、remove、query、clear、size 契约。

当前结论：先用可复现基线调优参数，再决定是否更换结构；不要为了“看起来更高级”提前引入复杂索引。
