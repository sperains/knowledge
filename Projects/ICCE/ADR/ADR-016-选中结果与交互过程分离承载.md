# ADR-016 选中结果与交互过程分离承载

- 状态：Accepted
- 日期：2026-08-07
- 作者：
- 相关领域：ICCE 画布协作、实时协作消息协议

---

## 背景（Context）

ICCE 协作复用 WS `drag` 消息的 `handleData`，其中有两个可选字段：

- `interaction`：承载**过程态**交互——一次手势的 `start / update / commit / reset` 生命周期（框选轨迹、绘制草稿、resize 边界、移动总位移）。
- `selection`：承载**结果态**——选中集最终快照（`shapeIds` / `lineIds`）。

实现与评审中发现，协作消息中同时存在两类语义差异极大的数据，容易产生以下疑问与误用：

- 为什么选中结果（`selection`）不并入 `interaction` 一起发送？
- 点选（单击选中）没有拖拽过程，为什么也不走 `interaction`？
- 接收端对两类消息的处理、节流和清理规则完全不同，判断依据是什么？

需要明确「为什么区分」以及今后新增协作状态的判别标准，避免后续实现把两类语义混用。

约束来源：ADR-006 已确立「过程态与提交态分离」；`ICCE画布交互协作设计方案` 定义了两条链路（过程态进 `interaction`、选中态进 `selection`）。

## 考虑方案（Options）

### 方案 A：合并为单一 `interaction` 消息

选中结果快照作为 `interaction` 的一个 kind（如 `kind: 'selection-result'`）发送。

优点：

- 消息类型单一，字段少一个。
- 接收端统一走 interaction 消费路径。

缺点：

- `interaction` 是有状态机的过程消息：必须携带 `sessionId`、按 `start/update/commit/reset` 相位流转、`commit/reset` 清理、TTL 过期。选中结果没有这些语义（无生命周期、无 sessionId、覆盖式更新）。
- 强制套用会引入大量"伪相位"（如瞬时 start+commit），节流、合并、清理逻辑全部错位。
- 点选等无过程态操作没有手势会话，无法生成合法的 `sessionId`。

### 方案 B：合并为单一 `selection` 快照

框选过程（轨迹）也用 `selection` 字段表达。

优点：

- 只保留一种结果消息。

缺点：

- 框选过程有随时间变化的 `bounds` 轨迹，快照只能表达最终结果，远端看不到框选过程，协作体验退化。
- 高频过程帧（允许丢帧、只保留最新）与低频结果快照（必须可靠、空快照=清空）混在同一字段，节流与合并策略互相冲突。
- 无法表达 `reset`（取消时清除轨迹）与 `commit`（保留轨迹）的区分。

### 方案 C：结果态与过程态分字段承载（选定）

`handleData.selection`（结果态）与 `handleData.interaction`（过程态）平级、互不交叉。

优点：

- 语义边界清晰：过程态按状态机处理（sessionId + phase + TTL + commit/reset 清理），结果态按快照处理（覆盖式 + 空快照清空 + leave/断线清理）。
- 各自可以独立演进：给点选加协作语义只需扩展 `selection` 链路，不触碰 `interaction`。
- 判别标准简单可执行：「是否有过程态」。

缺点：

- 需要维护两套生命周期与清理逻辑。
- 消息结构多一个字段，新人需要先理解判别原则。

## 决策（Decision）

最终选择：**方案 C —— `selection`（结果态）与 `interaction`（过程态）分字段承载，平级且互不交叉。**

判别标准（「是否有过程态」）：

1. 有过程态（一次手势有 start/update/commit/reset 生命周期，远端需跟随过程渲染）→ 走 `interaction`，携带 `sessionId`，按相位状态机处理。
2. 无过程态（瞬时操作直接产出最终结果）→ 走 `selection` 快照，覆盖式更新，空快照表示清空。

原因：

1. 两类数据的生命周期、节流策略和清理方式本质不同，合并会使一类消息承担两套语义，状态机、合并与清理逻辑互相纠缠。
2. 点选（单击）无过程态，直接更新选中集后由 `selection-store` 监听经 `handleData.selection` 同步；框选有过程态，走 `interaction.selection` 供远端跟随轨迹。
3. 推论：`interaction.selection` 只服务「有过程态的选择方式」，当前唯一即框选，因此消息不再携带模式字段（`mode` 已移除），`additive` 保留表达 Ctrl/Cmd 追加/替换语义。

## 后果（Consequences）

### 正面影响

- 过程态可丢帧、可覆盖、只影响视觉预览；结果态低频、可靠、语义明确。
- 点选、框选、快捷键、树节点、对话框等所有本地选择入口统一由 `selection-store` 监听驱动 `selection` 快照，不新增选择事务或专门同步服务。
- 远端过程态与选中态分别存入 `remote-interaction-store` 与 `remote-selection-store`，互不干扰，均不进入正式回放器。

### 负面影响

- 两套状态、两套生命周期、两套清理逻辑需要分别维护。
- `handleData` 同时存在两个可选字段，理解成本略高，必须依赖判别原则。

### 后续约束

- 新增协作状态时，先按「是否有过程态」判别归属：有过程态进 `interaction`，无过程态进 `selection`，禁止混用。
- `interaction` 消息必须携带 `sessionId` 并遵循 `start/update/commit/reset` 状态机；`selection` 快照不携带 `sessionId`，覆盖式发送。
- 禁止把选中集结果快照写入 `interaction` 消息；禁止把框选轨迹写入 `selection` 快照。
- 空 `selection` 快照（`shapeIds` 与 `lineIds` 均为空）是「取消全部选中」的业务信号，不得丢弃。
- 远端不得根据 `additive` 或包围盒重新推导选中成员，选中结果以发送端快照为准。

## AI 指导原则

实现相关功能时：

- 必须：新增协作状态时先按「是否有过程态」判别归属——有过程态走 `interaction`（sessionId + 相位状态机），无过程态走 `selection` 快照。
- 必须：点选、快捷键、树节点等瞬时选择操作复用 `selection-store` 监听链路发送 `selection` 快照，不创建 interaction 消息。
- 必须：`interaction` 消息统一经 `emitInteractionSync` 发布，禁止绕过统一入口直接 emit 交互同步事件。
- 禁止：把选中集结果快照写入 `interaction` 消息，或把框选过程轨迹写入 `selection` 快照。
- 禁止：在 `selection` 消息中重新引入模式字段；新增选择方式时先确认它是否具备过程态。
- 优先：为 `interaction` 与 `selection` 的判别和生命周期补充注释，保持类型与文档一致。
