# ICCE 空间索引与画布裁剪设计方案

## 1. 文档定位

本文记录 ICCE 大规模画布中“空间索引”和“视口裁剪”的完整设计，包括问题背景、坐标模型、索引结构、裁剪窗口、增量维护、渲染强制保留规则、交互一致性、性能验证和后续演进边界。

本文既是当前实现的说明，也是后续维护和排查性能问题时的约束文档。涉及代码调整时，应先确认调整的是索引、裁剪窗口、渲染细节，还是命中和查询语义，避免把不同层次的优化混在一起。

## 2. 当前状态与结论

### 2.1 已落地能力

当前实现已经完成以下能力：

1. 图形和连线分别维护独立的均匀网格空间索引。
2. 图形创建、更新、删除和清空时增量维护图形索引。
3. 连线创建、更新、删除、按图形删除和清空时增量维护连线索引。
4. 主图层根据视口世界坐标和缓冲区查询可挂载的区域、普通图形和连线。
5. 视口平移时只在接近当前渲染窗口边缘时刷新查询窗口，窗口内部移动复用已有结果。
6. 视口外的富文本不挂载，只在文本窗口内保留详细文字渲染。
7. 连续缩放过程中暂缓非强制富文本查询，缩放落稳后恢复视口内完整文字。
8. 当前选中图形、当前选中连线、文本高亮目标和富文本高亮目标始终强制保留。
9. 范围选择和画布范围查询复用同一套空间索引入口，不再为每次查询遍历全部图形或连线。
10. 视口变换期间关闭主图层命中监听，减少平移和缩放过程中的命中开销。

### 2.2 当前明确不做的事情

当前方案不包含以下能力：

- 不裁剪业务数据。索引和裁剪只决定查询结果和界面挂载集合，不删除、不隐藏领域实体。
- 不改变图形的世界坐标。舞台平移和缩放只改变视口变换，实体位置仍保存在画布世界坐标中。
- 不使用富文本窗口代替图形窗口。图形是否挂载和图形内部文字是否详细渲染是两个独立判断。
- 不把索引结果当作最终绘制顺序。查询结果必须经过稳定排序和强制保留合并。
- 不在连续手势中逐事件重建全量渲染集合。实时视口只用于按需刷新裁剪窗口。
- 不为了追求更复杂的空间结构而提前引入四叉树、矩形树或动态树。当前均匀网格已满足现阶段的画布查询需求。

## 3. 问题背景

### 3.1 全量渲染的成本模型

大规模画布同时包含区域、普通图形、连线、连线控制点、连线文本和富文本节点。如果每次平移、缩放或选择都渲染全部实体，主线程成本大致为：

```text
全量实体数量
× 每个实体的组件创建与更新成本
× 视口手势触发频率
```

在一千个以上图形的场景中，真正位于当前视口附近的实体通常只占总量的一部分，但 Vue 组件树和 Konva 场景树仍然会为视口外实体付出挂载、响应式同步、绘制和命中监听成本。

### 3.2 只做裁剪仍然不够

如果每次视口变化都遍历全部图形，虽然可以减少最终挂载数量，但查询本身仍然是线性成本：

```text
每次视口变化 → 遍历全部图形 → 判断是否与视口相交 → 生成挂载集合
```

平移和触控板缩放都可能在短时间内产生大量视口更新，因此需要将“找出附近实体”从全量遍历优化为索引候选查询。

### 3.3 索引和裁剪解决不同问题

两者的职责必须分开：

| 能力 | 解决的问题 | 输出 |
| --- | --- | --- |
| 空间索引 | 如何快速找到可能与范围相交的实体 | 候选编号集合 |
| 精确相交判断 | 候选实体是否真的与查询矩形相交 | 精确实体编号集合 |
| 视口裁剪 | 哪些实体需要挂载到当前渲染树 | 当前渲染集合 |
| 富文本裁剪 | 当前挂载实体是否需要详细文字结构 | 详细文字编号集合 |
| 强制保留 | 哪些交互目标不能因视口位置被卸载 | 强制保留集合 |

索引不是裁剪，裁剪也不是删除。索引只提高范围查询效率，裁剪只控制运行时渲染规模。

## 4. 坐标体系

### 4.1 画布世界坐标

图形、区域和连线的几何数据全部使用画布世界坐标：

- 图形和区域使用 `x`、`y`、`width`、`height`。
- 连线使用点数组计算渲染包围盒。
- 正交连线先根据正交渲染模型得到实际绘制点，再计算包围盒。
- 业务数据和空间索引都不依赖浏览器窗口像素坐标。

### 4.2 舞台视口坐标

舞台使用位置和缩放把世界坐标映射到屏幕：

```text
屏幕坐标 = 世界坐标 × scale + position
```

因此从当前舞台位置和缩放反推可见的世界范围：

```text
世界左边界 = -position.x / scale
世界上边界 = -position.y / scale
世界宽度   = viewport.width / scale
世界高度   = viewport.height / scale
```

代码入口为 `resolveVisibleViewportBounds`。所有空间索引查询都应使用世界坐标范围，不能直接拿屏幕像素矩形查询世界坐标索引。

### 4.3 屏幕缓冲换算

缓冲区以屏幕像素定义，因为用户感知的是“提前多少像素加载”。但索引使用世界坐标，所以必须除以当前缩放比例：

```text
世界缓冲距离 = 屏幕缓冲像素 / max(abs(scale), 0.01)
```

缩放越小，同样的屏幕缓冲对应越大的世界范围；缩放越大，对应的世界缓冲越小。这样可以让缓冲区在屏幕上的视觉距离基本稳定。

## 5. 空间索引设计

### 5.1 选择均匀网格的原因

当前画布的核心查询是“矩形范围内有哪些实体”，实体几何以矩形包围盒为主，插入、更新和删除都较频繁，且需要保持实现简单、可预测和易于测试。因此当前使用均匀网格，而不是一开始引入更复杂的层次空间树。

均匀网格的基本思路：

1. 将无限画布按固定世界尺寸切分为网格单元。
2. 根据实体包围盒计算其覆盖的所有单元。
3. 每个单元保存覆盖它的实体编号集合。
4. 查询矩形时只读取相交单元中的候选编号。
5. 对候选编号进行一次精确矩形相交判断，去除同一网格中的误报。

当前默认单元尺寸为 `512` 个世界坐标单位。单元尺寸是查询性能参数，不是业务规则，也不应影响图形的几何结果。

### 5.2 索引数据结构

当前空间索引维护三组数据：

```text
entries:    实体编号 → 规范化包围盒
entryCells: 实体编号 → 该实体覆盖的网格键列表
cells:      网格键 → 实体编号集合
```

网格键由整数单元坐标组成：

```text
cellKey = "cellX:cellY"
```

保留 `entryCells` 的原因是更新和删除时可以精确知道旧实体挂在哪些单元，不需要重新扫描所有单元。

### 5.3 包围盒规范化

索引入口会把负宽度或负高度的矩形规范化为正宽高矩形：

```text
normalized.x      = min(x, x + width)
normalized.y      = min(y, y + height)
normalized.width  = abs(width)
normalized.height = abs(height)
```

这样可以兼容拖拽、绘制或中间计算阶段出现的反向矩形，避免索引单元范围出现颠倒。领域层最终持久化的图形几何仍按现有规则取整，索引只对进入索引的边界做查询安全规范化。

### 5.4 单元范围计算

给定规范化包围盒和单元尺寸 `cellSize`，覆盖的单元范围为：

```text
minCellX = floor(x / cellSize)
maxCellX = floor((x + width) / cellSize)
minCellY = floor(y / cellSize)
maxCellY = floor((y + height) / cellSize)
```

循环遍历该范围生成网格键。负坐标通过 `floor` 自然落入负数网格，例如 `-1` 到 `0` 附近的世界区域不能使用截断取整，否则会把负坐标错误归入零号单元。

### 5.5 写入、更新和删除

索引的变更必须保持“旧关系先解除、新关系再建立”的顺序：

```text
upsert(id, newBounds)
  → 从 entryCells 读取旧单元
  → 从旧单元集合移除 id
  → 规范化新边界
  → 计算新单元列表
  → 写入 entries 和 entryCells
  → 将 id 加入新单元集合
```

实体更新时即使新旧边界仍处于同一单元，也允许走完整的解绑和重挂流程。这样实现简单、状态一致，避免为了微优化而留下旧单元引用。

删除时必须同时清理：

- `entries` 中的实体边界。
- `entryCells` 中的实体单元列表。
- `cells` 中所有单元的实体编号。
- 删除后变为空的单元。

清空画布时必须清空三组索引数据，而不能只清空业务实体映射。

### 5.6 查询流程

范围查询分为候选收集和精确过滤两步：

```text
查询矩形
  → 规范化查询矩形
  → 计算相交网格单元
  → 收集单元中的实体编号
  → 使用 Set 去重
  → 读取实体包围盒
  → 精确判断矩形相交
  → 返回实体编号
```

同一实体可能覆盖多个单元，因此候选集合必须去重。网格单元只是粗过滤，不能直接把单元命中的所有实体当作最终结果，否则会返回同一单元内但实际不相交的实体。

### 5.7 稳定排序

空间索引返回的是候选编号，不承担渲染顺序语义：

- 图形查询结果按 `zIndex` 升序，再按图形编号稳定排序。
- 连线查询结果按连线插入顺序排序。
- 强制保留项合并后仍要重新按对应规则排序。

稳定排序可以避免同一视口在平移、索引重建或集合合并后出现不必要的组件顺序变化，也避免视觉层级和命中顺序受到网格遍历顺序影响。

## 6. 图形和连线的索引边界

### 6.1 图形索引

图形索引覆盖区域和普通图形，因为区域也需要参与：

- 主图层视口裁剪。
- 框选范围查询。
- 画布范围查询。
- 后续智能对齐候选查询的基础能力。

区域与普通图形在索引层使用统一的矩形边界，但渲染层仍按区域优先、普通图形随后分组，避免索引的统一性改变区域视觉层级。

### 6.2 连线索引

连线使用独立索引，不与图形索引混用，原因包括：

1. 连线的实体结构不是矩形图形，包围盒来自点数组。
2. 连线有自己的顺序语义和渲染组件。
3. 连线更新频率和更新来源与图形不同。
4. 查询后通常需要分别渲染连线、控制点和连线文字。

直线连线直接使用规范化点数组计算包围盒；正交连线先使用正交渲染点计算包围盒。没有有效点数组的连线不进入索引，避免使用无效边界污染范围查询。

### 6.3 关系不单独建立空间索引

包含关系、父子关系和连线端点关系不是独立的可绘制空间实体，因此当前不建立关系索引。关系查询继续由关系仓储负责，空间索引只服务于有几何边界的图形和连线。

需要同时使用几何和关系时，先通过空间索引得到候选图形，再通过关系仓储做父子、祖先或后代过滤，不应把关系编号伪装成空间实体编号。

## 7. 视口裁剪设计

### 7.1 三个范围

当前渲染链路至少存在三个范围：

| 范围 | 屏幕缓冲 | 用途 |
| --- | ---: | --- |
| 可见视口 | 0 | 用户当前能看到的世界区域 |
| 图形渲染窗口 | 320 像素 | 决定区域、图形和连线是否挂载 |
| 文本详细窗口 | 96 像素 | 决定图形和连线是否挂载详细文字 |

图形渲染窗口更大，是为了让节点在接近视口边缘时提前挂载，减少平移过程中刚进入视口才创建组件造成的闪烁。文本详细窗口更小，是因为文字结构和布局成本高，只需要为视口附近的实体保留。

### 7.2 图形渲染窗口

计算流程如下：

```text
提交态或实时表现态视口
  → 计算可见世界矩形
  → 将 320 屏幕像素换算为世界缓冲
  → 扩展可见矩形
  → 查询图形索引和连线索引
  → 合并强制保留目标
  → 稳定排序
  → 挂载区域、图形和连线
```

窗口范围只影响挂载集合，不影响实体自身的世界坐标和舞台变换。

### 7.3 窗口刷新阈值

如果视口每移动一点就重新查询和重建集合，缓冲区本身带来的收益会被刷新成本抵消。因此当前只有在视口接近渲染窗口边缘时才刷新窗口。

刷新判断使用缓冲区的百分之三十五作为安全区：

```text
安全边距 = 320 屏幕像素 × 35% / scale
```

当可见视口接近或越过渲染窗口的安全边距时，重新扩展窗口并执行索引查询；如果视口仍在窗口内部安全区域，继续复用旧的渲染窗口和挂载集合。

以下情况必须强制刷新：

- 画布首次挂载。
- 画布尺寸变化。
- 视口缩放结束。
- 视口程序化定位、适配或聚焦结束。
- 进入或离开需要立即展示目标的交互状态。

### 7.4 连续平移和缩放

连续手势期间，视口实时表现态会随着舞台变换发布，但主图层不应为每个原始事件做全量响应式重建。主图层只在以下条件下更新裁剪窗口：

1. 实时视口使当前视口接近旧窗口边缘。
2. 手势进入落稳阶段，需要用最终提交态强制刷新。
3. 画布尺寸发生变化。

缩放时还要区分图形窗口和文本窗口：

- 图形窗口可以根据实时缩放状态更新，以避免视口快速扩大后没有实体挂载。
- 文本窗口在连续缩放期间暂缓刷新，保留已经挂载的文字，让舞台自然缩放。
- 缩放落稳后，按最终比例重新计算 96 像素文本窗口。

这样可以避免缩放过程中反复卸载和重新挂载大量富文本组件。

## 8. 渲染集合与强制保留

### 8.1 普通集合

普通集合由索引查询得到：

```text
renderShapes = shapeIndex.query(renderBounds)
renderLines  = lineIndex.query(renderBounds)
```

当渲染窗口还未建立时，兼容性回退是读取全量实体。正常稳定运行后，窗口会立即初始化，不能把该回退路径当成长期性能方案。

### 8.2 强制保留集合

部分目标即使位于渲染窗口外也不能被卸载，否则会破坏用户正在进行的交互。当前需要强制保留：

- 当前选中的图形。
- 当前选中的连线。
- 当前文本高亮图形。
- 当前连线文本高亮目标。
- 当前富文本高亮目标。
- 处于编辑状态的图形或连线文本。

合并规则：

```text
索引查询结果
  + 强制保留编号
  → 按编号去重
  → 读取最新实体
  → 按稳定排序输出
```

强制保留不是把实体永久加入空间索引查询范围，也不是扩大整个视口窗口，而是对最终渲染集合做局部补充。

### 8.3 富文本详细集合

图形已经挂载并不代表其富文本必须挂载。详细文字集合对图形和连线分别计算：

- 图形使用文本详细窗口判断图形包围盒是否相交。
- 连线使用文本详细窗口查询连线索引。
- 选中、文本高亮和富文本高亮目标强制保留详细内容。
- 没有详细文字的历史数据或普通文本走轻量只读文字令牌，不建立冗余富文本节点。

富文本裁剪依据空间范围，不依据固定缩放比例隐藏文字。低缩放比例下，只要实体仍在文本窗口内，仍应展示完整可读内容，避免出现“缩放较小时错误隐藏文字”的业务体验问题。

## 9. 主图层装配顺序

当前主图层的职责可以抽象为：

```text
读取视口状态
  → 计算图形渲染窗口和文本窗口
  → 图形索引查询
  → 连线索引查询
  → 合并强制保留目标
  → 图形按区域和普通图形分组
  → 计算详细富文本编号
  → 关闭或开启主图层命中监听
  → 挂载渲染组件
```

渲染顺序保持：

```text
区域
  → 普通图形
  → 连线
  → 选中连线控制点和连线文字
```

空间索引只负责“查哪些”，主图层仍负责“按什么顺序渲染”和“使用什么组件渲染”。

## 10. 交互与查询一致性

### 10.1 范围选择

框选使用画布世界坐标矩形查询图形和连线索引，再根据现有范围选择语义决定“相交”还是“完全包含”。索引查询只负责快速缩小候选集，不能改变框选的几何判定。

特别需要注意：如果一个区域跨越多个网格，查询必须只返回一次；如果实体位于同一网格但与框选矩形不相交，必须在精确相交阶段排除。

### 10.2 智能对齐

智能对齐可以通过空间索引查询“移动对象边界向外扩展阈值后的范围”，再过滤当前选区和后代图形。这样候选查询不需要遍历全部图形，但吸附距离、中心线和边界判定仍由智能对齐纯计算模块负责。

移动预览阶段不应因为图形坐标尚未提交而提前修改索引。只有移动计划提交后，图形 Store 更新才触发 `upsert`。预览位置属于过程态，不应污染正式空间索引。

### 10.3 命中检测

视口裁剪不能直接替代精确命中检测：

- 画布点击首先根据当前图层和直接目标解析业务编号。
- 需要范围候选时使用空间索引。
- 需要精确标签、轮廓或覆盖层策略时，继续使用共享几何命中内核。
- 视口变换期间主图层监听关闭，但选中覆盖层和必要的手势处理仍由对应交互层控制。

不能因为某实体没有挂载，就把它从业务数据或全局查询中视为不存在。

### 10.4 视口外目标定位

树节点选中、搜索结果定位和聚焦操作可能针对当前视口外实体。定位流程应直接从 Store 读取实体边界并执行视口适配，不能依赖实体已经挂载在 Konva 场景树中。定位完成后，视口强制刷新裁剪窗口，目标再按普通索引查询进入渲染集合。

## 11. 数据一致性约束

### 11.1 Store 是正式边界

空间索引不保存业务实体副本，只保存编号和包围盒。实体详情仍以图形和连线 Store 为准。查询编号返回后必须重新从 Store 读取实体，以避免索引结果与实体删除、替换之间出现陈旧对象。

### 11.2 所有几何写入口都要维护索引

以下写入口必须成对出现：

```text
实体 Store 写入
  + 空间索引 upsert/remove
  + 对应修订号递增
```

禁止出现以下情况：

- 只更新 Store，不更新索引。
- 只更新索引，不更新 Store。
- 图形删除后仍从索引返回编号。
- 连线点数组更新后仍使用旧包围盒。
- 清空业务实体但保留旧网格单元。

### 11.3 连线端点移动

连线端点随图形移动时，连线包围盒可能变化。更新图形本身不会自动推导连线新边界，因此负责移动和连线重算的应用流程必须在连线点数组发生变化后调用连线更新入口，使连线索引同步迁移到新网格。

### 11.4 视口状态不是实体状态

实时视口状态只影响裁剪窗口计算，不应写入图形或连线索引。索引边界仅由实体几何决定，不能把平移位置、缩放比例或屏幕尺寸混进索引数据。

### 11.5 视口平移和缩放不更新空间索引

空间索引记录的是实体在画布世界坐标中的位置，视口平移和缩放只改变观察画布的方式，不改变实体的世界坐标和几何包围盒。因此视口变化不需要更新空间索引，只需要重新计算查询范围。

典型流程为：

```text
视口 position / scale 变化
  → 将屏幕视口换算为新的世界范围
  → 按缓冲区扩展查询范围
  → 使用原有图形和连线索引查询
  → 更新渲染集合
```

例如实体始终位于世界坐标 `x = 100`。平移只会让它的屏幕位置从 `100` 变为 `-400`，索引中的 `x = 100` 不应变化；缩放只会改变世界范围映射到屏幕的比例，也不应移动索引条目。

如果在平移或缩放过程中修改索引，就会把镜头状态混入实体数据，导致每一帧搬移大量索引条目，增加主线程成本，并可能让索引与正式业务坐标不一致。

因此需要严格区分：

| 变化 | 是否更新空间索引 | 正确动作 |
| --- | --- | --- |
| 图形位置、尺寸变化 | 是 | 更新图形包围盒 |
| 连线点数组变化 | 是 | 重新计算连线包围盒 |
| 图形或连线删除 | 是 | 移除索引条目 |
| 视口平移 | 否 | 更新世界查询范围和渲染集合 |
| 视口缩放 | 否 | 更新世界查询范围和渲染集合 |
| 画布尺寸变化 | 否 | 重新计算可见范围和裁剪窗口 |

连续手势期间可以复用已有裁剪窗口；只有视口接近缓冲窗口边缘或手势落稳时，才重新执行索引查询。这样既保持索引稳定，也避免每一帧重建完整渲染集合。

## 12. 性能模型与参数调优

### 12.1 查询成本

理想情况下，范围查询成本近似为：

```text
相交网格单元数量
× 每个单元候选数量
 + 候选精确相交判断数量
```

相比全量遍历，索引收益来自于大多数远离视口的实体不会进入候选集合。实体数量、分布密度和实体尺寸会影响收益。

### 12.2 单元尺寸权衡

单元过小：

- 大区域或长连线会覆盖大量单元。
- `entryCells` 维护成本增加。
- 大范围查询需要读取更多网格键。

单元过大：

- 每次视口查询会读到更多远处候选。
- 精确相交过滤成本增加。
- 稀疏大画布下索引区分度下降。

当前使用 512 世界单位作为默认值，后续调整必须用确定性千节点场景和真实单据分别对照，不能只看单次开发机采样。

### 12.3 缓冲区权衡

图形缓冲区越大，平移时越不容易看到节点刚进入视口才挂载，但初始挂载量和内存占用会增加。缓冲区越小，挂载量较低，但窗口刷新和组件创建更频繁。

当前 320 屏幕像素是交互稳定性与挂载规模之间的折中；文本 96 屏幕像素是针对富文本成本单独设定的更小缓冲。

### 12.4 不以单一帧率结论验收

浏览器调度、页面并行加载和机器环境会影响帧间隔，因此验收至少同时记录：

- 场景节点数量。
- 渲染落稳耗时。
- 平移和缩放期间长任务数量。
- 索引查询耗时和候选数量。
- 富文本布局次数和总耗时。
- 视口窗口刷新次数。

帧率和九十五分位帧间隔可以作为辅助指标，但不能单独证明索引或裁剪正确有效。

## 13. 测试与验证矩阵

### 13.1 空间索引单元测试

必须覆盖：

1. 查询只返回实际相交的实体。
2. 同一实体跨越多个单元时只返回一个编号。
3. 负坐标正确归属网格。
4. 更新实体后旧位置不再返回，新位置可以返回。
5. 删除实体后所有旧单元都不再返回该编号。
6. 清空后索引大小为零且查询为空。
7. 无效单元尺寸回退到安全默认值。
8. 负宽度和负高度边界能够正常查询。

### 13.2 视口裁剪单元测试

必须覆盖：

1. 视口位置和缩放能够正确转换为世界矩形。
2. 屏幕缓冲按缩放比例换算到世界坐标。
3. 视口位于渲染窗口安全区内时复用窗口。
4. 视口靠近四个方向任一边缘时刷新窗口。
5. 首次没有旧窗口时必须刷新。
6. 文本窗口使用独立的 96 像素缓冲。
7. 连续缩放期间不因固定比例隐藏窗口内文字。
8. 强制目标在窗口外仍保留详细文字。

### 13.3 Store 集成测试

必须验证：

- 图形新增、更新、删除与图形索引同步。
- 连线新增、点数组更新、删除与连线索引同步。
- 正交连线索引使用实际渲染包围盒。
- 按图形删除关联连线时不会留下孤立索引项。
- 清空画布后重新添加同编号实体不会命中旧边界。

### 13.4 浏览器验证场景

至少验证以下场景：

1. 一千个确定性图形、二十个区域和九百七十五条连线的基线场景。
2. 大量实体集中在同一网格的密集场景。
3. 实体分散在正负坐标的大范围稀疏场景。
4. 一个大区域跨越多个网格的场景。
5. 连续平移从视口内穿过多个窗口边界。
6. 连续缩放期间文本挂载和落稳后的文本恢复。
7. 选中视口外图形后继续平移，选中目标不能丢失。
8. 搜索视口外文本并聚焦，目标应能正确挂载。
9. 编辑视口外强制保留目标时，编辑器和覆盖层不能被裁剪卸载。
10. 图形移动后关联连线进入和离开视口时，连线索引与渲染结果一致。

## 14. 排查指南

### 14.1 视口内缺少图形

按以下顺序排查：

1. 确认舞台位置、缩放和画布尺寸是否正确。
2. 确认世界可见矩形是否正确，尤其是 `position` 的正负方向。
3. 确认图形包围盒是否进入索引，检查索引大小。
4. 直接调用图形索引查询渲染窗口，判断是索引遗漏还是渲染集合过滤。
5. 检查强制保留合并和稳定排序是否误删或覆盖。
6. 最后检查区域、普通图形和文本详细集合的分组逻辑。

### 14.2 视口外图形仍然很多

可能原因包括：

- 当前图形处于选中或高亮强制保留状态。
- 渲染窗口仍在缓冲区内复用，尚未到刷新边界。
- 初始渲染窗口为空时走了全量回退。
- 图形边界过大，确实与渲染窗口相交。
- 查询结果已裁剪，但文本、控制点或覆盖层仍在其他图层保留。

因此不能只观察主图层组件数量，要同时区分图形集合、详细文字集合、覆盖层集合和浏览器文档级监听器数量。

### 14.3 图形移动后旧位置仍能查到

重点检查：

- 更新入口是否调用了图形 Store 的 `updateShape`。
- `upsert` 是否先解绑旧单元。
- 是否存在绕过 Store 直接修改实体对象的代码。
- 是否实际查询到了旧的渲染窗口，而不是旧索引结果。

### 14.4 连线消失或残留

重点检查：

- 连线点数组是否被规范化。
- 正交连线是否按渲染点计算包围盒。
- 连线更新后是否调用连线索引 `upsert` 或 `remove`。
- 关联图形移动后是否同步更新连线点数组。
- 选中连线是否被强制保留造成“仍显示”的误判。

## 15. 后续演进边界

### 15.1 何时考虑更复杂的索引

只有在以下证据成立时，才评估四叉树、矩形树或分层索引：

- 均匀网格查询在真实数据中仍占据明显长任务。
- 大量大区域和长连线导致单个实体覆盖过多网格。
- 数据分布极度倾斜，部分网格候选数量远高于其他网格。
- 单元尺寸调优无法同时覆盖密集和稀疏场景。

替换索引结构时必须保持 `upsert`、`remove`、`query`、`clear` 和 `size` 的抽象契约，Store、范围选择和主图层不应依赖具体索引实现。

### 15.2 何时考虑分层渲染

索引和裁剪解决“挂载哪些实体”，不能解决单个复杂实体自身绘制成本过高的问题。若性能面板显示主要成本来自少量静态背景或复杂富文本，应单独评估：

- 静态图层缓存。
- 低细节图形。
- 位图快照。
- 只读富文本的绘制合并。

缓存必须遵守“空闲预热、缓存未就绪不阻塞当前交互、明确失效条件”的约束，不能在平移或缩放首帧同步生成大缓存。

### 15.3 何时考虑分块持久化

当前索引是运行时内存结构，不参与后端持久化和协作协议。只有当画布规模达到单次加载、协作同步或内存占用无法接受的程度时，才评估按空间分块加载。分块加载会引入数据生命周期、跨块关系、离屏编辑和协作一致性问题，不能仅作为裁剪的自然延伸直接实施。

## 17. 当前结论

空间索引和画布裁剪应被视为同一条性能链路上的两个独立层次：索引负责降低范围查询成本，裁剪负责降低运行时渲染和组件维护成本。两者共同使用世界坐标，但不改变业务实体、命中语义和持久化数据。

当前方案以均匀网格、固定屏幕缓冲、边缘触发刷新和交互目标强制保留为核心约束，已经覆盖大规模画布的主要挂载成本。后续优化应优先通过可复现基线、候选数量、窗口刷新次数和性能面板定位瓶颈，再决定是否调整参数或替换索引结构。
