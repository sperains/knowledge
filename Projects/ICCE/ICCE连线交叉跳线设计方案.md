# ICCE 连线交叉跳线（Jump Line）设计方案

## 当前结论

| 已完成 | 明确保留的边界 |
| --- | --- |
| 连线交叉跳线 P1/P2/P4 落地：上层让路跳弧、凸向取屏幕固定方向（水平上、垂直倾向段按象限取左/右）、插点逼近渲染、工具栏开关；交互预览期间隐藏跳线弧；跳线领域服务与正交折线圆角已统一收敛到 `line-visual-service.ts`；相关领域服务 23 例、视觉几何 5 例、跳线组合式 5 例通过，既有全量基线 726 例通过 | 相邻交叉聚类合并暂缓设计；P3 增量失效 / 批量合并待实施，预览态协调已通过交互期间隐藏跳线弧落地；首次开启性能候选方案已完成实测但尚未选型；端点/箭头附近遮挡不做自动抑制（用户自调连线）；Konva 像素渲染视觉验收待人工确认 |

决策语义以 [[ADR/ADR-019-ICCE连线交叉跳线视觉语义|ADR-019]] 为准；本文记录设计依据与实施细节。

## 1. 背景与问题

icce 画布中，连线（`OrthogonalLine` 正交折线 / `PolylineLine` 普通折线）会相互交叉。当前交叉处两条线直接十字穿过：

- 同色、同线宽的线在交点处视觉粘连，读者无法区分「一条线越过了另一条」还是「两线在此相连」；
- 正交线横平竖直、交叉频繁（典型流程图中几十条线可产生几十上百个交叉点），问题被放大；
- 现有 `orthogonal-line-model.ts` 只做端点 stub + 正交连接，不做线间避障，交叉是常态而非例外。

**方案目标**：在两条线实际交叉处，为其中一条线绘制小半圆弧「跳线」，表示两线互不相连。纯视觉增强，不改变数据模型、命中语义与协作协议。

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 状态 |
|---|---|---|
| G1 | 所有 line-line 交叉显示跳线：正交×正交、正交×折线、折线×折线 | ✅ P1 |

| G5 | 端点重连、shape 移动重路由、undo/redo、协作远端变更后跳线收敛 | ⏳ P3（增量失效 / 批量合并待定；预览态协调已落地） |

## 3. 业界参照

| 产品 | 做法 | 可借鉴点 |
|---|---|---|
| draw.io (mxGraph) | 交叉处 z-order 在上的边画弧让路；可配 jumpSize/jumpStyle/fixedAngle/flipDirection | 「上层让路」、凸向可翻转 |
| ProcessOn | 工具栏「跳线」开关 + 半径设置 | 开关交互形态 |
| mermaid | 布局后对边交叉绘制 arc 型 line-jump | 弧形与半径默认值 |
| 电路图工具（EDA） | 交叉点默认跳线，语义就是「不相连」 | 弧向与线宽一致、视觉重量轻 |

**共识结论**：业界主流 = 「上层（后画）让路画弧 + 半圆弧 + 全局开关」，弧是线的视觉延伸（同色同宽），不做独立可交互对象。

## 4. 核心设计决策（均已拍板）

### 4.1 谁跳（D1）：上层让路跳

**两线交叉时，视觉上层（后画、数组靠后、zIndex 高）的线跳弧让路**，下层直穿；上层因几何约束不能跳时下层兜底跳。

- 与 draw.io / 电路图惯例一致（icce Line 无 zIndex 字段，层级 = `lineOrder` 插入序，靠后 = 上层）；
- 兜底语义：避免出现"谁都不跳"的视觉缺口。

### 4.2 弧凸向（D2）：屏幕固定方向（参考 miro）

**弧凸向相对屏幕固定（上 / 左 / 右，永不凸下），由跳线段相对其起点的倾斜方向决定**（决策演进：初版"直穿线方向"，2026-08-20 参考 miro 后定为固定方向）。

- 水平倾向段（|dy| ≤ |dx|，含水平段）→ 恒凸上（弧顶在跳线上方凸起，缺口/开口在下方）；
- 垂直倾向段（|dy| > |dx|，含垂直段）→ 以「从起点面向终点」为基准：终点偏移与画向同象限（dx·dy > 0）凸右、异象限（dx·dy < 0）凸左，取该侧法线保证弧仍为规则半圆；
- 严格垂直（无水平分量）→ 兜底恒凸右；
- 判定基准：段方向从起点看向终点（起点即线在图形上的锚点端），先按主轴倾向区分水平/垂直，只有垂直倾向段用象限规则；与直穿线方向无关。

### 4.3 弧形态（D3）

- 半圆弧，半径 `R = 6px`（画布坐标，随缩放等比，与线宽同基准）；
- 跳线样式 = 线自身样式（stroke / strokeWidth / dash / 动画继承），不加高亮。

### 4.4 渲染实现（D4）：插点逼近

渲染前把 `[cross-R, cross+R]` 段替换为半圆采样点（12 段采样，13 点含端点），仍走 `<v-arrow>`：

- 不换组件；箭头、虚线、`hitStrokeWidth` 命中、动画全部沿用；
- 只动「points 怎么算」，命中/高亮/协作链路零改动；
- 连续重复点去重，输出无冗余。

### 4.5 与现有机制的关系

| 现有机制 | 关系 |
|---|---|
| `orthogonal-line-model.ts` | 跳线消费其**渲染后 points**，不干预路由 |
| `spatial-index.ts` | P3 增量失效阶段接入 |
| `useHighlightState` / 选中覆盖层 | 无感知：跳线是 points 的一部分 |
| 协作（Local/RemotePreview） | 纯本地渲染派生，无新消息 |

## 5. 数据与算法设计

### 5.1 统一连线视觉服务：`line-visual-service.ts`

跳线和圆角都是连线的视觉派生处理，不拆成两个服务。服务只接收领域模型和几何点集，不依赖 Vue、Konva、Store 或持久化流程；界面层和组合式函数可以调用服务，服务不反向调用界面层。

当前职责如下：

- `getLineRenderedPoints`：生成基础渲染点；正交折线使用正交路由点，普通折线直接沿用业务点；
- `getLineVisualPoints`：在基础渲染点上生成视觉点，仅对正交折线应用圆角，普通折线不加圆角；
- `applyLineCornerRounding`：只修改渲染点集中的折点，不修改业务点；
- `computeLineJumpSegments`：计算交叉位置和应跳的线段；
- `applyLineJumpArcs`：把跳弧插入渲染点集；
- `getLineRenderedBounds`：使用基础渲染点计算交互包围盒，避免圆角采样点改变交互边界。

```
输入：lines（含渲染后 points）+ 配置
输出：Map<lineId, LineJumpSegment[]>
```

```ts
interface LineJumpSegment {
  /** 所属折线段索引（points 中的段序号） */
  segmentIndex: number;
  /** 交叉点（画布坐标） */
  cross: Point;
  /** 弧半径 */
  radius: number;
  /** 弧凸向单位向量：屏幕固定方向（水平凸上、斜段按倾斜凸左/右、垂直兜底凸右） */
  normal: Point;
  /** 跳线在该段的前进方向（单位向量），用于渲染插点 */
  along: Point;
  /** 与之相交的另一条线 */
  otherLineId: string;
}
```

以上方法均为纯函数、无副作用、不依赖 Konva，domain 层可直接单测。

### 5.2 求交流程

1. 每条线用渲染点集拆成段；
2. 先用线段包围盒做快速排除，再判断两条有限线段是否相交；
3. 谁跳判定（见 §4.1）+ 过滤（见 §7）；
4. 每个交叉点独立生成跳线（**不做相邻交叉合并/聚类**——该问题暂缓设计）。

其中，线段求交只负责几何判断，不负责绘制：两条线平行或共线时返回空；交点必须落在两条有限线段内部才算相交，端点允许在浮点容差范围内计入。

### 5.3 渲染插点

`applyLineJumpArcs(points, jumps, sampleCount=12)`：命中段用半圆采样点替换 `[cross-R, cross+R]`，首尾点不变，未命中段透传。

## 6. 渲染与更新

### 6.1 渲染接入

`LineShape.vue` 的 `linePoints` 计算：先调用 `getLineVisualPoints(line)` 生成正交圆角，再在开关开启且有跳线时调用 `applyLineJumpArcs` 插入跳弧。弧只作用于**渲染点集**，业务 `line.points` 不动（持久化/协作数据零污染）。

### 6.2 开关

- 底部工具栏「跳线」按钮（`toolbar.jump-line`，图标 `jd-jumper`），`role: 'toggle'` 走 `toolStore.toggleStateMap`；
- `useJumpLine.ts` composable：开关 off 返回空；模块级缓存绑定 store 实例引用 + `lineRevision` 失效；
- 默认关闭；关闭时零计算零渲染开销。

### 6.3 更新时机（现状与计划）

| 触发 | 现状 | P3 计划 |
|---|---|---|
| 线增删改、端点重连 | 全量重算（lineRevision 失效） | 增量失效（变更线邻域重算） |
| shape 移动/缩放（重路由） | 随 lineRevision 全量重算 | 同上 |
| 开关切换 | 全量重算 / 清空 | — |
| undo/redo、协作批量变更 | 批量合并后触发一次 | 微任务合并 |
| 图形、框选、控制点和重连预览态 | `dragging` / `connecting` 期间只渲染原始 points，不插入跳线弧；提交或取消后恢复 | 不做实时重算；以交互期间隐藏跳线弧协调预览 |

### 8.3 能力边界（坦诚说明）

- **Konva 真实像素渲染不进单测**：弧平滑度、凸向视觉一致性需人工验收；

### 8.4 首次开启性能实测与 P3 候选方案

#### 8.4.1 实测结果

通过本地跳线性能调试场景，在浏览器中验证首次打开跳线开关。场景由水平、垂直折线组成，重点观察「下一次更新」「首帧完成」「渲染稳定」三个阶段；以下数据用于定位瓶颈，不作为不同设备之间的绝对基准。

| 连线数 | 交叉对 / 跳弧数 | 算法计算 | 下一次更新 | 首帧完成 | 渲染稳定 |
|---:|---:|---:|---:|---:|---:|
| 80 | 1,600 / 1,600 | 12.5 ms | 28.6 ms | 32.6 ms | 58.3 ms |
| 160 | 6,400 / 6,400 | 8.3–13.3 ms | 46.3–76.2 ms | 53.5–93.0 ms | 103.2–184.1 ms |
| 300 | 22,500 / 22,500 | 25.8 ms | 155.9 ms | 190.4 ms | 510.1 ms |

结论：算法本身在 160 条连线场景约 8–13 ms，明显低于端到端首帧耗时；当前首次开启的主要压力来自跳弧插点后的大量渲染点进入连线渲染链路，而不是单纯的交叉计算。160 条连线约产生 6,400 个跳弧、约 83,200 个采样点；连线数增加后，渲染阶段增长更快。

#### 8.4.2 候选方案（均未拍板）

下面沿用讨论中的方案编号。它们分别解决渲染几何、候选计算范围和调度时机，不是互斥的同一层改动；是否组合，需以真实图形分布和视觉验收结果为准。

| 方案 | 方向 | 主要改动 | 适用收益 | 主要代价 / 风险 |
|---|---|---|---|---|
| 方案 1 | 减少 / 自适应跳弧采样点 | 将当前每个跳弧的固定采样段数按缩放级别或弧长调整，在视觉允许范围内从 12 段降到更少的采样段；保留现有插点逼近与 `v-arrow` 渲染链路 | 改动最小，可直接减少渲染点和更新数据量，适合作为低风险基线 | 只能降低单个跳弧的点数，不能改变跳弧数量和连线节点更新方式；采样过少时可能出现弧线折角，缩放规则需要视觉验收 |
| 方案 2 | 主体连线分段绘制 + 原生跳弧绘制 | 主体连线在交叉点两侧留出 `[cross-R, cross+R]` 空白，再在同一自定义渲染器中用原生弧绘制补回；主体与跳弧必须原子替换，不能先出现空白再补弧；命中、箭头需要时可继续保留透明原始线层；不为每个交叉创建独立图形节点 | 直接减少 12 段采样点带来的渲染和节点更新压力，是核心候选方向 | 需要同步处理线宽、虚线、动画、缩放和箭头层；若拆成大量独立图元，可能抵消收益 |
| 方案 3 | 视口感知的候选计算 | 复用 `lineSpatialIndex`，按扩大的可视区域查询候选线；缓存键增加视口分桶 / 版本，平移缩放时节流更新并保留边界缓冲 | 真实大图中大量线条位于视口外时有效；改动中等 | 当前密集压测场景的线条都在视口内，收益有限；要处理视口边界、缩放和缓存失效，不能单独解决首次全量开启 |
| 方案 4 | 渐进式首次开启 | 保持原始完整连线作为底图，跳线按批次准备；每条线或每个批次必须把「主体留空 + 跳弧」作为一个整体原子切换，禁止先展示空白缺口；可选择全部准备完统一切换，或分批切换 | 将一次性渲染峰值拆开，降低单帧卡顿 | 分批切换会出现局部已显示、局部未显示的中间态；统一切换则保留最终切换峰值，需要产品接受视觉过渡策略 |

#### 8.4.3 当前建议与边界

当前建议仅作为实施顺序，不是架构决策：

1. 先用方案 1 建立低风险对照，确认减少采样点能带来多少收益；它适合快速验证，但不预期单独解决大规模场景。
2. 如果方案 1 仍不足，验证方案 2，优先优化跳弧进入渲染链路的方式；这是针对当前实测瓶颈的直接改动。
3. 如果真实大图中存在大量视口外连线，再评估方案 3；方案 3 改动中等，但对「所有线都在视口内」的压测不会有明显收益。
4. 只有方案 1/2 仍无法满足首次开启体验时，才评估方案 4；方案 4 是调度策略，不能替代方案 2 的主体留空与弧补回语义。
5. P3 的增量失效主要改善后续局部变更，不应被当作首次开启全量计算的直接解决方案。

待验证项：方案 1 的采样段数与视觉阈值、原生弧绘制与线条样式同步、透明命中 / 箭头层兼容性、视口查询在真实图中的收益、渐进式中间态是否可接受。当前未选定方案 1/2/3/4，也未修改生产渲染实现。

#### 8.4.4 调试实例整合建议

`jump-line-performance.ts` 可以整合到 `icce-demo.vue` 的调试宿主中，但不建议把场景生成和测量函数直接搬进 Vue 文件。推荐保留以下边界：

- `jump-line-performance.ts`：继续负责跳线压测场景生成、配置归一化和算法耗时测量，保持纯函数，便于单测与复用；
- `icce-demo.vue`：作为统一调试入口，通过查询参数切换普通画布性能场景与跳线性能场景，例如 `?mode=jump-line&lines=160`；
- 公共宿主：复用 `DfdCanvas`、`CanvasPerformancePanel`、视口初始化和加载计时；仅在跳线模式增加“关闭状态强制、首次开启按钮、下一次更新 / 首帧 / 稳定三个阶段”的专用面板；
- 调试入口：当前不通过应用路由暴露；需要复测时临时挂载 `icce-demo.vue`，或直接调用独立场景模块与测试。

这样可以减少一个重复的调试页面，但不会把性能测试逻辑耦合到界面组件。统一宿主代码已落地，但两个开发路由已撤销，不再从应用路由暴露；性能场景仍可通过测试或临时调试挂载使用。
