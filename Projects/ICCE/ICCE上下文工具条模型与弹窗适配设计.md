# ICCE 上下文工具条模型与弹窗适配设计

> 当前结论：上下文工具菜单与固定工具栏是两套并列的交互入口，不合并工具栏容器和状态。上下文工具菜单采用“业务状态生成统一模型、通用工具条按类型渲染、业务层统一处理命令”的结构；固定工具栏采用“权限与图表类型生成工具配置、控制器编排交互、状态模块分别保存画布工具和画布显示状态”的结构。上下文菜单弹窗在自身层基于实际画布边界完成水平修正和上下翻转，不通过移动整个工具条解决弹窗越界。

> 事实来源：`jd_ipd` 的结构重构基线为提交 `a8a83bafe`，当前动作命名和分发基线为提交 `6b0e7beb7`，并结合当前源码、测试和构建验证结果。

## 1. 背景

上下文工具条原先由多个按钮组件分别维护。图形类型、字号、对齐、颜色、层级、连线类型和边框面板各自拥有不同的弹窗封装、状态处理和事件回写方式，导致以下问题：

- 同一类按钮的打开、关闭、禁用和提示行为不一致。
- 图形填充色、文字颜色和文字背景色等颜色面板难以统一适配。
- 弹窗默认向下展开，画布边缘空间不足时容易被裁剪。
- 工具条组件同时承担界面渲染、权限判断、选项计算和业务命令分派，新增按钮需要修改多个入口。
- 面板内部图标的提示、选中状态和关闭行为容易出现局部差异。

本次重构保持既有业务逻辑、按钮能力和命令入口不变，主要调整上下文工具条的描述方式、渲染分流和弹窗定位边界；固定工具栏则明确模型、控制器、状态和命令事件的职责边界。

## 2. 目标与边界

### 2.1 目标

1. 用统一的工具条模型描述普通按钮、选项面板、颜色面板、字号面板和复杂组合面板。
2. 将权限和选项计算集中在上下文工具条业务层及模型层，避免渲染组件读取业务状态。
3. 让通用工具条只负责尺寸、定位、弹窗开合和事件转发。
4. 让所有弹窗复用同一套画布边界适配逻辑。
5. 保持快捷操作、确认提示、颜色面板保持打开、层级操作和图形类型禁用规则不变。

### 2.2 非目标

- 不改变现有应用命令、领域规则、权限规则和画布数据结构。
- 不把上下文工具条改造成新的通用命令总线。
- 不把每个面板都继续抽象成独立的业务按钮类型。
- 不通过增大工具条整体边距来掩盖弹窗自身越界问题。
- 不将弹窗定位修正写入图形模型、持久化数据或协作消息。

## 3. 总体架构

上下文工具条当前遵循以下链路：

```text
选区与目标状态
  → ContextualToolbar 计算权限和业务状态
  → contextual-toolbar-model 生成 ToolbarItem[]
  → FloatingToolbar 管理工具条尺寸、位置和当前展开项
  → ToolbarControl 按 kind 分流到具体控件
  → ToolbarPopup 或复杂面板处理局部交互
  → ToolbarCommandEvent
  → ContextualToolbar 复用既有上下文命令入口
  → 应用命令、领域规则和变更运行时
```

### 3.1 业务编排层

`ContextualToolbar.vue` 是上下文工具条的业务编排入口，负责：

- 将当前覆盖层目标转换为上下文命令目标。
- 读取选区、图形、图表类型和权限信息。
- 生成 `ToolbarAccess` 能力标记。
- 调用模型构建函数得到当前可见的工具条项。
- 处理需要确认的清空区域、引用活动图等特殊命令。
- 将普通属性修改和动作命令转回既有上下文命令入口。

这一层可以感知业务和权限，但不负责具体按钮结构与弹窗样式。

### 3.2 模型层

`contextual-toolbar-model.ts` 是统一描述入口。它根据目标类型分派到图形、多图形、连线、区域和混合选择构建器，再执行权限过滤和分割线归一化。

模型层负责把以下内容组合成展示数据：

- 按钮标签、图标和提示文本。
- 按钮类型、动作类型和属性字段。
- 当前值、混合值、选中值和禁用状态。
- 选项列表、颜色值、菜单布局和面板保持策略。
- 图形类型切换、插入图形和对齐选项的领域规则结果。

模型层不执行命令，也不直接写入 Store。图形类型是否允许切换仍由领域服务判断，模型只把判断结果映射为菜单项的禁用状态。

### 3.3 通用渲染层

`FloatingToolbar.vue` 负责工具条级状态：

- 根据真实尺寸向覆盖层反馈宽高。
- 在画布安全范围内计算工具条水平位置。
- 通过 `activeItemKey` 保证同一时间只展开一个面板。
- 在工具条隐藏、按钮列表变化或退出键触发时关闭当前面板。
- 将命令、打开和关闭事件向上转发。

`ToolbarControl.vue` 负责单项分流：

| 模型类型 | 渲染方式 | 主要职责 |
| --- | --- | --- |
| `command` | 普通工具条按钮 | 触发一次性动作 |
| `toggle` | 带激活态的普通按钮 | 修改布尔属性 |
| `options` | 通用选项弹窗 | 展示列表或网格选项 |
| `color` | 通用颜色弹窗 | 展示颜色选择器并生成属性补丁 |
| `number` | 字号或数值控件 | 输入数值、步进或选择预设值 |
| `composite` | 少量复杂组合面板 | 承载边框和连线类型等已有复杂交互 |
| `divider` | 分隔线 | 只参与布局，不产生业务事件 |

渲染层只组装 `ToolbarCommandEvent` 并转发，不直接修改图形、连线或 Store。

## 4. 统一模型与事件契约

### 4.1 模型类型

`ToolbarItem` 是工具条的联合模型。新增常规按钮时，优先使用已有类型并补充描述字段，而不是新增一个专用按钮组件。

- 一次性动作使用 `command`。
- 布尔属性使用 `toggle`。
- 有多个可选项的菜单使用 `options`。
- 颜色选择使用 `color`，通过 `propertyKey` 映射到统一属性补丁。
- 数值输入使用 `number`。
- 只有确实包含多段内部交互的既有面板才使用 `composite`。

`id` 用于稳定识别当前项。弹窗开合、列表变化和重新渲染都应优先使用稳定标识，避免多个同类动作共享 `action` 时互相关闭或覆盖。

### 4.2 命令事件

控件向业务层发送最小化的统一事件：

```ts
interface ToolbarCommandEvent {
  action: ToolbarAction;
  patch?: ToolbarPropertyPatch;
  shapeType?: FlowShapeType;
}
```

典型的颜色选择链路如下：

```text
颜色选择器 change
  → ToolbarControl.selectColor
  → { action: 'update-property', patch: { fill: '...' } }
  → ContextualToolbar.executeToolbarCommand
  → 既有上下文命令入口
  → 应用命令与变更运行时
```

选项菜单遵循相同原则：选项只声明动作、属性补丁或图形类型，业务层决定最终如何执行。

### 4.3 面板开合策略

- 普通命令执行前关闭当前面板。
- 选项菜单选择后关闭当前面板。
- 颜色面板和边框、连线类型等需要连续操作的面板保持打开。
- 关闭工具条、切换选区或按退出键时清理当前展开项。
- 颜色或选项面板内部的图标统一通过 `ToolbarPopupTooltip` 提供文字提示。

`ToolbarAction` 来自现有动作注册表。画布持久化变更使用应用层的
`ContextualCanvasAction` 与 `CONTEXTUAL_CANVAS_ACTIONS`；工具栏专属的界面动作继续保留在
`TOOLBAR_ACTIONS` 中。两者共享已注册的画布动作值，但不把固定工具栏的界面动作泄漏到应用层。

## 5. 上下文工具菜单与固定工具栏的边界

### 5.1 两套入口不合并

上下文工具菜单和固定工具栏解决的问题不同，当前设计明确保持两个交互面：

| 交互面 | 触发位置 | 作用范围 | 主要状态 | 典型能力 |
| --- | --- | --- | --- | --- |
| 固定工具栏 | 画布左侧和底部的固定位置 | 当前画布和全局视图 | 当前画布工具、菜单展开、画布显示状态 | 选择、绘制图形、区域、模版、字典、网格、缩放、全屏 |
| 上下文工具菜单 | 选区或目标附近的覆盖层 | 当前选中图形、连线、区域或混合目标 | 当前目标的面板、属性值和菜单项 | 删除、属性编辑、颜色、对齐、层级、区域操作、连线操作 |

两者可以复用元数据、动作注册表、按钮视觉组件和基础事件约定，但不共享以下内容：

- 不合并左右固定布局和选区锚定布局。
- 不把固定工具栏的当前画布工具状态放进上下文工具菜单模型。
- 不把上下文菜单的当前面板和目标属性值放进固定工具栏 Store。
- 不让任一工具条组件直接承担另一套工具条的业务编排。

这样可以避免“选中了区域工具”和“当前选中区域的编辑菜单”被误认为同一种激活状态，也避免弹窗、全局视图状态和选区状态相互覆盖。

### 5.2 固定工具栏的实现链路

固定工具栏遵循以下链路：

```text
图表类型与权限
  → fixed-toolbar-model 生成左右、底部工具配置
  → ToolBar.vue 负责固定布局、可见性和子面板容器
  → ToolButton.vue 负责图标、提示、激活态、状态值和徽标展示
  → useFixedToolbarController 负责点击分流、菜单生命周期和状态切换
  → tool-store / canvas-display-store 保存对应状态
  → 画布意图或事件总线执行视图与工具命令
```

各层职责如下：

- `toolbar-meta.ts` 是按钮文案、图标和提示文本的统一数据源。固定工具栏和上下文菜单需要展示相同语义时，优先引用这里的配置，不在组件中重复手写文本。
- `fixed-toolbar-model.ts` 是纯配置构建层，根据图表类型、权限和视图状态生成工具项；模型不读取 Store，也不执行命令。
- `ToolBar.vue` 只负责左侧、底部和全屏按钮的布局、可见性、子菜单容器和分隔线。
- `ToolButton.vue` 只负责通用按钮视觉和状态投影。数字徽标通过工具配置的 `badge` 声明数据源，按钮不为每个徽标数量声明独立的响应式变量。
- `useFixedToolbarController.ts` 负责点击行为、当前菜单和退出键，并把状态变化转给对应的 Store 或画布意图；固定菜单不再因点击画布自动关闭，当前规则见下文“固定菜单与连续绘图操作约定”。

### 5.3 固定工具栏的按钮角色

固定工具栏通过 `ToolConfig` 的 `role` 表达行为，不按按钮名称增加分散的专用分支：

| 角色 | 状态归属 | 行为 |
| --- | --- | --- |
| `tool` | `tool-store.current` | 持续接管画布交互；重复点击当前工具时退回选择工具 |
| `menu` | 控制器内部的 `openMenu` | 切换子面板时退出原绘图工具；选中子工具后保持面板展开，子项高亮由当前画布工具决定 |
| `action` | 无持久激活态 | 点击执行一次性命令；模版、字典等动作执行前清理当前画布工具 |
| `toggle` | `canvas-display-store` | 独立切换网格等画布显示状态，不与当前画布工具混用 |
| `bistate` | 工具 Store 或画布显示 Store | 在两个明确状态间切换，如指针/手型、全屏/普通屏 |
| `status` | 由配置中的值函数读取 | 只展示当前状态，例如缩放比例；点击行为仍由控制器统一分发 |

“区域工具高亮后点击模版，区域状态应清空”属于 `tool` 与 `action` 的明确边界：模版不是持续画布工具，而是一次性入口，所以控制器在执行模版命令前将当前工具恢复为 `pointer`。字典遵循同一规则。展开图形菜单时也会清掉区域等其他持续工具；选择菜单中的子图形后，再由 `tool-store` 激活具体画布工具。

### 5.4 状态拆分

固定工具栏的状态按影响范围拆分，避免一个 Store 同时承担所有按钮状态：

| 状态模块 | 保存内容 | 不保存内容 |
| --- | --- | --- |
| `tool-store` | 当前画布工具、指针/手型模式 | 菜单是否展开、网格是否显示、全屏状态 |
| `canvas-display-store` | 网格、跳线开关、全屏、单屏显示 | 当前绘制工具、上下文选区、弹窗位置 |
| `useToolbarMenuState`（控制器内部） | 固定工具栏当前打开的菜单 | 画布业务状态、持久化图形数据、协作数据 |

菜单展开状态是固定工具栏的局部界面状态，因此保留在控制器内部；它不需要进入全局 Store，也不应被上下文工具菜单复用。画布工具和画布显示状态则需要被按钮、画布事件或视图逻辑共同读取，分别由对应状态模块维护。

### 5.4.1 固定菜单与连续绘图操作约定

2026-10-30 用户确认以下交互，作为固定工具栏的当前产品约定：

| 操作 | 菜单与工具状态 |
| --- | --- |
| 点击菜单按钮展开 | 展开该面板并退出原绘图工具；同一时间只展开一个菜单 |
| 选择图形子项 | 保持菜单展开，激活对应画布工具并高亮子项 |
| 普通图形工具下单击或悬停画布 | 菜单和当前工具保持；不创建图形、不显示跟随鼠标的默认尺寸预览 |
| 完成一次普通图形拖拽绘制 | 菜单保持展开；普通图形工具继续激活，保留高亮和十字光标，可连续绘制 |
| 普通图形手势无效或落在禁止绘制的位置 | 取消本次手势和远端预览，保留工具，允许重新绘制 |
| 再次点击当前菜单按钮 | 收起菜单、退出绘制并恢复普通光标；取消当前草稿，保留已完成图形 |
| 切换其他菜单 | 关闭原菜单、展开目标菜单并退出原绘图工具 |
| 选择其他画布工具或指针／手形按钮 | 收起菜单并切换到目标工具 |
| 菜单展开时按一次 Escape | 菜单层消费按键，同时收起菜单并回到指针工具；工具退出生命周期负责清理草稿 |

实现边界：

- 菜单展开由控制器局部状态维护；子项高亮来自 `tool-store.current`，不另外保存“上次选中项”冒充当前工具。
- 连续绘制仅涵盖 `shape-draw.tool.ts` 共用的两种数据处理矩形（`rect` / `rect-square`）、椭圆、多边形、开始、结束和用户图形。连线、表格、区域及拖拽创建仍按各自的工具行为完成，不推断为已支持连续绘制。
- 单次手势结束统一发送协作提交或重置、清空交互会话并恢复十字光标；退出工具时清理本地和远端草稿，不删除正式图形。
- 临时悬停和缩放手柄离开后，按工具注册表恢复当前工具光标，禁止直接将恢复光标固定为 `default`。
- 子项高亮样式由 `DraggableToolIcon.vue` 自身维护，避免依赖父组件作用域样式穿透子组件。
- 退出键优先级仍遵循 [[ICCE画布退出键分层取消设计]]；此处菜单关闭引起的工具退出属于同一菜单操作的收尾，不继续分发按键去清空选区。

历史与状态：2026-08-26 的固定菜单采用点击外部关闭；2026-10-30 起由上述主动收起规则替代。产品交互已确认，代码位于 `jd_ipd` 工作区、基于提交 `66ec0345a` 的未提交改动；既有元信息中的 `source_ref` 仍代表原工具条结构基线。本轮定向 Vitest 回归 4 个文件、37 项通过，差异检查通过；实际浏览器中的最新菜单和光标行为尚待验证，不记为已完成浏览器验收。

### 5.4.2 普通图形仅拖拽绘制与小尺寸反馈

当前结论（2026-10-30 用户确认）：普通图形仅通过按住左键拖拽创建；选中图形工具后只显示十字光标，悬停或单击不生成图形，也不显示跟随鼠标的默认尺寸预览。

#### 手势和尺寸

- 起笔时记录画布起点和缩放倍率，按屏幕上的移动距离判定拖绘，阈值为 6 像素；该距离不是图形最小尺寸。
- 未超过阈值时不显示图形预览；单击或轻微抖动后松手静默取消本次手势，不提示尺寸不足，当前工具继续保持激活。
- 超过阈值后显示真实拖拽尺寸的预览。舞台在逐帧事件合并前锁定 `hasDragged`，即使同一帧拖出阈值又移回起点，也保持拖拽语义，不退回单击。
- 不要求宽、高同时超过阈值；长距离单轴移动也属于拖拽，但最终几何仍须通过图形最小尺寸校验。
- 松手时读取释放位置，避免最后一次移动事件未处理而使用旧坐标提交。
- 默认尺寸不参与画布自由拖绘的预览、下限或失败兜底。工具栏拖放创建继续沿用自身默认尺寸和完成行为。

#### 小尺寸预览和提交

- 小于默认尺寸但满足最小尺寸的图形按实际边界创建；不能突然扩大到默认尺寸或最小尺寸。
- 普通图形最小宽高 36、菱形最小边长 40，用户图形保留最小宽度 20 和头像加文本区域约束；这些尺寸仍按画布单位校验。
- 拖拽期间不足最小尺寸时，保留真实小尺寸预览，显示红色虚线边界和最小尺寸提示；拖大至有效尺寸后取消错误提示。
- 已进入拖拽但松手时仍不足最小尺寸：提示并取消创建、重置协作预览，保留工具供重试，不自动扩充几何。
- 开始／结束、菱形的比例与用户图形的头像／文本结构约束从预览阶段生效；反向拖拽时固定起点侧，比例约束不导致图形越过起笔位置。
- 本地预览、协作更新和提交共用 `resolveShapeDrawingBounds` 的几何结果，统一整数化；既有区域校验和正式创建命令继续执行。区域、表格和连线不套用普通图形的新拖绘规则。
- 连续绘制结束后清空单次会话，鼠标移动不会重新建立悬停预览。菜单收起、切换工具及退出键行为沿用上一节约定。

#### 取舍、历史和实施状态

曾在本轮实现单击按默认视觉尺寸创建，并按画布缩放换算，但用户反馈默认预览持续跟随鼠标会削弱自由绘制感，随后明确要求撤回。该方案已从当前实现移除，不作为仍受支持的模式或待开发功能保留。

本节替代原先“低于手势阈值取消、超过阈值就将预览扩充至最小尺寸”的普通图形行为；原有最小尺寸约束仍保留，满足方式改为无效反馈与拒绝创建。区域绘制和选区缩放的既有最小尺寸扩充规则不在本轮修改范围。

实施状态：基于 `jd_ipd` 提交 `66ec0345a` 的未提交工作区实现。最新定向 Vitest 回归为 7 个文件、73 项通过，差异检查通过；最新仅拖拽版本未完成实际浏览器验收，不将此前单击方案的构建或验证结果写为本版本的验收结论。

### 5.5 当前固定工具项与命名约束

- 左侧工具按图表类型和权限生成：图形菜单、区域、模版和字典不会在无权限时渲染。
- 底部工具当前包含指针、网格、全屏、视图自适应、缩放和比例状态等能力。
- 底部的 `grid` 文案和语义是“网格”；当前没有接入表格图形，不能把该按钮解释为表格或表格创建入口。
- `jump-line` 的配置和显示状态暂时保留，但固定工具栏入口当前隐藏；重新开放时应继续复用现有显示状态和事件链路。
- “数据处理”和“判断”等图形名称，以及“边框颜色”“背景颜色”“文字颜色”“文字背景”等属性名称，统一从 `toolbar-meta.ts` 读取，禁止在上下文菜单模型和固定工具栏模型中各自维护一份文案。

### 5.6 动作命名与分发边界

动作名称由现有注册表统一提供：

- `CONTEXTUAL_CANVAS_ACTIONS` 只描述应用层真正执行的画布变更，如删除、清空区域、更新属性、插入图形和层级调整。
- `TOOLBAR_ACTIONS` 复用上述画布动作，并补充模版、区域编辑、区域适配、引用活动图和取消区域草稿等界面入口。
- `ContextualCanvasAction` 是应用层持久化变更的类型，不应因为存在固定工具栏而移除。
- `ContextualCommandType` 不再作为重复的界面动作联合类型维护；界面层统一使用 `ToolbarAction`，进入应用层时再收窄为 `ContextualCanvasAction`。
- `quoteActivityIntoRegion` 的实际实现仍在区域内容用例中，当前通过上下文意图统一分发，并在业务层确认后执行，不是被删除或仅保留占位动作。

固定工具栏的视图命令仍由 `toolbar-command.ts` 处理视图缩放、全屏、模版和字典等入口；上下文工具菜单的正式画布变更继续进入应用命令。动作注册表负责命名和类型约束，不替代应用层的业务准入和变更执行。

### 5.7 扩展规则

新增按钮时按以下顺序判断：

1. 先确认它属于固定工具栏还是上下文工具菜单，不能因为视觉相似就合并入口。
2. 先复用现有按钮角色或上下文模型类型，不为单个按钮新建专用状态或组件。
3. 展示文案、图标和提示先补充到 `toolbar-meta.ts`，两个工具条都从配置读取。
4. 持续接管画布事件的按钮进入 `CanvasToolType` 和 `tool-store`；视图显示切换进入 `canvas-display-store`；一次性入口通过动作注册表和已有意图分发。
5. 上下文菜单的正式图形变更必须使用应用命令；固定工具栏模型和通用按钮不直接写入图形数据。
6. 新增数字徽标时只在工具配置声明徽标数据源和展示参数，数量订阅与数据源适配放在徽标逻辑中，`ToolButton` 只负责建立映射和渲染。

## 6. 弹窗边界适配

### 6.1 为什么适配放在弹窗层

上下文工具条的位置由选区锚点和工具条真实尺寸决定。直接增大工具条整体安全边距会改变工具条锚点，可能造成原有视觉位置偏移，却不能保证右侧打开的颜色面板或菜单本身完整可见。

因此，工具条继续使用原有整体安全边距，弹窗通过 `ToolbarPopup.vue` 在自身层修正位置。这样可以把“工具条在哪里”和“弹窗如何避让边界”分成两个独立问题。

### 6.2 实际可视边界

弹窗挂载到 `.icce-left-canvas`。`ToolbarPopup` 将该容器的矩形与浏览器视口求交，得到真正可用的边界：

```text
左边界 = max(画布左边界, 视口左边界)
右边界 = min(画布右边界, 视口右边界)
上边界 = max(画布上边界, 视口上边界)
下边界 = min(画布下边界, 视口下边界)
```

弹窗与边界之间保留独立的边缘间隙，不复用工具条整体边距。当前默认弹出间距和边缘间隙均为 8 像素。

### 6.3 定位顺序

`toolbar-popup-position.ts` 只计算平移量，不改变工具条和触发按钮：

1. 先按组件库默认的向下位置计算。
2. 如果左右越界，将弹窗水平夹紧到可视边界内。
3. 如果向下展开超出下边界，尝试移动到触发按钮上方。
4. 如果上方也无法完整容纳，则将弹窗夹紧到可视区域内作为兜底。
5. 将修正量施加到弹窗外层，保留组件库的点击外部关闭和弹窗尺寸计算。

计算时会先扣除上一次已经应用的平移量，再重新计算基础矩形，避免连续帧在上一次结果上重复累加。

### 6.4 生命周期与尺寸变化

弹窗只在打开期间注册窗口尺寸、画布滚动和 `ResizeObserver` 监听；关闭时统一清理监听、观察器、待执行动画帧并重置修正量。

观察对象包括弹窗本身和画布容器，覆盖以下变化：

- 颜色选择器或复杂面板内容尺寸变化。
- 画布面板尺寸变化。
- 浏览器窗口缩放。
- 画布容器滚动。

## 7. 维护规则

### 7.1 新增按钮

1. 先判断是否能用现有 `command`、`toggle`、`options`、`color` 或 `number` 描述。
2. 在模型层添加按钮描述、可见条件和当前值计算。
3. 在业务编排层提供必要的权限和状态依赖。
4. 复用统一命令事件，不在 `ToolbarControl` 中新增业务写入逻辑。
5. 只有存在真正复杂的多段交互时，才扩展 `composite` 及其专用面板。

### 7.2 新增弹窗

- 必须复用 `ToolbarPopup`，不要为单个按钮重新接入组件库触发器。
- 弹窗内容尺寸固定或可变时，都必须经过统一边界修正。
- 需要面板内部提示时，复用 `ToolbarPopupTooltip`，不要在每个面板重复实现提示容器。
- 定位逻辑变化应优先修改纯函数并补充边界测试，不在业务按钮中写坐标修正。

### 7.3 业务边界

- 权限判断属于上下文工具条业务层或领域规则，不属于通用渲染组件。
- 图形类型是否合法属于领域服务，不由菜单组件自行推导。
- 正式画布变更必须继续进入现有应用命令入口。
- 弹窗定位状态属于界面状态，不进入图形模型、持久化数据或协作协议。

## 8. 取舍与后果

### 8.1 正面影响

- 按钮的描述、可见性和渲染方式集中，新增常规按钮不再需要扩散多个专用组件。
- 业务命令和界面渲染边界清晰，颜色、菜单和复杂面板可以共享事件契约。
- 弹窗边界适配集中在弹窗层，工具条整体定位不再被单个大弹窗牵连。
- 面板生命周期监听只在打开期间生效，减少隐藏按钮实例的无效监听。
- 模型和定位纯函数可以在不依赖浏览器交互的情况下单独验证。

### 8.2 维护代价与风险

- `ToolbarItem` 联合类型仍可能随着新能力增长，需要控制 `kind` 数量，避免重新回到“一种按钮一个类型”。
- 当前弹窗翻转需要识别组件库生成的顶部位置样式；如果组件库的弹窗位置标识变化，需要同步调整适配层。
- 当弹窗自身宽高超过整个画布可视区域时，单纯平移无法让内容物理上完整显示；后续若出现此类面板，需要引入尺寸约束、滚动或响应式布局。
- 通用模型降低了按钮组件数量，但业务层仍需维护目标类型、权限和选项规则的映射关系。
