# 售后记录数据库表设计

## 范围与依据

本设计覆盖后台设备修改记录和大屏售后记录：按设备查看、关键字查询、新建、编辑、详情及历史版本，内容支持文字、图片和视频。依据知识库 [[售后记录功能与后端接口契约]]、[[运维中心大屏功能优化需求分析]]，以及 `src/views/admin/modificationRecords/model.ts`、`record-data.ts` 和提交 `d8860d9`。知识库中的前端未提交状态已过时：该功能已在上述提交落地，但记录与媒体仍存于前端内存，后端尚未对接。设备、合同评审和用户的正式表结构与接口尚未确认，以下为待后端核对的设计，不代表现网已有表。

假设数据库为 MySQL 8.0、InnoDB、utf8mb4；主键采用应用生成的 UUID 字符串，外部系统标识统一转换为字符串。时间使用 UTC 的 `DATETIME(3)`，接口使用带时区的 ISO 8601。字段长度、数据库版本、设备及用户标识类型须与后端约定后调整。设备和用户由既有系统管理，不重复建设，也不假设跨系统外键。

## 表与关系

- `equipment_modification_record`：当前版本及列表查询字段，每条记录关联一个设备，一台设备可有多条记录；创建后不得更换关联设备。
- `equipment_modification_version`：每次保存的完整、不可变快照，包括第 1 版及当前版；`(record_id, version)` 唯一。
- `equipment_modification_media`：上传文件元数据和稳定存储位置，文件本体存对象存储。
- `equipment_modification_version_media`：版本与媒体的多对多引用，保留历史版本引用，避免编辑后误删文件。

```sql
CREATE TABLE equipment_modification_record (
  id VARCHAR(36) NOT NULL,
  equipment_id VARCHAR(128) NOT NULL COMMENT '设备主数据标识',
  equipment_number VARCHAR(128) NOT NULL COMMENT '保存时设备编号',
  equipment_name VARCHAR(255) NOT NULL DEFAULT '' COMMENT '保存时设备名称',
  review_id VARCHAR(128) NULL COMMENT '合同评审标识，可缺省',
  contract_number VARCHAR(128) NOT NULL DEFAULT '',
  title VARCHAR(255) NOT NULL,
  keywords JSON NOT NULL COMMENT '字符串数组，保留顺序',
  content_html LONGTEXT NOT NULL,
  version INT UNSIGNED NOT NULL,
  created_by_id VARCHAR(128) NULL,
  created_by_name VARCHAR(255) NOT NULL DEFAULT '',
  created_at DATETIME(3) NOT NULL,
  updated_by_id VARCHAR(128) NULL,
  updated_by_name VARCHAR(255) NULL,
  updated_at DATETIME(3) NULL,
  PRIMARY KEY (id),
  KEY idx_equipment_created (equipment_id, created_at DESC, id DESC),
  KEY idx_created (created_at DESC, id DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE equipment_modification_version (
  id VARCHAR(36) NOT NULL,
  record_id VARCHAR(36) NOT NULL,
  version INT UNSIGNED NOT NULL,
  saved_by_id VARCHAR(128) NULL,
  saved_by_name VARCHAR(255) NOT NULL DEFAULT '',
  saved_at DATETIME(3) NOT NULL,
  snapshot JSON NOT NULL COMMENT '该版本完整记录快照',
  PRIMARY KEY (id),
  UNIQUE KEY uk_record_version (record_id, version),
  CONSTRAINT fk_mod_version_record FOREIGN KEY (record_id)
    REFERENCES equipment_modification_record (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE equipment_modification_media (
  id VARCHAR(36) NOT NULL,
  original_name VARCHAR(512) NOT NULL,
  media_type VARCHAR(16) NOT NULL COMMENT 'image 或 video',
  mime_type VARCHAR(128) NOT NULL,
  size_bytes BIGINT UNSIGNED NOT NULL,
  storage_key VARCHAR(1024) NOT NULL COMMENT '对象存储稳定 key，不保存临时签名 URL',
  uploaded_by_id VARCHAR(128) NULL,
  uploaded_at DATETIME(3) NOT NULL,
  PRIMARY KEY (id),
  KEY idx_uploaded_at (uploaded_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE equipment_modification_version_media (
  version_id VARCHAR(36) NOT NULL,
  media_id VARCHAR(36) NOT NULL,
  PRIMARY KEY (version_id, media_id),
  KEY idx_media (media_id),
  CONSTRAINT fk_mod_vm_version FOREIGN KEY (version_id)
    REFERENCES equipment_modification_version (id),
  CONSTRAINT fk_mod_vm_media FOREIGN KEY (media_id)
    REFERENCES equipment_modification_media (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

## 保存与读取约定

1. 新建时校验设备、标题、正文和媒体，事务内插入主记录及版本 1 快照和媒体引用；创建人、创建时间不随编辑改变。正文至少包含非空文本或有效图片/视频。关键字按中英文逗号或换行拆分、去空和去重。
2. 编辑时设备关联不可更换，服务端应拒绝与原记录不一致的设备 ID，不得只依赖前端禁用选择。编辑请求携带读取时的 `version`；事务内按 `id` 和旧版本号更新主记录，更新条数为 0 时返回版本冲突，让用户重新加载，禁止静默覆盖。随后插入新版本完整快照和引用，任一步失败回滚。保存人和时间取服务端认证身份与服务端时间。首版 `updated_*` 为 null。
3. 快照保存对应版本的完整 `ModificationRecord`：设备的 id、编号、名称、评审 ID、合同号，标题、关键字、净化后的 HTML、媒体元数据、创建及修改人/时间、版本号。历史详情读取快照，不关联当前设备或用户名称，以免主数据变化改写历史。版本行的保存人和时间用于历史列表，首次操作显示“新建”，其余显示“编辑”。历史列表按版本降序，并排除当前版本；当前版本仍须保存快照。
4. 后台列表按设备 ID 精确筛选，关键字对设备编号、标题、关键字和创建人姓名做大小写不敏感的包含匹配；按创建时间倒序、ID 倒序分页。大屏先通过现有模块接口取得 `equipmentId`，再按设备 ID 查询同一数据。包含查询和 JSON 搜索不能依赖上述普通索引，高数据量时根据实际数据库与查询量评估全文或专用搜索索引；注意转义 LIKE 的 `%`、`_`。
5. 上传接口返回媒体 ID 和可供编辑器使用的稳定受控地址；保存时服务端解析并校验正文引用与提交的媒体 ID 一致、文件存在且调用者有权使用。不能持久化前端 `blob:` URL 或短期签名 URL。读取时按存储 key 生成授权访问地址；若需要动态签名，使用媒体 ID 或稳定地址在返回时重写 HTML。服务端也应净化 HTML 并限制标签、属性及 URL 协议，前端净化不能替代服务端校验。
6. 上传后取消编辑可能产生未引用文件。采用延迟清理：仅清理超过约定宽限期、没有任何版本引用的上传对象；清理前与保存流程协调并再次检查引用，避免并发删除。已有历史版本引用的文件不得清理。当前功能未定义删除、版本回滚及历史保留期限，本设计不预设这些行为。

## 对接前待确认

- 正式设备候选是否来自合同评审，以及设备 ID、模块 ID、合同号的映射和权限范围；大屏模块 ID 不能直接当作设备 ID。
- 数据库类型与版本、ID 格式、字符长度、时区和既有用户/设备主数据约束。
- 媒体存储、访问授权、大小及类型限制、上传清理宽限期和历史保留策略。
- 搜索量、分页排序及记录权限规则；现有演示数据不能证明后端权限或生产数据规模。
