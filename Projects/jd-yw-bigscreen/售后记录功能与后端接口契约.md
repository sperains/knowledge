# 售后记录功能与后端接口契约

当前结论：前端售后流水账页面已实现，记录及媒体仍使用内存数据，后端尚未开发。本文是售后功能业务规则与完整接口建议的知识库正文；接口方法、路径及未决规则不视为已获后端确认。

## 命名与范围

- 文档中的功能名称统一为“售后记录”，版本追溯称为“修改历史”，避免混淆业务记录与编辑版本。
- 2026-10-28 用户明确纠正：只修改文档名称，不修改界面。当前后台菜单、新增按钮和详情标题仍使用“修改记录”；大屏页面入口原本称“售后记录”。本次未实施界面更名，旧菜单命名保留为当前实现事实。
- 一台设备可以关联多条记录，每条记录有独立标识；设备标识用于关联，设备编号不是记录主键。
- 支持文本、图片、视频，无审核流程；每次保存保留完整版本，可查看旧内容和媒体。
- 本文对应原始需求 R5；原文及早期分析见 [[运维中心大屏功能优化需求分析#2. 文档明确要求]]。

## 当前前端实现与边界

- 后台入口为 `/admin/modificationRecords/list`，代码目录为 `src/views/admin/modificationRecords/`。`ModificationRecord` 等类型保留既有代码标识，文档术语更正不改变目录、路由或数据结构。
- 后台支持设备／关键字查询、新增、查阅和修改；有旧版本时才显示“修改历史”。查阅只显示当前内容，历史列表只列旧版本，历史详情复用同一详情组件。
- 大屏按当前模块解析出的 `equipmentId` 精确筛选记录，提供列表、分页、总数与详情；新增跳转后台并带入设备。设备解析失败或切换时不展示其他设备数据。
- 后台与大屏共用当前内存数据源。页面切换保留，刷新恢复初始数据；图片、视频使用本地 `blob` 地址，尚未上传服务器。
- 前端已完成 VXE 弹窗、鼠标／触摸拖拽、共用描述区样式和后台操作图标；代码入口为 `src/views/admin/modificationRecords/`、`src/views/bigscreen/device/realtime/afterSales.vue`，触摸适配位于 `src/exts/vxetable.ts`，共用描述区样式位于 `src/styles/main.less`。项目内的配套文档已移除，售后功能与接口契约集中在本专题维护。

## 数据结构

类型定义维护于 `src/views/admin/modificationRecords/model.ts`。代码目录、路由及 `ModificationRecord` 类型沿用既有标识；文档功能名称与当前界面名称不同，不表示已经实施界面更名。

| 类型 | 字段 | 含义 |
| --- | --- | --- |
| RecordAuthor | id、name | 人员标识与名称。正式接口由登录身份确定，不接受客户端冒充人员。 |
| RecordEquipment | id、number、name、reviewId、contractNumber | 设备标识、设备编号、设备名称、合同评审单标识与合同号；编号不代替独立记录标识。 |
| RecordMedia | id、name、type、mimeType、size、url | 媒体标识、文件名、图片／视频类型、格式、字节大小与展示地址。 |
| ModificationRecordDraft | equipment、title、keywords、contentHtml、media | 表单内容。关键字为去重后的字符串数组，富文本采用 HTML，媒体单独保留元数据。 |
| ModificationRecord | id、createdBy、createdAt、updatedBy、updatedAt、version，以及表单内容 | 当前版本。新建为第 1 版，修改后递增。首次创建时修改人和修改时间为空。 |
| RecordVersion | id、recordId、version、savedBy、savedAt、snapshot | 保存事件与当次完整记录快照，包括当时的设备、内容和媒体。 |

时间字段采用带时区的 ISO 8601 字符串；页面统一使用 `src/utils/index.ts` 的 `formatDateTime` 按本地时间显示为 `YYYY-MM-DD HH:mm:ss`，空值显示“—”。正式环境由服务端生成记录标识、人员、时间和版本号。当前模拟数据不作为已有后端字段约定。

## 版本规则

新建同时产生第 1 版快照；每次编辑保存同时更新当前记录并追加新快照。提交人及提交时间保持首次提交信息，修改人及修改时间记录本次操作者。已保存快照不得随表单继续编辑而变化。

历史版本查看应展示整份快照，而非用当前版本的设备、内容或媒体覆盖旧版本。删除当前内容中的图片或视频，不应影响历史版本引用的媒体；媒体清理和保存期限需在后端实现时确认。

## 后端接口清单（建议契约，待双方确认）

后端需要提供以下 8 项接口能力，后台与大屏共用记录查询和详情接口。下表使用建议前缀 `/api_java/admin/modificationRecords`，以 `B` 表示；方法、路径及新增字段尚未与后端确认，前端目前未请求这些地址。

| 接口 | 建议方法与路径 | 入参 | 成功时的 `data` |
| --- | --- | --- | --- |
| 设备候选查询 | `GET B/equipments` | `key?`、`page`、`limit` | 合同评审单关联设备的分页结果，行数据为 `RecordEquipment`。 |
| 售后记录列表 | `GET B` | `equipmentId?`、`key?`、`page`、`limit` | 当前版本的摘要列表及总数，供后台与大屏使用。 |
| 当前记录详情 | `GET B/{recordId}` | 路径中的记录标识 | 完整 `ModificationRecord`，供查阅和编辑初始化使用。 |
| 新增记录 | `POST B` | 设备标识、标题、关键字、富文本和媒体标识 | 保存后的完整 `ModificationRecord`，版本为 1，同时保存第 1 版快照。 |
| 更新售后记录 | `PUT B/{recordId}` | 路径中的记录标识、表单内容、`expectedVersion` | 保存后的完整 `ModificationRecord`，版本递增，同时保存本次快照。 |
| 修改历史列表 | `GET B/{recordId}/versions` | 路径中的记录标识 | 旧版本摘要数组，按版本倒序，当前版本不重复列入。 |
| 指定历史详情 | `GET B/{recordId}/versions/{versionId}` | 记录标识、版本标识 | 完整 `RecordVersion`，包含当时的 `snapshot`。 |
| 图片／视频上传 | `POST B/media` | `multipart/form-data` 中的 `file` | `RecordMedia`，包括媒体标识、名称、类型、格式、大小及访问地址。 |

### 通用响应与分页

建议沿用项目已有的 `{ code, msg, data }` 包装，成功 `code = 0`，失败返回可展示的 `msg`。失败码及 HTTP 状态按后端现有规范确认，需能区分记录不存在、无权限、表单错误、媒体错误及版本冲突。版本冲突应提示重新加载后再修改，不覆盖其他人的保存结果。

设备候选和售后记录列表沿用现有 `IPage` 分页字段，`total` 在本功能中必须返回。请求页码从 1 开始，默认 `limit = 10`，页面支持 10、20、50 条。空列表的建议响应如下：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "current_page": 1,
    "per_page": 10,
    "last_page": 1,
    "total": 0,
    "data": []
  }
}
```

记录、设备、版本和媒体标识建议统一传字符串，版本号使用正整数；时间字段按前述 ISO 8601 约定返回。

### 查询字段与筛选口径

- 设备候选：`key` 搜索设备编号、设备名称、合同号；每项返回 `id`、`number`、`name`、`reviewId`、`contractNumber`。`reviewId` 是合同评审单标识，不能用合同号代替设备标识。
- 记录列表：`equipmentId` 按设备标识精确匹配；`key` 在设备编号、标题、关键字和提交人名称中模糊匹配，字段之间取“或”，与设备条件取“且”。未传筛选项时不应用该项筛选，但仍受账号可见范围限制。
- 记录列表的每行至少返回 `id`、`equipment`、`title`、`keywords`、`createdBy`、`createdAt`、`updatedBy`、`updatedAt`、`version`；正文和媒体可留给详情接口返回。`equipment`、人员对象结构与上方数据结构表一致。
- 建议列表按提交时间倒序，时间相同时增加稳定的标识排序；`total` 为当前筛选条件下的总数。
- 大屏查询必须传当前设备的 `equipmentId`，不能用模块标识或设备编号替代；后台选择设备筛选时使用同一字段。
- 列表行的 `version > 1` 即可判断是否显示“修改历史”，不额外要求重复的历史标记字段。

### 新增与修改请求

建议正式接口仅接收设备、媒体的标识，由服务端解析关联信息；当前前端表单里的完整 `equipment`、`media` 对象需在接口接入时转换，不能直接作为可信关联数据保存。

新增请求示例：

```json
{
  "equipmentId": "eq-001",
  "title": "设备参数调整与现场复查",
  "keywords": ["参数调整", "复查"],
  "contentHtml": "<p>已完成参数调整，后续继续观察。</p>",
  "mediaIds": []
}
```

修改使用相同表单字段，另附 `expectedVersion`，其值为打开编辑时取得的版本号；记录标识放在路径中。`expectedVersion` 是建议新增的接口字段，当前模拟数据源尚未实现并发检查。

- 设备、非空标题及有效正文必填。正文只有图片或视频时也允许保存；关键字与媒体可以为空数组。
- 关键字去除首尾空白、空项和重复项；正文中的媒体应与 `mediaIds` 对应，且属于允许引用的媒体。
- 提交人、修改人根据登录身份确定，时间、记录标识和版本号由服务端生成，不接收客户端指定这些审计字段。
- 修改是否允许更换关联设备仍待业务确认；接口需按最终规则校验，历史快照始终保留当时的设备信息。

### 历史版本与保存一致性

历史列表建议只返回 `id`、`recordId`、`version`、`savedBy`、`savedAt`，不批量携带完整 HTML 和媒体；页面点击“查看”后再请求指定历史详情。

历史详情返回 `RecordVersion`，其中 `snapshot` 是当次完整 `ModificationRecord`：包括标题、关键字、正文、设备、媒体、提交／修改人员及时间。不能用当前记录的字段或当前设备资料回填旧版本。

1. 新增记录和第 1 版快照必须同时成功或同时失败。
2. 每次保存均产生完整快照，更新当前记录、递增版本号及写入快照应在同一事务中完成。
3. 修改时检查 `expectedVersion`，版本不一致则拒绝本次更新，不产生部分记录或额外快照。
4. 创建人员和创建时间保持不变；修改人员及修改时间记录本次保存者。
5. 已保存版本不可被后续修改覆盖；历史列表只展示旧版本，首次创建后应返回空历史数组。

### 媒体与访问要求

- 图片和视频可共用上传接口，后端根据文件校验类型，返回前述 `RecordMedia` 字段；上传格式及大小上限待约定，前端据此配置编辑器。
- 返回的地址必须支持页面展示和视频播放，不能使用浏览器本地 `blob` 地址作为正式上传结果。如果采用有期限的地址，读取当前或历史详情时需提供当次可访问的地址，持久关联依赖媒体标识。
- 当前记录删除某个媒体引用后，旧版本引用的文件仍应可读取；临时上传文件的清理、历史媒体保留期限待约定。
- 沿用现有登录凭证，对设备候选、记录查询、保存、历史和媒体访问执行相应权限校验；富文本需在服务端校验和净化，不能只依赖前端过滤。

### 可复用的当前设备解析接口

已存在 `POST /api_java/api/device/getModesByModeId`，请求为 `{ "module_id": "当前模块标识" }`。前端从响应数组中匹配当前 `moduleId`，取得 `equipmentId`、`equipmentNumber`、`name`。如果该接口能稳定返回这些字段，无需额外新建模块转设备接口；它不代替合同评审单设备候选的分页搜索接口。

### 联调顺序与待确认项

先确认设备标识与候选来源，再对接列表／详情、新增／修改及版本事务，最后接入上传和历史媒体展示。前端需将当前内存筛选换成服务端分页；查阅和修改先获取详情，历史列表与指定快照分别请求；保存后重新查询列表。

后端开发前需确认最终路径和错误码、字段长度与文件限制、账号权限口径、编辑时能否更换设备，以及历史和媒体的保留规则。本文提供接口建议，不表示上述未决规则已获业务确认。
