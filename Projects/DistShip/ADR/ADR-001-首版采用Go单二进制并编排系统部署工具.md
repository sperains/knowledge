# ADR-001 首版采用 Go 单二进制并编排系统部署工具

- 状态：Accepted
- 日期：2026-08-12
- 作者：Codex
- 相关领域：技术选型、命令行架构、软件分发、部署边界
- 所属项目：DistShip

---

## 背景（Context）

DistShip 的核心产品诉求是便于分发：普通用户应能直接安装和运行命令，不需要额外准备新版 Bash、配置解析器或语言运行时。工具还需要可靠处理 TOML 配置、中文终端排版、结构化输出、本机部署历史、跨平台测试和多架构发布。

现有 Bash 脚本已经验证了本地构建、Git 状态检查、SSH 连接和 `rsync` 增量上传的基本流程，但单文件脚本在配置解析、复杂交互、数据持久化和跨平台兼容方面的维护成本会持续增加。同时，用户已经拥有成熟的 Git、SSH 和 `rsync` 配置，工具没有必要重新实现这些协议。

## 考虑方案（Options）

### 方案 A：先发布 Bash 版本，后续再使用 Go 重写

优点：

- 可以直接复用当前脚本，短期开发量较少。
- 早期功能验证速度快。

缺点：

- 用户环境中的 Bash 和系统工具版本差异会扩大分发与支持成本。
- TOML、JSON、中文宽度、文件锁和结构化输出需要额外依赖或复杂脚本实现。
- 后续 Go 重写会产生第二次迁移，并增加命令和配置兼容风险。

### 方案 B：首版直接使用 Go，继续调用系统 Git、SSH 和 rsync

优点：

- 可发布不依赖语言运行时的单一二进制，并进行 macOS、Linux 多架构交叉构建。
- 配置解析、历史记录、错误模型、终端输出和自动化测试更易保持结构化。
- 继续复用用户现有的 Git 与 SSH 配置，不承担凭据管理和协议重写成本。

缺点：

- 首版需要重新实现已经由 Bash 原型验证过的流程。
- 运行时仍依赖目标机器上的 Git、SSH、`rsync` 和项目构建工具。
- macOS 与 Linux 外部命令行为差异仍需真实系统测试。

### 方案 C：使用 Go 并在进程内实现 Git、SSH 和文件同步

优点：

- 理论上可以进一步减少外部命令依赖。
- 可以完全控制协议调用和错误结构。

缺点：

- 难以完整复用用户已有的 SSH 别名、代理、跳板机和认证行为。
- Git 与增量同步实现复杂，容易偏离工具核心价值。
- 安全审计、兼容性和长期维护成本显著增加。

## 决策（Decision）

DistShip 从 `v0.1.0` 起直接使用 Go 1.26 开发，并发布 `CGO_ENABLED=0` 的单一二进制，不发布公开 Bash 版本。

命令使用 Cobra，配置使用 TOML 与 `pelletier/go-toml/v2`，终端排版使用 Lip Gloss；交互确认、进程执行、JSON Lines 历史和自动化测试优先使用 Go 标准库。

DistShip 只负责编排，不在进程内重新实现 Git、SSH 和增量同步协议：

- 通过 `os/exec` 调用本机 `git` 获取只读仓库状态。
- 通过本机 `ssh` 复用用户的 SSH 配置和认证链路。
- 通过本机 `rsync` 执行增量上传。
- 通过配置的参数数组直接执行项目构建工具，不默认经过 Shell 二次解释。

首版支持 macOS Apple Silicon、macOS Intel、Linux ARM64 和 Linux x86-64。Windows 不属于 `v0.1.0` 支持范围。

分发使用 GoReleaser 与 GitHub Actions 生成 GitHub Release 资产和 SHA-256 校验文件；Homebrew Tap 作为 macOS 首选安装入口，`go install` 只作为开发者补充入口。

## 后果（Consequences）

### 正面影响

- 普通用户无需安装 Go 或额外脚本运行时，可以直接下载或通过 Homebrew 安装。
- 配置、交互、历史和错误处理可以使用明确的数据结构与自动化测试保障。
- 一次实现即可覆盖目标系统和架构，避免公开 Bash 版本到 Go 版本的二次迁移。
- SSH 凭据和复杂连接能力继续由用户已有配置负责，DistShip 不接触私钥内容。

### 负面影响

- 首版开发成本高于直接整理现有 Bash 脚本。
- 用户机器仍必须安装 Git、SSH、`rsync` 和项目自身构建工具。
- 外部命令的版本与平台差异仍会影响行为，需要兼容检查和真实系统测试。
- Go 模块、发布产物和 Homebrew Tap 引入额外的供应链维护责任。

### 后续约束

- 新增核心依赖前必须说明标准库或现有三项依赖无法满足的需求。
- 禁止为了减少外部命令数量而直接引入 Git、SSH 或同步协议 SDK，除非形成新的 ADR。
- 构建命令必须优先使用可执行文件与参数数组，禁止默认使用 `sh -c`。
- 发布流程必须至少覆盖四个目标平台产物、校验文件和跨平台测试。
- Windows 支持必须先定义路径、权限、命令发现和传输协议，再通过新的决策记录评估。

## AI 指导原则

- 实现 DistShip 时必须以 Go 单二进制和便于分发为首要技术约束。
- 优先使用 Go 标准库，其次使用已确认的 Cobra、`pelletier/go-toml/v2` 和 Lip Gloss。
- 必须通过可替换的进程执行边界调用 Git、SSH、`rsync` 和项目构建工具，以便使用测试替身。
- 禁止让 DistShip 读取、保存或分发 SSH 私钥和密码。
- 禁止把旧 Bash 原型直接当作公开版本继续扩展；原型只用于行为对照和迁移验证。
