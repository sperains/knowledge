# 生成与更新开发日报

## 职责与输入

将已完成的工作按主题整理到 `Worklog/Daily/YYYY/MM/YYYY-MM-DD.md`。根据用户请求选择处理方式：

- **生成或补充**：读取目标日期的提交差异及用户补充的工作事实，确认完成结果后写入日报。
- **仅润色或精简**：以现有日报为事实来源，不重新统计提交，不补入后来发生的工作。

与 rewrite 组合调用时，由 report 决定事实范围、结构、文件操作和交付方式，rewrite 只负责精简表达与标点，不扩大内容范围。

## 执行流程

1. 确定日期和目标文件。优先使用用户指定日期或文件日期；生成当天日报时使用当前时区，相对日期先换算为绝对日期。
2. 阅读适用的 `AGENTS.md`、知识库说明、`Worklog/README.md` 和 `Templates/日报模板.md`，检查工作区差异与已有日报，保留用户补充及无关修改。
3. 生成或补充时，按本地规则指定的作者过滤当天非合并提交，排除其他作者及储藏产生的内部提交。用户提供的工作记录可作为补充，验证材料只用于判断事实，不进入正文。没有符合口径的工作时不生成空日报。作者或口径不明时先查本地规则和 Git 配置，仍无法确认则说明缺失信息，不扩大范围。
4. 按下方内容标准组织或精简正文。新增日报使用日期与日报标签的 YAML 元数据；更新时保留既有元数据、有效链接和用户手工补充，不静默覆盖。
5. 写入目标文件，按知识库规则追加修改日志。检查日期、章节、链接及本次差异；生成或补充时同时核对作者过滤结果。简短报告文件位置和实际未纳入的输入，不在回复中重复整篇日报。

## 内容标准

- 保持“今日概览”和“今日工作”。概览默认一句话，每个工作主题使用一个编号小节，只保留必要的成果条目，同一目标下的多个提交合并描述。
- 正文只陈述完成的能力、修复和结果。不写新旧实现对照、改动原因、内部机制、文件清单或提交标题流水账，也不记录提交时间和编号。
- 测试数量、测试命令、差异检查、类型检查及构建验收范围属于验证记录，不进入日报。
- “架构与经验沉淀”仅保留当天形成的可复用结论或约束，不复述今日工作，不展开实现对比；没有独立内容时省略。
- “相关资料”只链接明确关联且存在的设计文档或 ADR，不添加通用索引或空章节。
- 精简时保留事实和必要结构，优先删除重复表述，不为了字数删掉独立成果。不修改历史日报来补齐后续工作。

## 修改边界

只修改本次日报及规则要求的日志。生成或润色日报不授权修改项目方案、提交、推送或发布。
