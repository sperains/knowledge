# 生成开发日报

## 工作目标

把某一天已完成的开发工作整理成可读、可追溯、按主题归并的日报，写入 `Worklog/Daily/YYYY/MM/YYYY-MM-DD.md`。日报记录工作结果和经验，不复制提交记录，也不代替设计文档或架构决策。

## 执行流程

1. 确定日期。用户明确指定日期时使用指定日期，否则使用当前日期；涉及“昨天”等相对日期时先按当前时区换算成绝对日期。
2. 查找并阅读当前仓库及父级适用的 `AGENTS.md`、日报规则、知识库说明和 `Templates/日报模板.md`。若知识库已有 `Worklog/README.md`，以它补充日报口径。
3. 确认输入来源：默认读取目标日期内的 Git 提交，并按日报规则过滤作者；排除合并提交、其他作者提交、提交时间和提交编号；用户明确提供的工作记录、讨论结论和验证结果可以作为补充，但不得把没有证据的内容写成已完成；如果指定日期没有符合条件的工作，不生成空日报，也不虚构内容。
4. 阅读相关提交差异和必要的设计文档，按工作主题合并同一目标下的实现、修复和验证，不把每个提交机械地列成一个条目。只描述完成了什么以及产生的结果，不要追溯改动前的行为。
5. 生成日报内容：使用 YAML 元数据中的日期和日报标签；保持“今日概览”和“今日工作”结构；“今日工作”使用带序号的主题小节；只有当天形成可复用的架构、经验或明确约束时才添加“架构与经验沉淀”；只有存在明确关联的具体设计文档或 ADR 时才添加“相关资料”，并确保链接路径正确；使用中文自然描述，不直接复制提交标题。
6. 写入 `Worklog/Daily/YYYY/MM/` 下的目标路径。若目标日报不存在则新建；若已存在，先阅读并在不破坏已有内容的前提下更新，不能无提示覆盖用户手工补充。
7. 校验日期、章节、链接相对路径、作者过滤和合并提交排除结果，并说明生成或更新的文件以及未纳入的输入原因。

## 内容约束

- **只写完成了什么**：日报是工作结果清单，正文一律陈述当天完成的能力、修复和结果。禁止写改造前的旧实现、新旧对比、"原判定…现在…""改为…""之前…如今…"这类前后对照，也不写为什么这么改和内部机制推导。这些内容属于设计文档和架构决策，不属于日报。
- 即使写了"架构与经验沉淀"，也只写可复用的结论和约束，同样禁止新旧实现对比；拿不准就整节不写。
- 不记录提交时间、提交编号或合并提交。
- 不把提交标题、文件列表或测试文件明细直接当作日报内容。
- 同一主题的实现细节合并到同一个工作条目，避免流水账和重复描述。
- 没有实际内容时删除对应的小节，不保留空的“架构与经验沉淀”或“相关资料”。
- 不修改历史日报来补齐后来发生的工作；更正历史内容时必须明确日期和范围。
- 生成日报不等于创建 Git 提交；除非用户另外明确要求，不执行提交、推送或其他发布操作。

## 输入不足时

如果作者、日期或统计口径无法从本地规则确定，优先读取 `Worklog/README.md`、Git 配置和仓库说明。仍无法安全判断时，保守地不写入有争议的提交，并说明缺失信息；不要擅自扩大统计范围。
