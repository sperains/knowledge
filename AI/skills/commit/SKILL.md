# 提交改动

使用本技能处理用户明确授权的 Git 提交请求。调用 `$commit` 本身视为用户明确表达了创建提交的意图，但仍须遵守仓库中的 `AGENTS.md`、沙箱限制和命令审批规则。

## 流程

1. 查找并阅读当前仓库及其父级适用的规则文件，以及宿主提供的用户级规则；路径、文件名和规则载体按实际环境识别，优先遵守更具体的规则。
2. 使用 `git status --short`、`git diff --stat` 和 `git diff --name-only` 检查工作区。
3. 检查已修改、已暂存和未跟踪文件的内容，排除 `.env`、`.env.*`、凭据、密钥、环境配置和明显无关改动。不得擅自丢弃或覆盖用户改动。
4. 按真实改动归纳提交范围。相同问题合并描述，不为了增加条目拆分流水账。
5. 提交前运行 `git diff --check`；如果是代码改动，按风险运行相关测试或检查，并在提交结果中说明未运行的验证。
6. 根据仓库规范生成提交标题和正文。标题使用 `type(scope): 标题`；正文使用真实换行，条目按序号书写，避免重复。
7. 使用 `git add -- <已确认文件>` 精确暂存，不使用无范围的暂存方式。
8. 再次检查暂存区差异，确认没有环境配置、无关文件或意外内容后执行 `git commit`。
9. 提交完成后运行 `git status --short`，报告提交编号、标题、改动摘要和工作区状态。

## 提交信息规则

- `type` 使用 `feat`、`fix`、`refactor`、`chore`、`docs`、`style`、`test`、`perf` 等合适类型。
- `scope` 使用受影响的模块、业务范围或目录。
- 标题和正文准确描述实际改动，不夸大验证结果。
- 若仓库规则要求正文使用中文，则正文不得出现变量名、文件名、类名、接口名等英文词条；遵循仓库的具体规则。

## 用户级及仓库级规范

当用户级或仓库级规则存在时，至少遵循其中规定的提交信息格式和内容要求；以下格式仅作为没有更具体规则时的默认约束：

```text
type(scope): 标题

正文内容。如果有多处调整，正文按序号逐条罗列，每条之间不加空行。
```

- `type` 使用 `feat`、`fix`、`refactor`、`chore`、`docs`、`style`、`test`、`perf` 等类型。
- `scope` 填写受影响的模块、业务范围或目录。
- 正文必须包含真实改动信息；多处调整按真实、独立且可验证的改动使用序号列出。
- 正文使用真实换行，不得把换行写成字面量的反斜杠加 `n`。
- 如果规则要求使用中文，正文避免出现不必要的英文词条；技术标识是否保留以更具体的仓库规则为准。
- 相同功能、同一问题或高度相似的改动必须合并为一条，不得为了增加条目拆分流水账。
- 同源的实现步骤应合并，不拆分为多个类似功能条目。

## 提交前检查

- 确认用户明确要求创建提交；仅分析、检查或报告状态不等于授权提交。
- 确认正文条目之间没有重复或相似功能描述。
- 排除环境配置及无关改动。
- 不要提交 `.env`、`.env.*` 等环境配置文件，除非用户明确要求。

## 安全边界

- 未调用本技能或未获得其他明确提交请求时，不创建提交。
- 不执行 `git reset --hard`、`git checkout --`、删除文件或其他破坏性操作来整理工作区。
- 不为了消除授权提示而使用全局危险模式、关闭审批或扩大沙箱权限。
- 如果提交因沙箱或审批被阻止，说明具体阻塞点并请求必要的最小权限，不改用危险参数绕过。
- 如果改动范围不清楚，优先提交已确认文件；无法安全判断时，先报告待确认内容。

## 共享与运行时副本

- 知识库中的技能文件是可审阅、可追踪的共享来源。
- 如果宿主从安装目录加载技能，修改本文件后按宿主提供的安装或同步机制更新运行时副本，再依赖新的行为。
- 不在通用流程中写入用户目录、厂商特定的绝对路径或固定安装命令。
