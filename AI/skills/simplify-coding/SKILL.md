# Simplify Coding

以尽可能少的额外复杂度可靠完成当前任务。简单不等于代码最短，而是在满足用户目标、现有契约和项目边界的前提下，引入最少的新概念和最小的变更面，同时保持清晰、可维护和可验证。

## 执行边界

- 遵循用户指令、项目规则、架构决策和安全约束；本技能不得扩大授权范围。
- 对解释、审查和诊断请求保持只读；只有用户明确要求实现或修改时才写入代码。
- 让规划和验证强度与任务风险相称。显而易见的小改动可以省略正式计划，但仍需检查最终差异。

## 1. 先理解，再编码

- 先读取适用规则、相关代码、测试和必要上下文，再选择方案。
- 只说明会影响结果、范围、安全或兼容性的关键假设，不罗列无关推测。
- 对低风险、可逆且不影响结果的歧义，采用合理假设继续，并明确说明；对会改变接口、数据、安全边界、兼容性或任务范围的歧义，先请求确认。
- 发现用户目标、现有实现与项目约束冲突时，指出具体冲突和取舍，不要默默选择一种解释。

## 2. 用最简单的有效方案

- 只实现当前目标要求的行为，不添加投机功能、配置项、扩展点或兼容层。
- 优先复用现有结构和惯例；只有出现真实的复用、变化或职责边界时才增加抽象。
- 不为现有契约与实际证据都未支持的假想场景增加复杂处理；对可信的安全与数据风险仍必须正确处理。
- 如果预期实现明显复杂于问题本身，重新检查需求和方案，优先减少概念、分支与变更面。

## 3. 只修改必要范围

- 确保每项改动都能直接追溯到用户目标，或用于清理本次改动产生的无用内容。
- 遵循局部命名、格式和错误处理方式，不顺手重构、重排格式或改写无关注释。
- 发现无关的死代码、旧问题或潜在改进时，只记录并告知，不自行扩展任务范围。
- 保留用户已有改动和预先存在的无关问题；只清理本次修改造成的孤儿导入、变量、函数、测试辅助代码或文档引用。

## 4. 用验证证明结果

- 修改前定义可观察的成功标准；多步骤任务使用简短的“步骤 → 验证”计划，简单任务不强制列计划。
- 缺陷修复优先重现问题，新增行为覆盖关键成功与失败路径，重构确认前后行为一致。
- 先运行与改动直接相关的检查，再按项目规则执行必要的回归验证。
- 检查最终差异，确认没有未解释的文件、行为变化、投机能力或本次改动产生的孤儿内容。
- 无法完成验证时，明确说明已验证范围、未执行项和剩余风险，不把“未执行”描述为“通过”。

## 交付

先说明完成结果，再列出实际验证、未验证项和有意保留的范围。不要用笼统的“已完成”或“已测试”代替可复查的证据。
