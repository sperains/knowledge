# 月度日报总结

## 概览

将一个自然月内的日报整理成主题化、可追溯的月度工作总结。以已有日报为事实来源，合并重复主题，区分已完成、进行中和计划事项；不把提交记录、文件清单或推测内容直接当成总结。

## 目标与默认路径

- 月份由用户明确指定的 `YYYY-MM` 决定；未指定时使用当前日期所在月份。涉及“上月”“本月”等相对日期时，先按当前时区换算成绝对月份。
- 在知识库中查找 `Worklog/Daily/YYYY/MM/`，读取其中命名为 `YYYY-MM-DD.md` 且日期属于目标月份的日报。
- 默认将月报写入 `Worklog/Monthly/YYYY/YYYY-MM.md`。目录或文件不存在时创建；已有月报必须先阅读，并在保留手工补充的前提下更新。
- 输出路径、知识库位置或月份规则存在项目级约定时，以当前知识库的 `README.md`、`Worklog/README.md`、模板和适用的 `AGENTS.md` 为准。

## 执行流程

### 1. 读取规则并收集日报

- 先读取知识库说明、日报规则、月报模板（如果存在）以及仓库或项目级适用规则。
- 按文件名和文件内一级标题双重确认日期；忽略临时文件、索引文件、其他月份文件和明显不是日报的笔记。
- 没有目标月份日报时，不创建空月报，不虚构工作；说明未生成或未更新的原因。

### 2. 提取并归并事实

- 只使用日报中明确记录的完成内容、结果、问题、经验和关联资料；日报未说明的动机、收益或完成状态不得补写。
- 将同一目标跨多天出现的实现、修复、排查和验证合并为一个主题，不按日期机械罗列，也不重复同源改动。
- 优先提炼“完成了什么、解决了什么、带来了什么结果”；对仍在进行、延期、阻塞或仅提出的事项保持原状态，不改写为已完成。
- 汇总时不记录提交时间、提交编号、分支名、逐日流水账或文件列表；不展开测试文件明细，只保留日报中明确记载的验证结论。
- 对架构、数据边界、性能策略、协作约束等可复用内容单独判断，只有有明确证据时才写入“架构与经验沉淀”。

### 3. 生成月报

使用中文自然描述，默认采用以下结构；没有实际内容的章节删除，不保留空标题：

```markdown
# YYYY-MM

## 月度概览

用一段话概括本月主要工作方向、最重要的成果和仍需关注的问题。

## 主要工作

### 1. 工作主题

- 完成内容及覆盖范围。
- 关键结果、影响或当前状态。

## 重点成果与影响

- 仅记录日报中有证据支持的结果和影响。

## 问题、风险与未完成事项

- 只保留日报明确记录的阻塞、风险、遗留项和后续动作；没有此类内容时删除本节。

## 架构与经验沉淀

- 只记录本月形成、验证或明确强化的可复用原则、边界和取舍；没有则删除本节。

## 下月建议

- 仅根据日报中的未完成事项、风险或明确后续计划提炼；不得凭空制定新计划。

## 相关资料

- 只链接实际被本月工作直接引用或形成关联的具体设计文档、ADR 或专题笔记。
```

### 4. 更新已有月报

- 先识别已有月报中的手工内容、已确认结论和原有链接，不整篇覆盖。
- 只更新由本月日报支持的生成区域；无法判断某段是否为手工内容时保留原文，并在相邻位置补充而不是删除。
- 若已有月报与日报冲突，保留事实来源和不确定性，不能默默把历史内容改写成新结论。

### 5. 校验并反馈

- 校验目标月份、源日报范围、章节结构、序号连续性和所有知识库链接。
- 检查正文没有提交时间、提交编号、合并提交信息、逐日流水账或无证据的完成表述。
- 汇报实际读取的日报数量、被排除的文件及原因、生成或更新的月报路径；无内容时明确说明未写入。

## 约束

- 月度总结不是日报拼接，也不是 Git 提交报告；必须以主题和结果为中心。
- 不能把“计划、待处理、排查中、部分完成”改写成“已完成”。
- 不能用其他字段、其他月份或其他作者的内容补齐缺失事实。
- 不创建 Git 提交、推送或发布操作，除非用户另行明确要求。
